## 摘要
检索增强生成（RAG）将大语言模型锚定于外部知识。现代流水线结合了嵌入、分块、检索、重排序、查询增强、上下文压缩与智能体验证，然而这些技术通常被逐一评估。尚不清楚它们的孤立增益在组合后是否仍然存在，检索质量与答案忠实度是否偏好相同的设计选择，以及来自小规模语料的结论是否在大规模下成立。我们预先声明三项假设，并引入 LASAGNA——一个用于受控 RAG 评估的开源框架。我们在八个基准以及从 5K 到 200K 文档的语料上测试了 450 种配置。得到三项发现。第一，来自 RAG 流水线不同阶段的单独表现强的技术不一定能够组合：三种检索技术预测可获得 +47% 的组合提升，但一起使用时仅带来 +17%。第二，各组件增益对检索与忠实度的叠加方式不同，优化其一可能损害另一。第三，最佳组合会随语料增长而变化：在小语料上胜出的组合在大规模下未必仍为最佳。这些发现表明，孤立测得的增益并不能可靠预测真实性能，新的 RAG 技术应在完整周边技术栈中测试。我们呼吁研究者这样做，并提供 LASAGNA 以简化这些实验。

## Abstract
Retrieval Augmented Generation (RAG) grounds large language models in external knowledge. Modern pipelines combine embedding, chunking, retrieval, reranking, query augmentation, context compression, and agentic verification, yet these techniques are typically evaluated one at a time. It remains unclear whether their isolated gains survive composition, whether retrieval quality and answer faithfulness favor the same design choices, and whether conclusions from small corpora hold at large scale. We pre-declare three hypotheses and introduce LASAGNA, an open-source framework for controlled RAG evaluation. We test 450 configurations across eight benchmarks and corpora ranging from 5K to 200K documents. Three findings emerge. First, individually strong techniques from different phases of a RAG pipeline do not necessarily compose: three retrieval techniques predict a +47% combined improvement but deliver only +17% when used together. Second, component gains stack differently for retrieval and faithfulness, and optimizing one can hurt the other. Third, the best composition changes as the corpus grows: the combination that wins on a small corpus may not remain best at large scale. These findings show that gains measured in isolation are not reliable predictors of realistic performance, and that new RAG techniques should be tested with the full surrounding stack. We call on researchers to do so and supply LASAGNA to simplify these experiments.

## 一、核心问题与整体含义（研究动机与背景）

- **背景**：RAG 已成为将 LLM 锚定于外部知识的主流范式。现代 RAG 流水线横跨八个阶段：嵌入、分块、索引期增强、检索、查询增强、重排、上下文压缩、智能体质量门控（agentic gate）。
- **核心痛点**：文献中的新技术几乎都是**单阶段、孤立地**在简化基线上评估，并把孤立增益直接当作"推荐配置"；但真实部署必须把这些技术**组合**起来。
- **三个未解问题**（即三项预先声明的假设）：
  - **H1（可加性假设）**：单组件消融测得的增益，在组合后是否仍然保留？（对应"组件是否可加"）
  - **H2（配方通用性假设）**：是否存在一个固定配方能同时覆盖"检索质量–忠实度–延迟"的多个部署目标？还是必须逐部署调参？
  - **H3（尺度不变性假设）**：在 5K–50K 小语料上得到的配置排名，能否外推到生产级（大一个数量级）语料？
- **整体含义**：论文不是提出新 RAG 技术，而是**对"RAG 研究的方法论本身"做实证审计**，主张把"组合式评估"作为新技术的报告标准。

## 二、方法论：核心思想与关键技术细节

### 2.1 核心思想

- 构建**阶段隔离（stage-isolated）**的开源框架 **LASAGNA**，使"换掉一个组件"不会悄悄改变相邻阶段的实现，从而让配置差异可归因于被变化的组件。
- 用**因子实验设计（factorial design）**而非贪心搜索，直接估计主效应与两两交互效应，并跨**两个度量（检索 / 忠实度）**与**多个语料规模**重复测量。

### 2.2 框架工程细节

- **9 个处理阶段**：文档处理 → 分块 → 索引期增强 → 嵌入与索引 → 查询增强 → 检索 → 重排 → 上下文压缩 → 答案生成（含可选智能体验证）。
- **8 类组件抽象基类（ABC）**：`embedder / chunker / reranker / retriever / document_processor / query_enhancer / agentic_pipeline / generator`；阶段间用类型化 dataclass 契约传递。
- **注册机制**：单行装饰器 `@registry.register("<stage>", "<name>")` 即可让新组件在 YAML 配置期被发现；配套 YAML 声明式因子扫描 + 端到端运行 + 配对统计检验（图 2 三步工作流）。
- **内置资源**：53 个内置组件、30 个方法（对应 8 个因子维度）、6 个向量后端（Milvus、Pinecone、Qdrant、Weaviate、pgvector、OpenSearch）、15 个基准适配器（本研究用 8 个）、MCP 服务器（31 个工具）、配置器 UI。
- **5 项自动化隔离测试**（全部通过）：Pydantic 类型强制、**会话配置隔离**（A 会话改配置不影响 B）、嵌入维度检测（384 维灌入 1024 维集合报错）、分块器无状态性、插件自动发现。

### 2.3 实验设计方法（统计）

- **全因子规模**：4×4×4×3×5×4×2×4 = 30,720 种配置，估算需 ~40,000 GPU 小时、~$600,000，超出预算两个数量级。
- **D-最优分数因子设计**：用 **Fedorov 坐标交换算法**（逐行交换以最大化 D 准则 φ_D(X) = det(XᵀX)）抽取 **242 行**子设计；模型矩阵含 1 截距 + 22 主效应 + 209 两两交互 = **232 参数**，留 10 个残差自由度；采用**效应编码（±1）**保证主效应与截距正交。实际执行 167 个（63 个 GraphRAG 组合因孤立消融无收益被剔除，12 个超时）。
- **关键公式**：
  - NDCG@k：DCG@k = Σᵢ (2^{rᵢ} − 1) / log₂(i+1)，再除以 IDCG@k；检索块先按父文档 ID 去重再计分。
  - 忠实度（RAGAS）：将答案分解为原子声明 {c₁…c_M}，Faithfulness = (1/M) Σ 1[claim cₘ 被上下文支持]。
  - 联合超体积：**HV(L_ref) = NDCG@10 × Faith × max(0, 1 − latency / L_ref)**，主参考 L_ref = 30 s。
  - 交互强度用偏 η²（Type-III ANOVA）与 Holm/Bonferroni 校正。
- **统一多域语料**：把 8 个基准合并进**单一向量库**，让每条查询都承受跨域干扰文档压力（区别于 BEIR 的逐基准评估）。
- **两个评估轨道**：检索轨（BEIR qrels，5,132 文档 / 93 查询）与端到端生成轨（注入金标段落后 5,566 文档 / 56 查询）。
- **语料缩放协议**：从同一 5 个 BEIR 域采样干扰文档，按 5K/15K/25K/50K/100K/200K 增量注入，并做三级去重验证（基座∩增量 = ∅、增量间两两交集 = ∅、文件内无重复）。
