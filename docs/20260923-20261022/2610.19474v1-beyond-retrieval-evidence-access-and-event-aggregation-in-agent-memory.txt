# Beyond Retrieval: Evidence Access and Event Aggregation in Agent Memory 

Zerui Yang *, Quan Xue, Chaorui Zhang † Xueyan Niu, Xuanyu Zheng, Xiyuan Wang , Haolin Ruan , Guangcheng Song , Weixi Zhang , Wei Han , Bo Bai

Abstract 

Questions about an agent’s history often require aggregating events, which retrieval alone does not resolve. We combine source-preserving evidence access with executable aggregation. Trajectory Memory (TM) retains the original trajectory and constructs a source-addressable reading view at question time. TallyMem aug-ments it with a reusable event ledger, model-generated event specifications and determinis-tic execution. With a commit-specific adapta-tion on 776 questions from 99 held-out MINTE-val repositories, TallyMem raises Qwen3-32B exact match from 35.2% to 49.0%, a 13.8-point gain over TM; gains span 12.8–13.9 points across three readers. A controlled probe with event sets parsed independently from raw logs shows an 11.0-point gain, from 82.8% to 93.8%, without routing. On full AMA-Bench, the routed system yields a smaller 1.3-point gain, from 69.8% to 71.1%. These results sup-port executable aggregation on tasks that re-quire combining events, with benefits depen-dent on the task and event specification, the largest residual system-error category in our diagnostic analysis. 

1 Introduction 

An agent that edits a repository, navigates a website or operates in a simulated home accumulates a history of actions and observations. Later questions about that history can ask what happened at one step, how an object’s state changed, or how often an action was taken (Zhao et al., 2026; He et al., 2026; Xu et al., 2026b). Answering them may need the exact action, its result and its position. Such questions place two distinct demands on memory. The first is access : the steps that deter-mine the answer must reach the reader unchanged. The second is aggregation : when an answer com-bines many events, they must be selected and com-

bined correctly. Common memory designs retrieve evidence from summaries, extracted facts or linked records (Packer et al., 2023; Chhikara et al., 2025; Xu et al., 2026a; Gutiérrez et al., 2024). These ap-proaches emphasize evidence access through reten-tion and retrieval; combining the retrieved events remains a separate challenge. Figure 1 shows why this is not enough: even a reader given all 150 steps of a trajectory miscounts five of eight action types. For access, we argue for deferred evidence se-lection . Memory written before the questions are known must guess what will matter: a sum-mary commits to an interpretation that a later ques-tion may contradict, and AMA-Bench attributes memory errors to lost objective information and causal order (Zhao et al., 2026). We therefore keep the trajectory verbatim and decide what to show only at question time. Trajectory Memory (TM) implements this principle through a lossless, source-addressable archive and a budgeted, order-preserving reading view, built without model calls. Better access does not remove the second de-mand. We measure a question’s aggregation load ,the number of events its answer combines. On a controlled probe with event sets parsed from raw logs, long-context reading of fully visible histo-ries answers the same count correctly for 100% of trajectories at 14 events but for 80% at 53 events. On AMA-Bench, a compiler-derived load proxy shows TM falling from 77.1% at one to five events to 10.0% above a hundred (Figure 2). The probe supplies independent event sets; reference-answer-derived loads provide an approximate cross-check (Appendix G). TM’s advantage over long-context reading is larger for each of five readers when the history exceeds the context budget, while aggrega-tion errors remain on fully visible probe histories.

Held-out repository evaluation and controlled aggregation tests, alongside full-benchmark comparisons and analysis of residual event-specification errors. 

2 Related Work 

Agent memory. MemGPT, Mem0 and A-Mem organize experience through summaries or ex-tracted records (Packer et al., 2023; Chhikara et al., 2025; Xu et al., 2026a); HippoRAG retrieves through a knowledge graph (Gutiérrez et al., 2024), and MemSearch-o1 constructs query-aligned frag-ments (Zhang et al., 2026). Evaluation extends from dialogue to agent trajectories (Maharana et al., 2024; Wu et al., 2024; He et al., 2026; Zhao et al., 2026; Yang et al., 2026). We study evidence ac-cess and event aggregation on AMA-Bench and MINTEval (Lee et al., 2026). 

Executable memory and event specifications. 

Binder generates programs with model calls (Cheng et al., 2022), ChatDB uses SQL as sym-bolic memory (Hu et al., 2023), and AMA-Agent executes code over trajectories (Zhao et al., 2026). Retrieval versus aggregation. Available context does not ensure correct use of evidence (Liu et al., 2024). RULER and Oolong test information aggre-gation (Hsieh et al., 2024; Bertsch et al., 2025); con-trolled studies identify instance count as a source of difficulty (Dai and Fan, 2026; Chen et al., 2026). MemTrace finds failures despite retrievable evi-dence (Long et al., 2026). Our trajectory analysis distinguishes evidence-access failures from errors in selecting and combining events. 

3 Problem Formulation 

Trajectories and memory. Let H =(( i, a i, o i)) i∈I H be an ordered trajectory of actions ai and observations oi (Yao et al., 2022). Memory is built from H before questions arrive. Given a later question q, it supplies context Cq to a fixed answer model, by = Fθ(q, C q). We compare systems with shared readers and judges; TM’s view has budget B; computed evidence has its own bound. 

Two requirements. The first requirement is ac-cess : the steps that determine the answer must reach Cq unchanged and in order, so that the reader can use the exact action, its observed result and its position. Many questions also ask for a quantity over a set of steps,

6 Separating Specification from Execution: TallyMem 

TallyMem takes aggregation away from the reader. A model writes the specification (Iq, ϕ q, g ) of Equation 1 as a plan in a small typed query lan-guage, and an executor evaluates the plan exactly over an event ledger of the whole trajectory. The model therefore decides what to count but never does the counting (Lyu et al., 2023). TM is un-changed, and the result is added to its reading view (Figure 4).

7.2 AMA-Bench: Aggregation Gains and Overall Performance 

Full-set gains over TM are modest. With Qwen3-32B (Yang et al., 2025), TM reaches 69.8% and TallyMem 71.1%, a 1.3-point gain; gpt-oss-120b (Agarwal et al., 2025) reaches 78.4% and 79.2% (+0.8), and Qwen3-8B (Yang et al., 2025) reaches 60.7% and 62.3% (Table 2). Qwen3.6-27B (Yang et al., 2025) improves overall (Table 17), but its held-out-half gain is only 0.1 points, with a 95% trajectory-bootstrap interval of [ −0.7, +1.0]. With-out routing, Qwen3-32B reaches 70.4% (+79/ −63 versus TM, p = 0 .21 ); the overall gain is not signif-icant under the paired sign test. Appendix I reports gains, intervals and trajectory splits. On the 212 questions where the router attaches nonempty evidence (compiled load above 15), Qwen3-32B rises from 43.9% to 59.4% (+47/ −14). These are the same 33 net additional correct an-swers as in the full-set routed comparison. The subset explains that gain but is selected by the method, rather than independently defining aggre-gation difficulty. TM also exceeds the external memory systems in the same Qwen3-32B deploy-ment, of which BM25 is strongest at 46.1%. Re-moving only the counts of TM’s keyword-triggered counter (239 questions) leaves TM at 69.5%, still 4.5 points above long context (Appendix I). TM achieves state-of-the-art performance relative to the previously reported AMA-Bench methods com-pared here (Appendix D). 

7.3 Held-Out Repository Histories: Cross-Dataset Evaluation 

MINTEval tests the ledger-and-execution approach on commit histories with held-out repositories (Lee et al., 2026). We adapt the ledger and compiler prompt to commits: a program extracts file addi-tions, deletions, renames and added assignment lines from diffs. The adaptation was developed on 25 repositories and evaluated once on 99 held-out ones. TallyMem raises exact match from 35.2% for TM to 49.0%, a 13.8-point gain, and exceeds long-context reading at 39.2% by 9.8 points (Table 2), with the strongest gains in file order and value history. Answering from the same evidence, gpt-oss-120b and Qwen3-8B show the same ordering: 41.1% and 36.5% with long context, 37.8% and 32.2% with TM, and 50.6% and 46.1% with Tally-Mem. The gain comes from the computation path, which also reaches commits outside TM’s reading view: with every reader TM alone trails long con-text, because commit questions can lose evidence to the retrieval budget even when they involve few events (Appendix M). 

7.4 Controlled Probe: Testing the Aggregation Mechanism

Long context reaches only 49.3%, partly be-cause truncation cuts every software trajectory; on 20 fully visible embodied trajectories, its accuracy on the same count falls from 100% to 80% as mean load grows from 14 to 53 events. 

8 From Miscounting to Misspecification 

Execution removes miscounting where the specifi-cation is right: on the probe, a correct plan written from each template’s definition, run by the same ex-ecutor and reader, answers 99.2% of the questions from templates whose events the ledger records (Appendix H). We then analysed every error Tally-Mem makes on the 630 diagnostic questions with Qwen3-32B (Pan et al., 2023) (Appendix N). 

Where the errors are. Of the 214 errors, 66 re-ceive no computed evidence and are TM’s own. We labelled the other 148 with a decision proce-dure fixed before inspection: a reference or judging error if the answer agrees with the log; otherwise an answering error if the evidence suffices, partial coverage if the error lies outside the evidence, a specification error if the plan does not express the referenced quantity, and a ledger error if it does but the rows are wrong. None arises in execu-tion or in truncating the evidence (Table 3), and an independently written matcher reproduces ev-ery stored result (Appendix I). Specification is the largest category: 51 errors, 49% of the 104 that re-main after excluding reference, judging and unclear cases, against 20% each for the ledger and the final answer. Another 42 answers agree with the log but are rejected because the reference is wrong (29) (Northcutt et al., 2021) or the judge errs (13). Other readers given the same evidence answer 39.3% of the answering errors but only 18.1% of the specifi-cation errors, so the latter are systematic. 

What misspecification looks like. Most specifi-cation errors select the wrong events (36 of 51). For questions about actions on an object, the reference counts only opening and closing it, whereas the plan lists every step that names it; a literal filter for 

drawer 1 also matches drawer 10 ; “between Step 6 and Step 9” is read inclusively. Others choose the wrong operation (11). In 26 cases the plan’s read-ing is defensible and the reference adopts another. On the probe, where event sets are parsed from the log, 21 of 36 plans for a question that names the create, replace and insert commands also count 

view , and the correct plan raises them from 75.0% to 97.2%; non-zero exit codes, which the ledger does not record, are approximated by the failure outcome. Because each result states its filters and step IDs, such errors can be checked against the log, whereas a reader’s miscount leaves no trace (Appendix O). 

More freedom moves the same error. Three controls point the same way: five sampled plans repeat the same choice (Chen et al., 2023) (Ap-pendix K); TM’s fixed counter fails when the wording differs (Section 7.4), so a fixed aggregate also fails on specification; and free-form Python over the same ledger and log reaches 62.1% (TM 61.9%, TallyMem 66.0%) (Wang et al., 2024) (Ap-pendix L); on the probe it reaches 86.2% against TallyMem’s 93.8%. Detailed code comparisons and error examples appear in Appendices L and O. 

9 Conclusion 

TM preserves source evidence; TallyMem makes event selection explicit and executes aggregation. The controlled probe supports the aggregation mechanism, and the adapted MINTEval evalua-tion shows gains on held-out repository histories. Full AMA-Bench gains are modest and depend on routing and the reader. Executable aggrega-tion therefore offers a task-dependent benefit, with event specification the main residual challenge. 8Limitations 

Our evidence covers AMA-Bench, a controlled probe built from its embodied and software trajec-tories, and the GitHub subset of MINTEval, not all agent or dialogue memory tasks. Gains vary across question types and domains (Appendices E and P) and trajectory splits (Appendix I). Appendix I dis-cusses judging, reference answers, method develop-ment and the single-annotator error analysis. The ledger and the query language cannot express every event predicate, and on MINTEval TM alone trails long context. 

Ethics Statement 

We use public agent-trajectory and repository-history benchmarks and collect no new personal data. Trajectory content is treated as untrusted data. The ledger builder does not execute commands contained in a trajectory; compiled queries select operations from a fixed executor rather than run-ning arbitrary model-written code. The free-form code control runs model-written programs only in an operating-system sandbox without network or file access. 

Use of AI assistance. 

AI tools were used only for language polishing and assistance with writing code. The research ideas were developed by the authors.

Quote recovery. The frozen computation path retries quote matching after a looser normaliza-tion when a row was rejected for quote formatting. The path also restores truncated target lists when the preserved prefix agrees. These rules check textual occurrence, not semantic entailment or the completeness of the annotation. 

Plan and result handling. The query language supports the operations in Equation 7; it does not support arithmetic over values, joins or free-form code. Compilation uses temperature 0 and no think-ing. A catalog provides tool names, the 40 most frequent targets and the 20 most frequent change properties. Filters are case-insensitive substring matches: lists are disjunctions and different fields are conjoined. Explicit question bounds define the scope, including open bounds and distinct bounds for sub-queries. Results are capped at 6,000 char-acters, with compressed step ranges and grouped outcomes; failed actions can be separated by error text. A timeline or list query with no matches is retried once with only its object and action filters, and any result is marked relaxed. Otherwise un-grounded or empty sub-queries are dropped. F Context Fit and Actual Visibility 

The context-fit strata use raw trajectory length at most 24k tokens. This is a property of the history, not proof that TM displays it completely: TM’s saved configuration uses per-field caps of 1,200 characters, or 4,000 for anchor steps. Selecting every step can therefore still omit part of an obser-vation. For a separate check, we join the existing fit and load annotations to the saved Qwen3-32B long-context answers. The long-context wrapper renders all original actions and observations and truncates only when the total exceeds its token target. Every saved context in the nominal-fit, nonempty-load strata is strictly below that target. Accuracy is 78.9% (90/114) at loads 1–15 and 32.2% (28/87) above 15. This establishes a high-load decline with complete visible histories for the long-context con-trol; it does not establish complete visibility for TM. This is an additional descriptive audit of ex-isting answers, not a new model evaluation or a pre-registered analysis. The same compiled-load and domain-composition limitations apply.

H Controlled Aggregation Probe 

Design. A deterministic script generates the ques-tions over all 30 embodied and 36 software tra-jectories of AMA-Bench, the two domains whose actions have a fixed format. Answers and event sets S⋆ are parsed from the raw action and obser-vation strings only, without the ledger, the com-piler or a model: embodied actions by their leading verb; software actions by the tool name before the colon, with editor commands and paths read from the JSON arguments and the exit code of a bash command taken from the last “exit code N ” in its observation. For a trajectory with n steps the bounds are b1 = ⌊n/ 4⌋ − 1, b2 = ⌊n/ 2⌋ − 1 and 

b3 = n − 1, phrased “up to and including step b”. A template is skipped for a trajectory without the relevant event or, for the most-visited location, with a tie. Each question states its answer format (an integer, a step number, a comma-separated list or “none”, or a name). Table 12 lists the templates and the accuracy of each system. 

Protocol. Templates, bounds, systems, scoring and analyses were written down before the ques-tions were generated, and the question files were hashed before any answer was produced. The sys-tems are TM, unchanged; TallyMem in its frozen principal configuration without routing, compiling on the same deployment; a fixed counter, which runs the same executor and renderer with one plan per question (group by tool within the stated bound, or over all steps for first-event templates) and thus involves no compilation; and long-context read-ing. Three arms were added after these results: a correct-plan arm, a second reader and free-form code (below). Qwen3-32B (bf16, local vLLM) answers with thinking enabled; compilation and judging run without thinking, as in the main evalu-ation.

Execution. Re-executing the stored plans of all 2,459 full-benchmark questions whose plan parsed reproduces their evidence byte for byte. An inde-pendently written matcher, which implements the documented filter semantics (case-insensitive sub-string terms, outcome sets, inclusive step ranges and the relaxation rule), recomputes the matched steps, first and last steps and tool or outcome groups of all 1,160 rendered sub-queries of the 804 ques-tions with evidence identically. The evidence is therefore a deterministic function of the plan and the ledger; whether either is right is what Table 3 labels. 

Judging, references and development. AMA model judging and reference-answer ambiguities add uncertainty. On the probe, where references are parsed from the logs, the official judge ac-cepted 36 wrong answers among the answers we read (Appendix H). The later compiler refinement followed in-spection of the principal method’s errors, and the reported AMA results include the trajectories used for method development (Table 16 separates the two halves). 

Other limitations. Aggregation load on AMA-Bench is defined by compiled queries and the extreme bins are small; alternative measures are checks, not independent difficulty annotations, and the probe’s parsed load covers two domains and generated templates. The free-form code con-trol uses one model and one prompt design (Ap-pendix L). The error analysis covers one reader on the diagnostic questions, and its labels were assigned by a single annotator following a fixed procedure, with a written rationale for each case. N Error Analysis Protocol 

The analysis covers the 214 errors of TallyMem on the 630 diagnostic questions with Qwen3-32B, using the principal configuration with computed evidence always attached ( γ = 1 ). It uses frozen outputs only: no model was called and no method was changed afterwards. The procedure was writ-ten before any error was inspected. 

Stage 1. Errors without computed evidence (66) are separated automatically. Their answers are TM’s: the compiler declined in 20 cases, every sub-query failed the grounding checks in 43, and compilation failed in the rest. 

Stage 2. Each remaining error was labelled from the question, the reference, the compiled plan, the per-sub-query outcomes, the rendered evidence and the final answer, and the raw log and ledger were consulted whenever the label depended on them. The first applicable label is assigned, in this or-der: reference or judge (the answer agrees with the log in substance, and the reference contradicts the log or the judge rejects a correct answer); an-swering (the rendered evidence states everything the reference requires, or the answer contradicts what it states); partial coverage (the evidence is correct and the error lies only in parts answered from TM’s view); specification (the scope, predi-cate or operation does not express the referenced quantity, including a requested quantity that was not compiled or was dropped); ledger (the plan ex-presses the quantity but ledger rows are wrong or inconsistent); truncation (a correct result was cut by the rendering budget); unclear. A plan whose reading of an ambiguous question is defensible is still a specification error and is flagged; 26 of the 51 specification errors carry this flag. Four clarifi-cations were added while labelling and applied to all cases: contradicting stated evidence counts as an answering error; evidence that must be joined or recomputed across sub-queries does not state the quantity; a flawed reference yields the reference label only if the answer is correct against the log; and an answer that adds a false claim to otherwise complete content is an answering error. The last rule moved four cases out of the reference category. 

Validity check. The evidence of each question is shared by all readers, so a systematic error should persist across readers while an answering error should not. As specified in advance, we compared the accuracy of the other four readers on answer-ing and specification errors: 39.3% versus 18.1% (two-sided permutation test, p = 0 .005 ). O Error Analysis and Later Compiler Changes 

Selection errors. For a query that counts logged steps, let S be the executed set and S⋆ the intended set of Equation 1. Before rendering and answering, the computed count error is 

|S| − | S⋆| = |S \ S⋆| − | S⋆ \ S|, (12) the difference between extra and missed events. Both terms can be checked against the log because each result states its filters and supporting step IDs, although S⋆ itself is unknown at inference time. Equal counts can still conceal cancelling errors (Figure 9). 

Where computation does not help. First/last-change and single-step state questions are flat (Ta-ble 8), because retrieval already finds the relevant step. By domain, the gain comes mostly from em-bodied trajectories (Table 23 in Appendix P). Multi-part text-to-SQL statistics improve only partly (22 

→ 27 of 51), because the gold answers’ notion of an “object” often differs from the ledger’s. Harm-ful evidence mostly comes from inconsistent target labels in the annotated ledger (for example, a web element labelled differently across steps) and from content questions about code, which the refined compiler now leaves to retrieval. 

Execution fails when the quantity is misspecified. 

The following Qwen3-32B DeepInfra diagnostic examples show programs executing exactly what the plan asked, while the plan’s notion of the quan-tity differs from the gold answer’s. • For “which containers has the agent interacted with and what state changes occurred”, the gold answer lists only open and close events. The plan grouped every step that visited or looked at an object. • For “which objects has the agent interacted with and how many times”, the gold answer counts only objects picked up or moved. The plan counted visits to furniture. Sampling more plans does not fix a definition the compiler consistently gets wrong, which explains why self-consistency fails. A general rule does fix part of it: questions about state changes use only steps with recorded changes. The refined compiler raises the container template from 4 to 12 of 26 questions. Overall, the refined compiler answers 423 of the 630 questions correctly, against 416 for the principal compiler and 390 for TM. The computation path thus converts an error that cannot be inspected (a miscounted list) into one that can be examined: a query that says what it counted. 

A fixed counter is a special case. TM’s keyword-triggered counter is itself a small program. On count questions where it fires, TM is nearly as accurate as TallyMem (67% vs. 68%, 221 ques-tions). A fixed aggregate works when the question happens to match it; the probe isolates this effect by asking the same count in two wordings (Ap-pendix H). Compiling the question extends this to groupings, outcome breakdowns, first/last queries and timelines.
