## 摘要
显式记忆系统将对话历史转化为持久表示，旨在改善未来的访问，但通常伴随可观的构建成本。然而，这种额外复杂性是否能比直接从原始历史中检索带来更高的答案准确率，仍不清楚。本研究在原始和受控检索设置下，于 LongMemEval-S 和 BEAM-100K 上比较了六种最先进的显式记忆系统与原始历史 RAG。我们发现，仅在特定问题类型和紧张的运行时上下文预算下存在局部增益，且相对于强原始历史 RAG 基线并无一致优势。Oracle 检索表明，一些系统在显式记忆构建过程中未能保留支撑答案的信息，而另一些系统虽保留了这些信息却未能有效检索到，尽管构建成本可达每段对话数小时。我们的发现表明，尽管许多面向 AI 智能体的现有记忆系统强调日益精细的显式记忆构建，但它们往往在没有与原始历史 RAG 进行强受控比较的情况下被评估，并可能低估了检索的重要性。当有用信息被保留时，检索仍是主要瓶颈，这表明改善对现有信息的访问至少与构建更丰富的显式记忆同样重要。

## Abstract
Explicit memory systems transform conversation history into persistent representations intended to improve future access, often at substantial construction cost. Yet it remains unclear whether this added complexity yields better answer accuracy than retrieving directly from raw history. This study compares six state-of-the-art explicit memory systems with raw-history RAG on LongMemEval-S and BEAM-100K under original and controlled retrieval settings. We find only localized gains for particular question types and tight run-time context budgets, with no consistent advantage over strong raw-history RAG baselines. Oracle retrieval shows that some systems fail to preserve answer-supporting information during explicit memory construction, while others preserve it but fail to retrieve it effectively, despite construction costs reaching hours per conversation.   Our findings suggest that while many existing memory systems for AI agents emphasize increasingly elaborate explicit memory construction, they are often evaluated without strong controlled comparisons to raw-history RAG and may underemphasize retrieval. Retrieval remains a major bottleneck when useful information is preserved, suggesting that improving access to existing information may be at least as important as constructing richer explicit memory.

## 2. 方法论

### 2.1 核心思想：三阶段统一评测流水线

将显式记忆系统与原始历史 RAG 统一放入 **构建 → 检索 → 回答** 三阶段框架，核心原则是**固定已构建的记忆表示，只变动下游检索与回答条件**，从而分离各因素的作用。

- **构建（Construction）**：系统 $s$ 由对话历史 $H$ 构建检索单元集合 $M_s = C_s(H)$。显式记忆系统的 $C_s$ 含摘要、抽取、更新、组织；原始历史 RAG 的 $C_s$ 直接索引原始对话，不做 LLM 构建。每个 $M_s$ 只构建一次，全程固定。
- **检索（Retrieval）**：$U_{s,r} = P_s(q, M_s; r)$，其中 $P_s$ 是系统特有的完整检索流程（可能含查询改写、规划、多路检索、结构扩展、过滤、合并、反思），$r$ 是其中可替换的检索器。受控实验只替换 $r$，保留系统其余检索逻辑。
- **回答（Answering）**：$\hat{a}_{s,r,b} = G(q, U_{s,r}; b)$，$G$ 为回答生成器，$b$ 为上下文预算。
- **两种上下文预算形式**：top-$k$（$k \in \{3,5,10,20\}$）与 token 预算（$B \in \{200,500,1000,2000\}$）。token 预算按排名顺序累加检索单元，超预算即停止，不跳过；首单元超预算则截断保留前缀。

### 2.2 关键技术细节：Oracle 检索（用于定位瓶颈）

- 利用 BEAM-100K 的标注"支撑对话轮"，绕过实际检索器，直接把应提供给生成器的信息送入回答模型，测得"该表示在无检索误差时能支撑的准确率"。
- 实现方式依赖**溯源（provenance）**：每个检索单元记录其来源（单轮、轮对、20 轮窗口或整个 session）。当单元溯源与标注支撑轮有重叠时纳入 oracle 上下文，不设 top-$k$ 与 token 限制；无匹配则用空上下文。
- **两类差距的诊断意义**：
  - 显式记忆的 oracle 准确率 vs. all-turns 的 oracle 准确率 → 衡量构建阶段损失了多少"可回答性"；
  - 该方法 oracle 准确率 vs. 其在 RQ2 中 64 种配置下的最佳实际检索准确率 → 衡量检索未实现多少潜力。

### 2.3 成本核算方法

- 分三阶段计量：构建（每段对话的 LLM 调用次数、token 数、wall time）、检索（每问的 LLM token 与耗时，含查询编码、检索、查询时 LLM 调用，不含模型加载与索引构建）、回答生成（每问的 token 与耗时）。
- 查询时总成本 = 检索 + 回答，不含构建；构建成本视为可被未来查询摊销的前置投入。
