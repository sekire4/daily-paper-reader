## 摘要
智能体记忆架构定义了 LLM 智能体如何跨任务存储和复用经验，但这类架构通常在部署后即固定，限制了其跨任务类型的适应性。近期的自演化方法则利用执行反馈来适配这些记忆架构，反馈通常表示为评估分数或压缩摘要。然而，在当前智能体系统中，长时程任务执行涉及多个相互作用的组件，这种粗粒度反馈不足以精确定位失败。在没有精确失败位置的情况下，现有方法缺乏明确的代码级修改目标，导致更新范围约束较弱，并往往对原本性能良好的记忆架构进行大规模重写。我们提出 MemScope，一个面向现有记忆架构的、基于证据的局部化演化框架。其使用工具的 Patch Agent 联合检查原始执行轨迹、运行时记忆状态和当前架构代码，以识别修复目标，并在提供者身份和记忆兼容性约束下施加有界的原地编辑。在 GAIA 上，轨迹与记忆联合检查变体达到 86.67% 的准确率，而仅使用轨迹和仅使用摘要反馈分别为 70.00% 和 63.33%。在 xBench 任务中，演化后的记忆架构相比原始版本，在使用 DeepSeek V3.2 时正确回答数从 49 提升至 55，在使用 Kimi K2.7 Code 时从 50 提升至 53。在互不重叠的 ALFWorld 未见任务上，成功率从 50.75% 提升至 71.64%。在归档的架构快照迁移中，代码变更比例的中位数为 4.4%。这些结果支持将细粒度执行证据作为局部化、原地记忆架构演化的基础。

## Abstract
Agent memory architectures define how LLM agents store and reuse experience across tasks, but they are typically fixed after deployment, limiting their adaptability across task types. Recent self-evolving approaches instead adapt these memory architectures using execution feedback, typically represented as evaluation scores or compressed summaries. However, such coarse-grained feedback is insufficient for precise failure localization in current agent systems, where long-horizon task execution involves multiple interacting components. Without a precise failure location, existing approaches lack a clear code-level target for modification, leaving the update scope weakly constrained and often leading to large-scale rewrites of an otherwise capable memory architecture. We propose MemScope, a framework for evidence-grounded, localized evolution of an existing memory architecture. Its tool-using Patch Agent jointly inspects raw execution traces, runtime memory state, and current architecture code to identify repair targets and apply bounded, in-place edits under provider-identity and memory-compatibility constraints. On GAIA, the trace-and-memory inspection variant achieves 86.67% accuracy, compared with 70.00% for trace-only and 63.33% for summary-only feedback. Under xBench tasks, the evolved memory architecture improves over its original version from 49 to 55 correct answers with DeepSeek V3.2 and from 50 to 53 with Kimi K2.7 Code. On disjoint ALFWorld unseen tasks, success rises from 50.75% to 71.64%. Across archived architecture-snapshot transitions, the median code-change ratio is 4.4%. These results support fine-grained execution evidence as a basis for localized, in-place memory-architecture evolution.

## 1. 核心问题与研究背景

- **背景**：LLM 智能体由语言模型 + agent harness（工具使用、上下文构建、执行控制、记忆）组成。其中“记忆架构”决定了存什么经验、如何检索、如何呈现给智能体。
- **痛点一**：主流记忆架构（MemoryBank、Mem0、DynamicCheatsheet、Agent Workflow Memory 等）在部署后基本固定，难以适应任务类型变化带来的不同记忆需求。
- **痛点二**：近期“自演化”工作虽用执行反馈改造记忆，但反馈形态过于**粗粒度**——通常只是评估分数或压缩摘要。
- **关键困难**：长时程任务中行为由“存储的经验、检索决策、下游动作”多组件交互决定。同一失败现象可能对应多种成因（经验根本没存、被检索过滤掉、被 early-return 代码路径绕过、或引导已正确给出而失败在别处），仅凭分数/摘要无法区分。
- **后果**：缺乏代码级修改目标 → 更新范围约束弱 → 往往对原本可用的架构做**大规模重写**。
- **论文主张**：应把“失败定位”变成记忆架构演化中的显式步骤，用**细粒度执行证据**支撑**有界、原地（in-place）**的代码修复，而非整架构重生成。

## 2. 方法论

### 2.1 演化对象（Evolution Target）
- 每个**记忆技能** `s_t` 遵循 Agent Skills 格式，由两部分组成：
  - `SKILL.md`：自然语言的设计指导（任务分析、记忆架构设计、存储与检索策略）；
  - `scripts/provider.py`：可执行 provider `p_t`，实现 `memory_retrieval` 与 `memory_storage`。
- **运行时记忆库 `M_t`** 与可复用技能文件**分离**：补丁只改代码，记忆库跨补丁保留。
- 演化只**局部修改 `p_t`**，并把设计教训写入 `SKILL.md`。

### 2.2 演化循环
- 一个 episode = 对任务窗口 `D_t` 的一次完整遍历。流程：
  1. **探针 + 路由**：先跑探针任务；Memory Skill Router 依据探针证据与技能描述选择已有技能并激活其 provider。
  2. **无合适技能时进入全局探索**：Skill Designer 从探针证据推导新技能规格 → 生成完整 provider → 注册并评估。
  3. **执行**：冻结的 Agent Executor `A` 用 `p_t` 与 `M_t` 逐任务执行：
     - `r_i = memory_retrieval(x_i, M_t)`
     - `(y_i, τ_i) = A(x_i, r_i)`
     - `m_i = memory_storage(τ_i)`
     - `M_t ← M_t ⊕ m_i`（⊕ 为 provider 特定的插入/更新）
  4. 保留原始轨迹 `τ_i` 作为诊断证据，并统计准确率、时间、成本。
- **修复触发器（Repair Gate）**：`g_t = I[a*_t − a_t > δ] · I[f_t ≥ f_min]`，即当前分段准确率 `a_t` 比历史最佳 `a*_t` 低超过 `δ=0.05` 且失败数 `f_t ≥ f_min=1` 时，才调用 Patch Agent。

### 2.3 Patch Agent：细粒度诊断 + 局部化修改
- **输入**：执行证据、当前记忆技能 `s_t`、补丁历史 `H_t`。
- **输出**：局部代码替换 `Δ_t`（精确 old→new 替换）+ **patch manifest**（根因、补丁摘要、预期效果、风险）。
- **三类只读证据工具**（表 1）：
  - *轨迹检查*：`list_traces`、`read_trace_header`、`read_trace_steps`、`grep_traces`；
  - *记忆检查*（`memory_store`）：`stats`（记录数/字段/schema/结果分布）、`list`、`read`、`query`（复放一次检索请求，返回原始匹配、选择决策与最终检索结果）；
  - *代码锚定*：`read_candidate_provider`、`read_skill_file`。
- **写入工具**：`edit_candidate_provider`、`run_candidate_checks`、`write_patch_manifest`。
- **约束（local-update contract）**：
  - 保持 **provider 身份**（provider_name、类名、`MemoryType`）不变，不得新建 provider / 新技能 / v2 命名；
  - **记忆兼容性**：不得引入使既有记忆记录失效的新 schema；
  - 允许范围：`provide_memory` 内的检索逻辑、排序/过滤、阈值、`top_k`、分数归一化、去重、兼容字段的存储/抽取、引导文本格式、防御性错误处理、小型辅助函数；
  - 禁止：大规模重写、无关重构、任务 ID/答案/基准名硬编码；
  - 契约保持：`initialize()` 返回 bool、`take_in_memory()` 返回 `tuple[bool, str]`。
- **本地校验**：早期 GAIA 版本检查语法、类身份、记忆类型、必需方法名；后续 xBench/ALFWorld 版本增加 import 检查与隔离检索检查。
- **补丁历史 `H_t`**：记录每次提案、是否安装、后续在复访任务上的结果（恢复的失败、回退的成功），供后续修复参考，避免重复无效方向。
- **可拒绝修改**：证据不足时输出 `patch_type="no_patch"`；若需架构级改动则 `needs_new_provider=true`，不改代码。

## 6. 主要结果

### 6.1 主结果
- **GAIA validation**：MemScope 在两个骨干上均取得领先。DeepSeek V3.2 下整体准确率显著高于 Flash-Searcher、MemEvolve、Agent KB、Cognitive Kernel-Pro 等；Kimi K2.7 Code 下同样保持优势，且 L3 难题提升幅度相对更大，说明细粒度修复对长时程、多步任务的收益更明显。
- **xBench DeepSearch-2505**：两个骨干上均优于 MemEvolve + Flash-Searcher 的匹配对照，且在时间/步数开销未显著膨胀的前提下取得提升。
- **ALFWorld valid_unseen**：优于 ALMA 及原始 DynamicCheatsheet，验证方法可迁移至具身顺序决策场景（记忆内容从“事实/网页线索”变为“子目标与动作经验”）。

### 6.2 匹配起点配对分析（xBench，70 题）
- 按四类迁移分解（C→C 一致正确、I→C 由错转对、C→I 由对转错、I→I 一致错误）：
  - **I→C（净增益）明显多于 C→I（净回退）**，说明演化总体为正收益；
  - C→I 的存在表明局部补丁可能引入过拟合或副作用，作者未回避该现象；
  - I→I 占比仍可观，指向“补丁未触及的失败类型”或 repair gate 未触发的情形。
- 该配对设计是全文最有说服力的证据：在**相同起点、相同执行器、相同任务**下隔离出“演化”这一变量。

- 阶梯大致为：No Memory < Original Provider < Summary-only < Trace+Memory ≈ MemScope（含 History）。

- 这直接支撑论文核心论点：反馈粒度是自演化记忆架构的性能瓶颈。

### 6.4 编辑局部性（表 8）
- 对 14 个归档 provider 快照做迁移测试，统计改动行数/函数数与契约保持情况：绝大多数补丁为**小规模、函数内**修改，provider 身份与 `MemoryType` 保持不变，未出现整体重写。
- 说明 local-update contract 在实践中**可被遵守**，而非仅停留在声明层面。

### 6.5 案例研究
- **GAIA 失败定位对比**：同一失败在 Summary-only 下无法定位，MemScope 通过 `query` 复放检索请求，区分“未存储 / 被过滤 / 被 early-return 绕过”三种成因，并给出对应最小补丁。
- **xBench `no_patch`**：证据显示引导已正确提供、失败源于下游执行，Patch Agent 拒绝修改，避免无效扰动。
- **DeepSeek vs Kimi 相反方向阈值修复**：同一检索阈值在两个骨干上一个需上调、一个需下调，说明补丁是**证据驱动、模型相关**的，而非通用启发式。
- **引导覆盖/条件准确率**：引导覆盖率 98.8%→99.4%，条件准确率 65.6%→84.1%，表明提升主要来自“引导被正确利用”而非“引导被更多生成”。

## 7. 贡献与创新点

1. **问题重构**：把“记忆架构演化”从“生成新架构”重构为“**失败定位 + 有界代码修复**”，明确指出粗粒度反馈是现有自演化方法的根本瓶颈。
2. **方法贡献**：提出 MemScope 框架，包含 (a) 探针路由 + 全局探索的技能选择机制；(b) 带 repair gate 的在线演化循环；(c) 具备轨迹/记忆/代码三类只读证据工具的 Patch Agent；(d) local-update contract 与本地校验构成的**有界修改约束**；(e) 补丁历史 `H_t` 作为跨 episode 的经验复用。
3. **证据贡献**：设计匹配起点、独立空记忆库的配对对照，并做逐层剥离式诊断消融，把“增益来自哪里”落到可检验的证据类型上。
4. **工程贡献**：验证了 Agent Skills 格式下“技能文件 + 可执行 provider + 运行时记忆库”分离的可行性，使补丁可复用、记忆可保留。

## 8. 局限与未来方向（含论文自述与评述）

- **自述局限**：诊断与修复依赖 LLM 的推理能力，Patch Agent 可能误判根因；局部补丁存在过拟合风险；架构级缺陷需 `needs_new_provider` 转人工/全局探索，当前未自动化闭环。
- **未覆盖的失败类型**：需要新工具、新外部知识源、多模态感知能力缺失等“非记忆架构”问题，MemScope 原则上无法修复，但论文未量化这类失败占比。
- **成本未量化**：Patch Agent 的多次证据读取（`grep_traces`、`query` 复放）在长轨迹上可能昂贵，缺少与“整架构重生成”的成本-收益对比。
- **可扩展性**：技能库规模增大后，Router 的选择准确率与 Patch Agent 的候选定位难度均会上升，论文仅以 12 个初始技能验证。
- **评测维度单一**：以任务准确率为主，缺少记忆库规模增长、检索延迟随 episode 演化的曲线，而这对“长期部署”至关重要。

## 9. 总体评价

- **优点**：问题抓得准（反馈粒度 → 修改范围失控），方法设计自洽（证据工具 ↔ 局部补丁 ↔ 契约约束三者互为支撑），实验在“匹配起点配对”和“逐层消融”两点上明显高于同类自演化工作的一般水准；`no_patch` 与“相反方向阈值修复”案例增强了可信度。
- **待改进**：消融样本量偏小、无重复与显著性检验、Patch Agent 质量指标缺失、超参数敏感性未探、成本未量化；跨论文基线排名需谨慎看待。
- **定位**：本文更像是为“自演化记忆架构”确立了**一条更可诊断、更可控的工程范式**，其方法论价值（细粒度证据 + 有界修改 + 契约校验）可能超过具体数字增益；对后续工作的直接启示是——在报告自演化系统时，应同时报告**补丁局部性、补丁正确率与失败类型分布**，而非仅报最终准确率。
