## 摘要
AI 智能体需要一种记忆机制，能够在用户与智能体的交互、用户之间的对话，以及有或无智能体参与的群组对话中保留信息，同时支持在证据发生变化或被移除时进行更新。我们提出 Stashbird，一种智能体记忆系统，它通过显式溯源将源片段与派生记忆状态关联起来。Stashbird 将记忆组织为情节记录、语义关系、社区摘要和持久化图状态，并提供用于增量更新和情节级删除的生命周期操作。我们在四个长期记忆基准上评估问答准确率和面向模型的工作负载。在 LoCoMo 上，Stashbird 使用的摄入提示 token 数比 Graphiti 少 76.4 倍。在同一基准上与复现的 Hindsight 相比，其检索提示 token 用量少 8.1 倍，准确率低 1.6 个百分点。在 LongMemEval-S 和 GroupMemBench 上，其准确率高于 Hindsight；在 EverMemBench 上准确率相当。

## Abstract
AI agents require memory that preserves information across user-agent exchanges, user-to-user conversations, and group conversations with or without agent participation, while supporting updates as evidence changes or is removed. We present Stashbird, an agent memory system that links source episodes to derived memory state through explicit provenance. Stashbird organizes memory into episodic records, semantic relations, community summaries, and persisted graph state, with lifecycle operations for incremental updates and episode-level deletion. We evaluate question-answering accuracy and model-facing workload across four long-term memory benchmarks. On LoCoMo, Stashbird uses 76.4x fewer ingestion prompt tokens than Graphiti. Compared with reproduced Hindsight on the same benchmark, it uses 8.1x fewer retrieval prompt tokens, with accuracy 1.6 percentage points lower. It achieves higher accuracy than Hindsight on LongMemEval-S and GroupMemBench and comparable accuracy on EverMemBench.

## 1. 核心问题与研究动机

- **背景**：AI 智能体越来越多地依赖长期交互历史工作，仅靠全上下文提示（full-context prompting）已难以可靠处理不断增长的历史，尤其在多方共享对话场景中。
- **需求**：记忆系统需同时具备四项能力——回溯早期上下文、跨交互保留事实/偏好/计划/决策、追踪信息来源（provenance）、在证据被修正或删除时更新记忆。
- **现有方案的问题**：主流做法包括向量库 + RAG、实体关系图与摘要、稠密检索与结构化/层次化记忆结合等；它们需在**答案质量**与**构建/查询记忆所需的模型调用和 token 开销**之间权衡。
- **核心缺口**：现有系统虽支持更新与记忆管理，但**源片段（episode）与派生记忆状态之间的显式溯源链接**，以及片段增删后派生状态的**一致性协调（reconciliation）**，仍缺乏系统化处理。
- **论文定位**：提出 Stashbird——以情节为 grounding、带显式溯源、支持增量更新与情节级删除的智能体记忆系统，覆盖用户—智能体、用户—用户、有/无智能体参与的群组对话。

## 2. 方法论

### 2.1 核心思想

- 将记忆维护为**持久化、情节 grounded 的状态**：原始对话证据与派生语义状态（实体、关系、偏好、社区摘要、图状态）通过溯源双向链接。
- 与仅存检索片段、抽取记忆项或图摘要的系统不同，Stashbird 保留原始对话证据，使记忆可被延续、修订、删除和查询。
- 记忆以多种**结构化视图**暴露于同一对话状态之上（表 1）：
  - Episodes：对话块，追加/删除，用于证据召回；
  - Entities：规范化实体，合并/失效，用于 grounding；
  - Relations：实体关系，替换/版本化，用于推理；
  - Preferences：用户特质，覆盖写，用于个性化；
  - Communities：实体簇，重新摘要，用于高层上下文。

### 2.2 摄入与更新（Ingestion & Update）

- 以**有序、带时间戳的情节序列**摄入对话，每条情节记录发言者、内容、消息时间与摄入时间；相邻情节构成对话线程，并链接到被引用实体且保留溯源。
- **分块与摘要**：为避免重复全历史 LLM 调用，先用 15K token 窗口构建全局摘要；再以 20K token 块、10% 重叠处理情节。
- **抽取流程**：先用 NER 模型减少漏提及，再由骨干 LLM 结合块文本、全局摘要和**滚动实体中心上下文**抽取实体与关系；该上下文上限 4K token，超限时压缩，仍超限则剪除支持度最低的实体。
- **实体调和**：余弦相似度与 Levenshtein 比率**均 > 0.85** 时接受匹配；任一指标 > 0.75 的候选交由骨干模型裁决；阈值跨基准固定。
- **关系调和**：在每对实体内部进行，重复关系扩展溯源，矛盾关系替换旧关系。
- **社区摘要**：启用时用标签传播（label propagation）聚类实体图，每簇摘要为社区节点并链接成员。
- **增量更新**：持久化 checkpoint 保存对话摘要、序列化滚动上下文、最后处理情节、当前实体数；更新时加载 checkpoint、恢复上下文、追加新情节、更新摘要，并复用已有实体与关系；新实体归入既有社区。

### 2.3 删除（Algorithm 1：Episode-Anchored Memory Deletion）

- 删除粒度为**情节级**；请求指定情节 ID，通过溯源确定受影响的实体、关系与社区。
- 设 \(P(x)\) 为支持实体/关系 \(x\) 的情节集合，删除情节 \(d\)：
  - 对每个受影响关系：\(P(r) \leftarrow P(r)\setminus\{d\}\)；仍有支持则仅更新溯源，无支持则从图和搜索索引中移除。
  - 对每个受影响实体：同样更新 \(P(e)\)；**无支持且无幸存邻居**的实体删除；**无支持但有幸存邻居**的实体清空情节派生元数据，保留为“连接锚点”（connective anchor），并移除其过期搜索文档。
  - 删除情节本身及其索引文档；若前后邻居均存在，则**重连前驱与后继**。
  - 受影响社区标记为 dirty，移除其过期检索文档，延迟重新摘要。

### 2.4 检索（Retrieval）

- 保留原始查询，并由骨干模型生成**至多 4 个聚焦子查询**；有时间信息时相对问题日期解析时间表达。
- 对每个查询变体做嵌入，执行**对话范围内的混合检索**（情节、实体、关系文档，启用时含社区文档），跨查询合并去重。
- 用**倒数排名融合（RRF，k=60）**融合多源证据；再由 LLM 相关性打分器评估每个候选对回答的有用性；取 top 候选组成最终证据集（默认 30 条）。
- 生成器仅依据检索证据与问题日期作答。

## 6. 主要结论与发现

- **LongMemEval-S**：Stashbird 75.6%（GPT-4o-mini）略高于 Hindsight 74.8%；81.0%（GPT-4.1-mini）高出 2.7 个百分点；单会话偏好题优势最大（74.6%/88.4% vs 53.7%/55.3%）；运行间方差小于 Hindsight。
- **LoCoMo**：80.4%（GPT-4o-mini）、87.5%（GPT-4.1-mini），优于 Zep、Nemori、Mem0、Graphiti，但低于 Hindsight（85.9%/89.1%）；该差距伴随显著更低的 token 成本。
- **EverMemBench**：55.4% 平均准确率，与 Hindsight 54.8% 相当；强于单跳召回、约束意识、画像理解，弱于多跳召回、时间召回、主动性与知识更新。
- **GroupMemBench**：51.1% vs Hindsight 24.9%（+26.2 点）；时间推理 72.3% vs 2.2%，用户隐式问题 60.8% vs 22.8%，与系统保留发言者和时间信息一致。
- **效率**：
  - LoCoMo 摄入 prompt token 484K，比 Graphiti（37M）少约 **76.4×**，比 Hindsight（6.58M）少约 13.6×；
  - LoCoMo 检索 prompt token 8.24M，比 Hindsight（66.4M）少约 **8.1×**；
  - LongMemEval-S 摄入 164M vs Hindsight 700M、Graphiti 3.57B；EverMemBench 摄入 21.4M vs 169M，检索 52.5M vs 282M。
  - 代价是**检索阶段 LLM 调用次数更多**（以调用换 token）。
- **骨干敏感性**：LoCoMo 上随骨干增强单调提升（87.5% → 89.9% → 92.0%），开放域与时间题增益最大；EverMemBench 提升有限且非单调（55.4% → 56.4% → 55.9%），说明其更受**检索瓶颈**而非骨干能力限制。
- **Top-K 稳定性**：K 在 10–50 间性能基本平稳（EverMemBench 55.2–55.5%，LoCoMo 87.0–87.5%），K=30 最佳，说明融合重排后有效证据通常已在头部。
- **总体判断**：Stashbird 实现了较好的**质量—成本权衡**，以显式溯源和结构化多视图换取可更新、可删除

可删除的记忆状态，并在多方群组场景中以显著更低的摄入成本取得大幅领先；其相对短板在于检索阶段以更多 LLM 调用换取 token 节省，且性能对检索与重排环节的依赖强于对生成骨干的依赖。

## 7. 局限性与风险

### 7.1 评测覆盖的局限

- **能力—评测错位**：论文的核心卖点是显式溯源与情节级删除后的一致性协调，但这两项能力**未进入任何基准的定量评测**。删除算法（Algorithm 1）仅以伪代码与案例说明呈现，缺少“删除后记忆正确率”“误删率”“锚点实体残留影响”等可测指标，因而无法验证其在真实噪声对话中的鲁棒性。
- **组件默认关闭**：社区摘要、图扩展、可信度加权、反思机制、专用偏好检索在实验中被关闭，意味着论文实际评测的是系统的**简化配置**，与架构图中呈现的完整能力存在差距；这也解释了 EverMemBench 上提升有限、非单调的现象可能部分源于检索链路被削弱。
- **消融粒度不足**：仅做了骨干模型与最终证据数（Top-K）两类敏感性分析，未对分块大小与重叠率、滚动上下文上限（4K）、实体调和双阈值（0.85/0.75）、RRF 的 k 值、相关性打分器是否启用等关键超参做扫描，无法判断性能对这些设计的敏感程度，也难以支撑“阈值跨基准固定即可泛化”的主张。

### 7.2 方法与工程风险

- **阈值与规则的脆弱性**：实体调和依赖余弦相似度与编辑距离的固定组合阈值，对多语言、缩写、同名异指（如人名与产品名冲突）场景可能失效；论文未报告调和错误率或人工抽检结果。
- **“连接锚点”策略的副作用**：删除后保留无支持但有邻居的实体，可维持图连通性，但会留下**无证据支撑的节点**，在后续检索中可能作为噪声被召回，甚至诱导生成器产生无依据的推理；论文未讨论该风险及缓解手段。
- **删除的级联范围有限**：算法以情节为单位传播影响，但若某条派生事实被**多条情节共同支持**，删除单条情节只更新溯源而不改变语义状态，这在“用户明确要求遗忘”类场景下可能不满足合规预期（如隐私删除请求）。
- **增量更新的状态一致性**：checkpoint 保存对话摘要、滚动上下文与最后处理情节，若摄入过程中断或情节乱序到达，恢复逻辑的正确性未被讨论；亦未说明并发写入或多源摄入时的冲突处理。
- **成本结构转移而非消除**：检索阶段每个查询生成至多 4 个子查询、对每个变体做嵌入、再经 LLM 相关性打分，使**每次查询的调用次数显著上升**。在低延迟、高频查询的在线智能体场景中，调用次数而非 token 量往往才是瓶颈，这一代价在论文的指标框架下被相对淡化。

### 7.3 可比性风险

- 部分基线（Zep、Nemori、MemOS、MemoBase）取自文献而非同 harness 复现，问题集、答案骨干与 judge 配置不完全一致，跨表数值只能作趋势参考。
- 各基准使用自带 LLM-as-a-judge，不同 judge 对“部分正确”“时间近似正确”的容忍度不同，尤其在时间推理与开放域题上可能放大或压缩系统间差距。
- GroupMemBench 上 Hindsight 仅 24.9% 的异常低分，提示该基线可能在该数据分布上存在适配问题（如角色/时间格式处理），+26.2 点的领先幅度需谨慎解读为“架构优势”，其中可能混入了工程适配差异。

## 8. 对实践的启示

- **“证据留存 + 派生状态”双层记忆是可维护性的前提**：只存摘要或只存向量的系统在事实被修正时无法回溯到原始依据。Stashbird 表明，把 episode 作为一等公民、让所有派生状态反向链接到证据，是支持修订与删除的低成本路径。
- **多视图而非单一索引**：实体、关系、偏好、社区在同一对话状态上以不同粒度暴露，使检索可按问题类型（事实召回 / 多跳 / 时间 / 画像）走不同路径，比单一向量库更适配异质查询。
- **成本优化的重心应从“少读”转向“少写”**：Stashbird 的主要节省来自摄入阶段的摘要复用与滚动上下文（避免对全历史反复调用 LLM），而非检索阶段。对长期运行的智能体，摄入成本是随历史线性累积的一次性支出，通常是更值得优化的目标。
- **多方对话需要显式的发言者与时间建模**：GroupMemBench 上时间推理与用户隐式问题的巨大差距说明，保留结构化元数据（谁、何时、对谁）比增强生成模型更能解决群组场景的核心难点。
- **可删除性是合规刚需**：隐私法规与用户预期都要求“可遗忘”，情节级删除 + 溯源传播提供了一个可实现的工程范式，但需配套审计日志与多情节共同支持事实的处理策略。

## 9. 总体评价

- **贡献定位**：论文的主要贡献不在单点算法创新，而在**系统层面的整合与工程取舍**——把情节 grounding、显式溯源、增量更新、情节级删除与混合检索统一在一个可运行系统中，并给出跨三类对话场景的统一评测。
- **证据强度**：准确率证据较扎实（4 基准、统一 harness、5 次重复、置信区间、效率并列报告），在多方群组场景上的领先幅度具有说服力；但**系统主张与评测范围不匹配**——最独特的删除与溯源能力缺乏定量验证，削弱了“可维护记忆”这一核心论点的实证支撑。
- **实用性**：以 token 为主要成本口径，Stashbird 在摄入侧的优势（LoCoMo 上较 Graphiti 低约 76×）具有明确的部署价值；检索侧调用次数的上升需通过批处理、缓存子查询或弱化相关性打分器来平衡。
- **可复现性**：骨干、嵌入模型、硬件、重复次数与 judge 配置披露较完整，但代码与数据划分未提及，超参扫描缺失，第三方复现仍存在门槛。
- **后续研究方向**：①为删除与更新设计专门基准（如“删除后问答一致性”“遗忘合规性”）；②补齐被关闭组件的消融，量化社区摘要与图扩展的边际收益；③研究多情节共同支持事实的删除语义；④在延迟/调用次数约束下重新审视检索管线，探索子查询生成与打分的轻量化替代。
