ABSTRACT 

In long-term memory systems, memories are constructed from interaction his-tories and retrieved in response to queries, enhancing the reasoning ability of LLM agents. In complex scenarios, facts are scattered across sessions and their relationships evolve over time, making it difficult for existing memory systems to compose them to adapt to diverse queries. Motivated by the modularity and composability of code, we propose Memory as Code (MaC), a unified mem-ory framework that jointly designs memory construction and retrieval through a shared code abstraction. MaC couples codified construction , which establishes ex-ecutable memory abstractions, with declarative retrieval , which translates queries into structured retrieval programs. Specifically, codified construction builds a three-layer executable memory structure that progresses from an atomic function layer, through a relational layer, to a modular composition layer. Declarative re-trieval recasts retrieval from relevance-based fact selection into declarative query processing over memory. Experiments on L OCOMO and L ONG MEM EVAL show relative gains of up to 15.91% in overall LLM-judge accuracy over the strongest baseline in each setting, while substantially reducing token consumption, high-lighting the effectiveness of memory as code for long-horizon memory tasks. 

1 INTRODUCTION 

Long-term memory enables Large Language Model (LLM) agents to retain and use information across interactions, supporting personalized assistance and long-horizon tasks (Zhong et al., 2024; Park et al., 2023). A memory system Xu et al. (2026a); Packer et al. (2023) comprises memory construction, which organizes interaction histories into memory data, and memory retrieval, which processes memory queries over memory data. For memory construction, MemoryOS (Kang et al., 2025) organizes dialogue into topic segments and summaries, Mem0 (Chhikara et al., 2025) consol-idates facts through update operations, and A-Mem (Xu et al., 2026b) constructs dynamically linked memory notes. These methods support memory organization and maintenance, but provide lim-ited support for encapsulating computations over stored facts for reuse across queries. For memory retrieval, existing approaches combine search with contextual or relational expansion to gather rele-vant evidence (Borgeaud et al., 2022; Liu et al., 2023), using either predefined pipelines (Han et al., 2024; Rasmussen et al., 2025) or agentic workflows (Yao et al., 2022; Li et al., 2025; Ji et al., 2026). However, predefined pipelines offer limited flexibility for diverse queries, whereas stepwise agen-tic methods achieve this flexibility through repeated LLM planning, incurring additional inference overhead(Kim et al., 2023; Tan et al., 2025). The above observations motivate a joint design in which memory construction encapsulates reusable computations over stored facts, and retrieval composes them for each query while reducing the need for repeated planning. Code provides a suitable foundation: shared references preserve consistent fact identities, functions expose reusable computations through explicit interfaces, and programs specify their composition and conditional branches before execution begins. However, achieving these goals through a shared code abstraction poses two challenges: (1) How can interaction histories be transformed into executable memory code? Facts expressed across ses-sions may overlap, supplement one another, or supersede earlier states, distinctions that are not automatically resolved by encoding facts as functions. Preserving consistent fact identities and dis-tinguishing current from historical states is a key challenge. (2) How can retrieval compose memory code to accommodate diverse queries? Relevant functions alone do not specify how their outputs should be combined, and subsequent operations may depend on intermediate results. Capturing these dependencies and conditional continuations in a complete retrieval program while reducing repeated LLM planning is another key challenge. To address these challenges, we propose Memory as Code (MaC), a framework that represents long-term memory as executable code and retrieves information through query-specific programs. The framework comprises two components: (1) codified construction transforms facts extracted from in-teraction histories into a three-level executable memory structure. The atomic function layer encodes facts as functions with canonical identifiers and source references; the relational layer connects fact functions through explicit supersession relations while retaining historical evidence; and the modu-lar composition layer composes base functions into reusable current-state and history computations. A compact memory index exposes function capabilities, arguments, and available operators for re-trieval. (2) Declarative retrieval interprets each query as a high-level specification and compiles it into a complete retrieval program in one LLM planning call. Using the memory index, the program selects and composes the required memory computations, specifying operator arguments, dependen-cies, and conditional continuations. An executor checks and runs the program, following predefined branches based on intermediate results and assembling supporting evidence without stepwise LLM planning during successful execution. The two components work together through the memory in-dex and a common evidence representation. The index connects constructed capabilities to query requirements, while the evidence representation supports result composition and source tracing. As illustrated in Figure 1, this design connects facts distributed across sessions through reusable func-tions to answer the query. Our main contributions are as follows: • We study long-term memory for LLM agents to support reasoning over evolving informa-tion across interactions. We propose Memory as Code (MaC), a framework that uses a shared code abstraction to connect memory capabilities with query-specific composition. • We develop two complementary techniques: codified construction organizes facts, their evolving relations, and reusable computations in a three-level executable memory structure with consistent state semantics and source provenance; declarative retrieval compiles each query into a complete retrieval program that selects and composes these capabilities in one LLM planning call. 2• Extensive experiments on widely used memory benchmarks show that MaC achieves the highest overall LLM-judge accuracy in all four evaluation settings, improving over the strongest baseline by up to 15.91% on L OCOMO and 9.06% on L ONG MEM EVAL . 2 MEMORY AS CODE 

In this section, we present MaC for long-term agent memory. We first introduce the problem def-inition and solution framework (§2.1), then describe codified construction (§2.2) and declarative retrieval (§2.3), and finally analyze the time and space complexity (§2.4). 2.1 PROBLEM DEFINITION AND SOLUTION FRAMEWORK 

Problem Definition. Given a dialogue history H = ( s1, . . . , s nsess ) of nsess sessions, memory construction organizes its information into an external memory M. For a query q, memory retrieval accesses and combines information in M to produce supporting evidence Eq , which is used to generate an answer aq . Appendix A.1 summarizes the notation used throughout the paper. 

Solution Framework Overview. MaC organizes memory construction and retrieval around a shared code abstraction: memory provides reusable functions, and retrieval composes these functions into query-specific computations. As illustrated in Figure 2, the framework comprises two stages. Cod-ified construction transforms dialogue history H into a code library of fact functions and reusable computations over current and historical states. A memory index exposes the callable interfaces and the available memory operators. Declarative retrieval uses these interfaces to translate a query q

into a complete retrieval program in one LLM planning call. After checking, the program executes over the library to assemble supporting evidence Eq for answer generation. The two stages are con-nected by indexed interfaces and a common evidence representation, allowing retrieval to discover and compose the capabilities established during construction. 32.2 CODIFIED CONSTRUCTION : F ACT -TO -F UNCTION 

Given dialogue history H, memory construction begins by extracting atomic facts to distill salient information and filter out irrelevant conversational details. We then encode these facts as executable memory to support reusable computation. However, directly encoding these facts into code is chal-lenging because they are expressed in natural language, and the relations among them are complex and evolve over time. To address these challenges, we design codified construction to organize facts into callable functions, explicitly represent their relations, and compose them into reusable operators. We first introduce the codified memory representation (§2.2.1), then describe memory organization and indexing (§2.2.2). 2.2.1 CODIFIED MEMORY REPRESENTATION 

We define codified memory M that includes a code library L and a memory index I. The code library comprises four sets: base fact functions F, memory views V, fact relations R, and derived functions D:

M = ( L, I ), L = ( F, V, R, D).

The library organizes memory into three layers. The atomic function layer represents individual facts as callable functions in F. The relational layer specifies fact connections and state replace-ments through R. The modular composition layer provides derived functions in D for reusable computations over facts and their relations, including current-state resolution and history retrieval. Base and derived functions return evidence with fact identifiers and source references, supporting composition and provenance. The set of memory views V contains concept views , which group function references by person or topic, and session views , which group them by dialogue session. The memory index I specifies view membership, callable function interfaces, and available memory operators, enabling retrieval to select and compose memory computations. 2.2.2 MEMORY ORGANIZATION AND INDEXING 

We construct the three layers of the code library L from extracted facts, then build the memory index 

I to expose the resulting functions and memory operators for retrieval. 

Code Library Organization. To translate natural-language facts into executable memory, we use an LLM to produce structured function specifications. A structured prompt specifies the required fact fields and function interface, and a local generator converts each specification into an executable base fact function. At the atomic function layer , we canonicalize and deduplicate facts and assign each a canonical identifier i. For each canonical fact, the LLM produces a specification containing its structured value vi, including the subject, predicate, and available time information, together with a statefulness annotation. The local generator uses this specification and the supporting dialogue references Si to create a base fact function fi ∈ F that returns an evidence record ei = ( vi, {i}, S i). Concept views and session views import shared references to these functions. At the relational layer , we group stateful facts by subject and predicate and ask the LLM to identify explicit replacements. Each replacement becomes a supersession relation (j, supersedes , i ) ∈R, indicating that fact j replaces fact i while both functions remain available. We also connect facts by temporal order, shared subject, and shared topic. At the modular composition layer , we instantiate derived functions in D from reusable current-state and history templates over linked facts and register them in the relevant views. The resulting functions invoke base fact functions in F and use their relations in R to compute results. For a state group G sharing a subject and predicate, let G(τ ) contain the identifiers of facts whose recorded times do not exceed the time boundary τ . Memory Index Construction. The code library provides executable memory, but downstream retrieval also needs to discover its contents and determine how to use them. We therefore construct the memory index I with two parts: indices over library contents and interfaces to memory operators. For the library contents, we build indices at two levels. The function index Ifunc maps each base or derived function identifier to its entry point, description, and accepted arguments, extracted from function metadata. The view index Iview maps each concept or session view in V to the identifiers of the functions it references. Together, these indices support navigation from views to callable functions without inspecting their implementations. We define four categories of memory operators for downstream computation. The operator index 

Iops records their interfaces. Memory access retrieves facts and invokes functions; context expan-sion follows views and relations to gather additional facts and source context; evidence composition 

combines, filters, ranks, and aggregates evidence; and verification provides heuristic checks of ev-idence completeness and unresolved states. The content indices and operator interfaces together form I = ( Iview , I func , I ops ), exposing both available memory resources and the operations for using them. Table 6 in Appendix A.2 provides detailed operator descriptions. 2.3 DECLARATIVE RETRIEVAL : Q UERY -TO -P ROGRAM 

To adapt retrieval to diverse queries, declarative retrieval interprets each query as a high-level spec-ification and compiles it into a structured retrieval program that selects and composes the required memory computations. We first describe declarative query planning (§2.3.1), then present retrieval program execution (§2.3.2). 

Retrieval Program. Given a query q and codified memory M = ( L, I ), we define a retrieval program Pq as an executable query plan over the memory operators exposed by I. The program specifies operator arguments and dependencies, together with any conditional continuations. These operators encapsulate memory access and computation, allowing the program to compose existing memory functions and process their results through predefined operations. Executing Pq over M

produces the supporting evidence Eq specified in the problem definition. 2.3.1 DECLARATIVE QUERY PLANNING 

Diverse queries require retrieval plans tailored to their information needs. A question about a current attribute may need a single function call. Questions combining facts across sessions may require context expansion and evidence composition. We use an LLM planner to interpret each query and reason about the required memory operations. Initial retrieval selects a set of candidate function identifiers Kq using the memory index I built during construction. Their entries in Ifunc and the operator interfaces in Iops form the planning context Iq (M). Function entries describe what each callable computes and which arguments it accepts. Operator interfaces specify the available operations and their input and output constraints. This compact context supports planning without loading the full code library .Our structured prompt presents the query, function information, operator constraints, and planning guidance (Appendix B). The guidance illustrates how query requirements translate into operations, such as temporal filtering or expansion across sessions. The prompt also specifies evidence compati-bility constraints and requires the program to return supporting evidence. in one planning call. In restricted Python, it specifies operator calls, arguments, dependencies, and conditional retrieval actions based on intermediate evidence. 2.3.2 RETRIEVAL PROGRAM EXECUTION 

Before execution, MaC checks the retrieval program’s structural compatibility with the available memory operations, including permitted language constructs, operator calls, variable references, and evidence dependencies. These dependencies connect function invocation, any selected view expan-sion, and subsequent evidence processing, preserving the information required by each operation. The query determines which computations and conditional continuations the program combines. Once accepted, Pq executes over the code library L, with function calls resolved through the memory index I. Calls to base and derived functions reuse the fact definitions and state computations estab-lished during construction, while evidence composition preserves their fact identities and sources. Intermediate results determine which conditional continuations already specified in Pq are followed. Execution can therefore perform additional memory access when indicated by these conditions with-out a new LLM planning decision. This planning–execution separation combines operator compo-sition tailored to each query with reusable memory computation. The final evidence assembly combines selected facts, supporting dialogue, and computation prove-nance into Eq , loading source context as specified by the program; execution also produces a trace 

Tq . A separate answer model generates the response as aq = Fanswer (q, E q ). A valid first attempt uses one planning call and a separate answer-generation call; checking or execution failures may trigger bounded repair attempts, followed by a fixed retrieval fallback if needed. 3 EXPERIMENTS 

3.1 EXPERIMENTAL SETUPS 

In this section, we describe the experimental setup and present comprehensive results to systemati-cally evaluate MaC and address the following research questions (RQs): • RQ1 (Overall performance) How does MaC perform against representative long-term memory systems across benchmarks, question types, and LLM backbones? • RQ2 (Cost, runtime, and storage) What are the token consumption, wall-clock runtime, and storage footprint of MaC during memory construction and retrieval? • RQ3 (Ablation study) How do executable memory and programmatic search individually and jointly contribute to MaC’s performance? 

Datasets. We evaluate MaC on two benchmarks for long-term conversational memory: LO-COMO (Maharana et al., 2024), which evaluates question answering over long conversations, and LONG MEM EVAL (Wu et al., 2024), which evaluates memory across multiple sessions with longer interaction histories per query. 

Baselines. We compare MaC with representative baselines: A-Mem (Xu et al., 2026b), Memo-ryOS (Kang et al., 2025), Mem0 (Chhikara et al., 2025), and MRAgent Ji et al. (2026). 

Implementation Details. We conduct our experiments on NVIDIA A100 GPUs. On L OCOMO,we evaluate all methods using three LLM backbones: Qwen3.6-27B, ChatGPT-5.6-Luna, and DeepSeek-V4-Flash. On L ONG MEM EVAL , we use Qwen3.6-27B as the backbone for all methods. Following prior work, we report F1 and LLM-Judge (J) scores. LLM-Judge (J) scores are obtained using DeepSeek-V4-Flash. 4 RELATED WORK 

Memory Construction. Memory construction concerns retaining useful information from growing interaction histories and revising it as new interactions arrive. A related foundation is retrieval-augmented generation (RAG) (Lewis et al., 2020), which indexes external passages as dense vec-tors for generation; GraphRAG (Han et al., 2024) augments this setting with graph structure, community summaries, and neighborhood-based access. For persistent conversational memory, Mem0 (Chhikara et al., 2025) extracts salient facts and reconciles them with existing memory, whereas MemoryOS (Kang et al., 2025) organizes information across short-, mid-, and long-term stores. Other methods emphasize relational and temporal structure: A-Mem (Xu et al., 2026b) dy-namically links and updates structured notes, and Zep (Rasmussen et al., 2025) records fact validity and historical changes in a bi-temporal graph. More recently, MemSkill (Zhang et al., 2026) learns to select and evolve memory-construction skills. Collectively, these methods improve information selection, consolidation, and structural organization through different memory representations and construction strategies. 

Memory Retrieval. Memory retrieval addresses both locating relevant records and deciding how further evidence should be accessed and composed. SeCom (Pan et al., 2025) improves retrieved context through topic-based segmentation and compression-based denoising. Structured retrieval extends access beyond flat text matching: Zep (Rasmussen et al., 2025) combines semantic and full-text search with graph traversal and reranking. In external-knowledge search, Search-o1 (Li et al., 2025) integrates on-demand search into document-based reasoning, and Search-R1 (Jin et al., 2025) uses reinforcement learning to learn multi-turn search behavior. At the execution-interface level, Text2Mem (Wang et al., 2026) translates memory instructions into typed, validated operations and supports workflows with dependencies across backends. MRAgent (Ji et al., 2026) uses intermedi-ate evidence to guide exploration and pruning over a Cue–Tag–Content graph. These approaches improve context quality, structured access, or adaptive exploration; nevertheless, candidate-based retrieval remains bounded by the records selected for access, while iterative reasoning can require repeated context processing and model calls. Thus, retrieving sufficient evidence under a limited budget remains a central challenge. 95 CONCLUSION 

We presented MaC, a unified framework that jointly designs memory construction and retrieval. We develop two complementary techniques: codified construction organizes facts, their evolving relations, and reusable computations into a three-layer executable memory structure. declarative retrieval compiles queries into complete programs that select and compose these computations, enabling query-specific conditional execution without stepwise LLM planning. Experiments on LOCOMO and L ONG MEM EVAL show that MaC achieves the highest overall F1 and LLM-judge scores across the evaluated settings while substantially reducing token consumption.

12 A.3 COMPLEXITY ANALYSIS 

This subsection expands Section 2.4. To characterize the cost of reusable memory computation, we distinguish one-time construction from per-query retrieval and account for model inference sepa-rately. Let n be the number of extracted facts before deduplication, so |F| ≤ n, and let h be the total length of the source dialogue H in tokens. For a query q, let p be the number of syntax-tree nodes in 

Pq and b the maximum fully expanded size of an evidence collection materialized during retrieval, counting scalar entries and text tokens in its values and provenance. We assume bounded fact text, structured values, and query length, bounded annotations per extracted fact, and fixed retrieval and repair limits. 

Time Complexity. Construction compares facts for deduplication and scans and sorts candidate neighbors for each canonical fact. The latter costs O(n2 log n) in the worst case, even though only a bounded number of neighbors is retained per structural relation. Including source preprocessing and model inference, the construction bound is Tbuild = O(h log h+n2 log n+Cbuild ). During retrieval, candidate matching scans and sorts the memory index, while view expansion and provenance com-position can incur quadratic work through list-based deduplication. Structural program checking takes O(p) time, and the loop-free language permits at most O(p) operator calls. Accounting for memory access, source loading, evidence composition, and trace generation gives the conservative bound Tq = O Cq + p(n2 + h + b2) + p2. Here Cbuild and Cq sum the model inference costs in the corresponding stage, including extraction, semantic compilation, retrieval preprocessing, plan-ning, and answer generation as applicable. This accounting includes both operator execution and the model calls used across the query pipeline. 

Space Complexity. Let r count stored references across memory views, fact relations, derived functions, and source annotations. The code library, memory index, construction records, and source dialogue require O(n + r + h) space. A query additionally retains intermediate evidence and its exe-cution trace Tq , giving O(n + r + h + pb ) space, excluding model weights and inference workspace. Under the stated annotation bounds and the implemented relation limits, r = O(n), so memory storage is linear in the input size. The pb term accounts for the generated program’s intermediate results, including matching pairs materialized by joins and their provenance.
