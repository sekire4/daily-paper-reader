## 摘要
在长期记忆系统中，记忆由交互历史构建，并针对查询进行检索，从而增强LLM智能体的推理能力。在复杂场景中，事实分散于多个会话之中，且其关系随时间演化，这使得现有记忆系统难以组合这些事实以适应多样化查询。受代码的模块性与可组合性启发，我们提出Memory as Code（MaC），一种统一的记忆框架，通过共享的代码抽象联合设计记忆构建与检索。MaC将代码化构建与声明式检索相结合：前者建立可执行的记忆抽象，后者将查询转化为结构化检索程序。具体而言，代码化构建构建一个三层可执行记忆结构，从原子函数层，经关系层，推进到模块化组合层。声明式检索将检索从基于相关性的“事实选择”重塑为对记忆的声明式查询处理。在LoCoMo和LongMemEval上的实验表明，与各设置下最强基线相比，整体LLM评判准确率相对提升最高达15.91%，同时大幅降低token消耗，凸显了“记忆即代码”在长时程记忆任务中的有效性。

## Abstract
In long-term memory systems, memories are constructed from interaction histories and retrieved in response to queries, enhancing the reasoning ability of LLM agents. In complex scenarios, facts are scattered across sessions and their relationships evolve over time, making it difficult for existing memory systems to compose them to adapt to diverse queries. Motivated by the modularity and composability of code, we propose Memory as Code (MaC), a unified memory framework that jointly designs memory construction and retrieval through a shared code abstraction. MaC couples codified construction, which establishes executable memory abstractions, with declarative retrieval, which translates queries into structured retrieval programs. Specifically, codified construction builds a three-layer executable memory structure that progresses from an atomic function layer, through a relational layer, to a modular composition layer. Declarative retrieval recasts retrieval from relevance-based fact selection into declarative query processing over memory. Experiments on LoCoMo and LongMemEval show relative gains of up to 15.91% in overall LLM-judge accuracy over the strongest baseline in each setting, while substantially reducing token consumption, highlighting the effectiveness of memory as code for long-horizon memory tasks.

## 1. 核心问题与研究动机

- **背景**：长期记忆系统让 LLM 智能体跨交互保留信息，是个人助理与长时程任务的基础。一个记忆系统包含两阶段：**记忆构建**（把交互历史组织为记忆数据）与**记忆检索**（针对查询访问并组合记忆）。
- **现有构建方法的不足**：MemoryOS 按主题分段并摘要、Mem0 通过更新操作整合事实、A-Mem 构建动态链接笔记、Zep 用双时序图记录事实有效性。这些方法擅长信息的**选择、整合与结构化组织**，但**难以把“对已存事实的计算”封装成可跨查询复用的单元**。
- **现有检索方法的不足**：
  - 预定义流水线（如 GraphRAG、Zep 式检索）灵活度低，难以适配多样查询；
  - 逐步智能体式检索（ReAct 类、MRAgent 式探索）虽灵活，但需**反复 LLM 规划**，推理开销大，且可能提前终止、遗漏证据。
- **核心痛点**：复杂场景中事实**跨会话分散**、关系**随时间演化**（补充、重叠、被取代），现有系统难以把它们组合起来适配不同查询。论文图 1 的示例即展示了关键词不匹配导致漏检、逐步规划在关键事件前停止等问题。
- **核心洞察**：代码天然具备三项性质——共享引用保持事实身份一致、函数以显式接口暴露可复用计算、程序可在执行前完整指定组合与条件分支。由此提出 **“记忆即代码”**：记忆是**可调用计算的库**，检索是针对该库的**查询专属程序**。

## 2. 方法论

### 2.1 总体框架

- 统一抽象：`M = (L, I)`，其中 `L = (F, V, R, D)` 为代码库（基础事实函数、视图、事实关系、派生函数），`I` 为记忆索引。
- 两个阶段通过**记忆索引**与**统一证据表示**衔接：索引把构建出的能力对接查询需求，证据表示支持结果组合与来源追溯。

### 2.2 代码化构建（Codified Construction：事实→函数）

三层可执行结构：

- **原子函数层 `F`**：
  - 先用 LLM 从各会话抽取带来源标注的事实，做规范化与语义去重，分配**规范标识符** `i`；
  - LLM 生成结构化函数规格（结构化值 `v_i`（主语/谓语/时间）、**状态性标注**、函数接口），由**本地生成器**转换为可执行基础函数 `f_i`，返回证据记录 `e_i = (v_i, {i}, S_i)`，保留源对话引用。
- **关系层 `R`**：
  - 按「主语 + 谓语」把**有状态事实**分组，用 LLM 识别显式替换，生成取代关系 `(j, supersedes, i)`；被取代的事实函数**仍然保留**（保留历史证据）；
  - 另以时间顺序、共享主语、共享主题补充连接。
- **模块化组合层 `D`**：
  - 从「当前状态模板」与「历史模板」实例化派生函数，注册进相应视图；
  - 当前状态判定（式 1）：设 `G(τ)` 为时间边界 `τ` 内符合条件的同组事实集合，活跃集 `A_G(τ) = { i ∈ G(τ) | ¬∃ j ∈ G(τ): (j, supersedes, i) ∈ R }`；若 `|A_G(τ)| = 1` 则当前值为该事实值 `v_i`，否则返回 `⊥` 表示状态未决；
  - 历史模板保留含被取代事实在内的全部事实（如把“银行职员 F1”与“教师 F2”组合成职业变迁 D1）；
  - 两类模板均保留事实 ID、对话引用与计算规则作为**溯源信息**。
- **视图 `V`**：概念视图（按人物/主题分组）与会话视图（按会话分组），通过共享引用导入函数。
- **记忆索引 `I = (I_view, I_func, I_ops)`**：
  - `I_func`：函数 ID → 入口点、描述、可接受参数；
  - `I_view`：视图 → 其引用的函数 ID 集合（支持“从视图导航到可调用函数”而无需读实现）；
  - `I_ops`：四类记忆算子接口——**记忆访问**（resolve / match / search / select / search_functions / execute）、**上下文扩展**（expand_scope / expand_relation / hydrate）、**证据组合**（union / rank / where / aggregate）、**验证**（validate）。

### 2.3 声明式检索（Declarative Retrieval：查询→程序）

- **检索程序定义**：给定查询 `q` 与记忆 `M`，程序 `P_q` 是在 `I` 暴露的算子上构建的可执行查询计划，显式指定**算子参数、依赖关系与条件续接**；执行 `P_q` 得到支撑证据 `E_q`。
- **一次规划**：用记忆索引做初始候选函数召回，把候选函数的 `I_func` 条目与 `I_ops` 算子约束组成**紧凑规划上下文** `I_q(M)`（不加载整个代码库）；LLM 规划器在一次调用中生成完整程序 `P_q = F_plan(q, I_q(M))`，用受限 Python 书写算子调用、参数、依赖与基于中间证据的**条件检索分支**。
- **执行与校验**：
  - 执行前做**结构兼容性检查**（允许的语言构造、算子调用、变量引用、证据依赖）；
  - 通过后在沙箱中对代码库执行，函数调用经索引解析，复用构建期确定的事实定义与状态计算；
  - 中间结果决定走哪条**已预先写好的**条件分支，因此可在不新增 LLM 规划决策的情况下继续取数；
  - 最终把选中事实、支撑对话与计算溯源组装为 `E_q`，并产出执行轨迹 `T_q`；答案由独立模型生成 `a_q = F_answer(q, E_q)`；
  - 失败处理：检查/执行失败触发**有界修复**（算法中最多 2 次重规划），仍失败则退回**固定兜底程序**；答案畸形/拒答时再做答案修复。
- **复杂度**：构建 `T_build = O(h log h + n² log n + C_build)`；单查询 `T_q = O(C_q + p(n² + h + b²) + p²)`（`p` 为程序语法树节点数，`b` 为证据展开规模）；常驻存储 `O(n + h)`（引用数 `r = O(n)`），查询额外 `O(pb)`。

## 6. 主要贡献与结论

- **概念贡献**：提出“记忆即代码”（Memory as Code）范式，把长期记忆从“被检索的数据集合”重构为“**可调用计算的库**”，把检索从“预定义流水线或逐步智能体探索”重构为“**一次规划生成的查询专属程序**”，为记忆系统提供了一个新的抽象层级。
- **技术贡献**：
  1. 一套**事实→函数→关系→模块化派生**的三层代码化构建流程，配合规范标识符与共享引用，使事实身份在组合中保持稳定；
  2. 一套**记忆索引**（`I_view / I_func / I_ops`）与四类记忆算子接口，使“从查询意图导航到可调用能力”无需加载整个代码库；
  3. 一套**声明式检索**机制：紧凑规划上下文 + 一次 LLM 规划 + 结构兼容性检查 + 沙箱执行 + 有界修复与兜底，兼顾灵活性与推理开销。
- **实证结论**：在 LOCOMO（三种异构骨干）与 LongMemEval 上，MaC 在 F1 与 LLM-Judge 准确率上总体优于 A-Mem、MemoryOS、Mem0、MRAgent；消融显示**声明式检索（DR）与代码化构建（CC）均有正贡献**，其中移除两者后退化最明显，说明“可复用计算 + 查询专属组合”是收益的主要来源；效率分析表明其在 token 消耗与运行时上具备竞争力，存储开销随事实数线性增长。

## 7. 方法优势与局限（客观评价）

**优势**

- **抽象层次恰当**：把“计算”作为一等公民，直接对应“跨会话事实需要被组合计算”的真实痛点，比“更强的检索启发式”更具结构性。
- **成本结构合理**：以“一次规划 + 预写条件分支”替代“多轮 ReAct 规划”，在保持灵活性的同时压缩了 LLM 调用次数，这一点在效率实验中得到了数据支持。
- **可溯源性强**：函数保留事实 ID、源对话引用与计算规则，证据 `E_q` 可回溯到原始会话，利于审计与纠错。
- **工程可控**：结构兼容性检查 + 沙箱 + 有界修复 + 固定兜底，构成了较为完整的鲁棒性防线，避免了“程序生成失败即系统失败”。

**局限**

- **构建期依赖 LLM 的质量与成本**：事实抽取、函数规格生成、取代关系识别均依赖 LLM，构建复杂度含 `O(n² log n)` 项，事实规模增大时的可扩展性存在隐忧；论文未给出大规模（万级事实）下的实测。
- **状态语义的表达力有限**：当前状态判定仅在活跃集唯一时返回值，否则返回 `⊥`；对于并行成立的多值状态（如同时持有多个职位/偏好）缺乏显式建模，可能把“多值”误判为“未决”。
- **规划器的能力上限即系统上限**：程序质量取决于 LLM 对算子接口与查询的理解，接口设计的“可学习性”未被系统评估；不同骨干上的性能差异（尽管结论一致）暗示规划器能力仍是瓶颈之一。
- **评测维度偏“问答”**：两个基准均以 QA 形式度量，未覆盖“记忆被下游任务反复复用”“长时程任务中记忆的增量演化”等更贴近“库”这一隐喻的场景。

## 8. 可复现性评估

- **较好之处**：给出了统一抽象、关键公式（活跃集定义）、算子接口分类、算法流程（含重规划次数上限）与复杂度分析，方法描述足以支撑独立实现；评测使用公开基准与公开基线。
- **不足**：未提供代码/数据链接（在给定文本中未见）；未报告提示词模板、函数规格的 schema 细节、结构兼容性检查的具体规则集；未说明基线（尤其 MRAgent）的复现配置与预算对齐方式；未给出 LLM 调用的温度、上下文长度、并发等推理配置；算力信息仅到“A100”粒度。
- **结论**：**方法层面可复现性中等偏上，实验层面可复现性中等**——核心机制可被重建，但数值结果的精确复现存在较多未披露的实现细节障碍。

## 9. 启示与可拓展方向

- **记忆系统的“接口化”**：把记忆能力显式暴露为带描述的算子与函数接口，可能成为记忆系统与智能体框架之间的标准契约，使记忆可被“编程”而非仅被“查询”。
- **构建期与检索期的分工**：本文展示了“把重计算前移到构建期、把组合决策留给检索期”的分工范式，这一思路可迁移到工具调用、检索增强生成等需要“复用中间计算”的场景。
- **可延伸的研究点**：多值/概率化状态语义；函数库的增量维护与版本演化；规划器的接口感知训练或接口自动精简；面向长时程任务（而非 QA）的记忆复用评测；构建质量的端到端误差归因分析。
