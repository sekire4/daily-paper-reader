## 摘要
AI智能体默认在跨会话时是无状态的，因此在运行层面表现为失忆：每个会话开始时，几乎不保留关于先前失败、修复、偏好或成功策略的持久知识。结果是，智能体会重复同样的错误，并丢弃来之不易的经验。主流解决方案是定制化记忆——将检索、持久化和学习逻辑手工接入单个智能体，并绑定到单一存储引擎。这造成了碎片化格局：记忆无法独立于拥有它的智能体进行替换、共享、隔离或推理。我们认为这是一个中间件问题：智能体记忆理应成为一个一等、可插拔的层，正如数据访问、消息传递和持久化各自都成为中间件关注点一样。我们通过六个系统挑战来展开这一愿景：双侧可插拔性、宿主原生介入、多租户隔离、写路径一致性、带来源追踪的联邦共享，以及生命周期治理。我们提出 ALTK-Evolve——面向自我改进型智能体的记忆中间件参考实现——并用它来推动未来记忆中间件更广泛的研究议程。

## Abstract
AI agents are stateless across sessions by default and therefore operationally amnesic: each session begins with little durable knowledge of prior failures, repairs, preferences, or successful strategies. As a result, agents repeat the same mistakes and discard hard-won experience. The dominant fix is \emph{bespoke memory}---retrieval, persistence, and learning logic hand-wired into one agent and bound to one storage engine. This creates a fragmented landscape where memory cannot be swapped, shared, isolated, or reasoned about independently of the agent that owns it. We argue that this is a middleware problem: agent memory deserves a first-class, pluggable layer, just as data access, messaging, and persistence each became middleware concerns.   We develop this vision through six systems challenges: two-sided pluggability, host-native interposition, multi-tenant isolation, write-path consistency, federated sharing with provenance, and lifecycle governance. We present ALTK-Evolve, a reference implementation of memory middleware for self-improving agents, and use it to motivate a broader research agenda for future memory middleware.

## 1. 核心问题与整体含义（研究动机与背景）

- **根本痛点：LLM 智能体天生“失忆”**。会话之间默认无状态，上下文窗口只是工作记忆而非持久记忆。一个编码助手花一小时才发现的构建参数、缺失的沙箱工具或特殊分页方式，下一次会话又要从零重新发现。随着智能体从一次性对话转向长期运行的软件行为体（多步规划、调用工具、多智能体协作），这种失忆从“有趣现象”变成**可靠性上限**。
- **现有方案是“定制化记忆”（bespoke memory）**：把向量库、检索提示、“把成功经验存下来”的步骤手工接入单个智能体的控制循环。这类方法确实有效（反思、技能库、轨迹蒸馏等已有工作证明），但存在四类结构性缺陷：
  - **不可移植**：换框架或换后端就要重写记忆逻辑；
  - **不可组合**：多个智能体无法可靠共享经验（例如开发者同时用 Claude Code、Codex、Antigravity 处理同一仓库，偏好与修复策略却散落在各工具私有记忆中）；
  - **语义不稳定**：事实、偏好、警告、修复、策略、过期产物被一视同仁当作文本块；
  - **不可治理**：企业需要可见性、策略与审计，个人需要查看、编辑、删除、授权记忆。
- **“存储 ≠ 中间件”**：文件、转录数据库、向量索引、托管记忆服务只提供持久化与检索；中间件必须定义“轨迹如何变成记忆、记忆如何变成上下文、上下文如何改变行为”的**语义**，以及隔离、共享、编辑、过期、审计、覆盖的**控制面**。作者用数据库/队列/缓存的历史类比论证：存储的出现不会消除中间件需求。
- **学习—治理鸿沟（learning–governance gap）**：智能体本地记忆（如 AGENTS.md、CLAUDE.md、技能库）贴近执行循环、学习内容丰富，但治理薄弱、私有于某个 harness；平台级记忆（Bedrock AgentCore、Vertex Memory Bank、OpenAI Memory 等）治理与持久化强，但语义偏个性化与会话连续性，缺乏从轨迹中提炼可复用操作知识的学习语义。二者都无法同时“学到”并“管住”。
- **核心主张（Big Idea）**：智能体记忆应成为**位于智能体与存储之间的一等、可插拔中间件底座**——对多个宿主（agent runtime）暴露统一契约、对多个后端可替换，并统一负责隔离、一致性、共享、来源追踪、用户控制与生命周期治理。外部记忆与权重内学习、RLHF、护栏是**互补**关系，承载的是无法按用户/租户训练进权重的部署级、项目级、组织级操作知识。
- **范围界定**：聚焦通过工具行动的软件智能体（编码、工作流、企业智能体）；具身智能体的记忆与感知控制耦合，不在讨论范围。

## 2. 方法论：核心思想与关键技术细节

### 2.1 三层设计框架

- **目标层（三目标）**：**Accuracy**（让行为更好而非记得更多，包括“不该浮现什么”）、**Cost**（上下文 token 与执行步数，压缩、惰性召回、按部署资源打包）、**Controls**（租户/范围隔离、可归因、默认私有、保留/审查/删除）。作者强调 accuracy 是 ML 社区已在追的目标，**cost 与 controls 才是记忆成为系统问题的原因**，也是它应归于中间件而非每个智能体的理由。
- **记忆类型层（Typed Memory）**：区分 **episodic**（任务/会话中发生了什么：轨迹、决策、错误、结果）、**semantic**（用户、项目、环境的稳定事实）、**procedural**（如何完成重复性操作）。三者几乎在存储层关心的每个维度上都不同：表示与访问方式、写语义（事实更新/情节不可变/过程被合并）、压缩容忍度、老化与治理策略。混在同一嵌入空间会产生 **retrieval interference**：一周的冗长工具调用情节会在近邻检索中淹没数月前“always target Java 11”的一行偏好——**不是被遗忘，而是被数量压过**。因此类型化是**结构性要求**，必须分 namespace 但相互链接。
- **六大中间件关注点**（由定制系统的反复失败模式推导：context leakage → 隔离；memory rot → 写路径一致性；silos → 可插拔与共享；unaccountable influence → 来源与治理）：
  1. **Two-sided pluggability（双侧可插拔）**：下抽象异构存储（文件、pgvector、分布式向量库、托管服务），上抽象异构宿主（控制循环、工具、提示上下文、轨迹各不相同）。缺的关键是**共同接口/编程模型**——类比“关系数据库之所以可互换不是因为内部趋同，而是因为都说 SQL”。
  2. **Host-native interposition（宿主原生介入）**：绑定宿主已有的拦截原语（生命周期钩子、用户命令、工具协议、项目级指令文件），对外呈现同一逻辑行为（行动前召回、行动后捕获），部署形态可为 sidecar、库、服务器、工具提供者或插件。
  3. **Multi-tenant isolation（多租户隔离）**：namespace 是最小抽象（用户/团队/项目/智能体/仓库/任务），但隔离必须贯穿存储、检索、合并、发布、删除、审计。
  4. **Write-path consistency（写路径一致性）**：append-only 记忆会“腐烂”（重复、过时、过度泛化、矛盾）。写路径应视为**协调问题**：add / update / merge / supersede / quarantine / reject。被协调的对象不是数据项而是**行为影响**。
  5. **Federated sharing with provenance（带来源的联邦共享）**：显式可见性模型（默认私有、主动发布）+ 联邦订阅/同步 + 来源可追溯（轨迹、用户、智能体、模型、策略）。共享同时扩大投毒与泄露的攻击面，故准入检查与来源验证也是**安全机制**。
  6. **Lifecycle governance（生命周期治理）**：保留、过期、压实、审计、审批、删除；多作者（智能体、用户、其他智能体、组织）需要策略钩子；治理既是企业驱动也是用户驱动。

### 2.2 参考架构：Experience Flywheel（经验飞轮）

- **六阶段闭环**：`capture → extract → consolidate → store → retrieve → inject`，通过智能体自身闭合。
- **五个接口 + 一个写路径阶段**：capture 接口记录轨迹；extraction 阶段蒸馏为记忆对象；store 在 backend 抽象后持久化；retrieval 接口选任务相关记忆；injection 路径回注；extraction 与 store 之间的 **consolidation** 负责新旧记忆协调。
- 架构只规定接口与语义，**不规定**具体智能体、模型、存储，任一组件的实现都可替换。

### 2.3 参考实现 ALTK-Evolve 的关键技术

- **类型化记忆模型**：三类记忆分 namespace；跨类型的公共单元是 **entity**——携带 content、type tag（guideline / fact / trajectory / policy）、metadata map（触发条件、来源=源任务与会话+自动或人工创建、所有权与可见性、以及 guideline 专属的 category、rationale、implementation steps、support count 与成功/失败证据）。会话轮次路由到 semantic，任务执行轨迹路由到 episodic/procedural；一条轨迹可同时产出事实与过程性准则。
- **Agent 面契约（六个逻辑操作）**：retrieve、write、consolidate、publish、delete、inspect。以 **MCP**（stdio/SSE）工具形式暴露：带类型过滤与 namespace 限定的任务条件检索、**dosage-aware 变体**（返回高支持度的常开核心准则 + top-k 最相关准则）、`save_trajectory`（捕获并触发抽取）、从对话轮次抽取事实、手工创建 entity、publish/unpublish、owner 校验的 delete。
- **控制面/数据面分离**：consolidation 与 inspection **故意不放在智能体工具面上**，而通过客户端库、CLI、Web 界面提供——“智能体可以使用记忆，但策展记忆是受治理、人类可见的行为”。
- **四类宿主绑定**（Table 1，同一逻辑操作、不同原语）：Claude Code（插件 + 项目指令文件一行 import + skills + 原生记忆桥接）、Codex（全局指令文件指针 + recall-first 协议）、Claw Code（携带 skills 的插件 + 可选 pre-tool-use 钩子）、IBM Bob（全局规则文件 + 命令 + 完整部署中的 MCP server）。共同附加**只追加的召回审计**（哪些记忆被查阅、是否被遵循）。
- **从轨迹到可复用记忆的四步抽取**：
  1. **Task segmentation**：轨迹未显式切分时先识别实际执行的不同任务；
  2. **Subtask identification**：分解到子任务粒度（如“服务认证”“结果集过滤”被大量无关任务共享，比任务级更可复用）；
  3. **Generalization**：抽象掉任务特定实体（“某个播放列表”→“目标播放列表”），使结构相似子任务可匹配；
  4. **Clustering and consolidation**：按语义相似度聚类，簇内 tips 合并去重为更全面的准则。
  - 这一“先泛化再合并”的纪律同时让写路径一致性可处理：协调发生在**可复用操作层面**而非逐字文本层面。
- **Purpose-directed gisting + 分层存储**：冗长的 episodic 会话与工具输出不逐字入索引，而是存为模型生成的 **gist**（嵌入向量索引）+ 原文留在 durable store 并以指针关联（gist 是索引，不是替代品）。压缩提示**编码该 gist 的用途**：面向 semantic 的对话轮次突出用户属性与偏好；面向 procedural 的工具调用突出检索/计算了什么、用了什么参数、结果如何。理由是完整段落嵌入会稀释“埋在长消息里的一句偏好”，用途定向压缩可让该信号主导检索。工具调用 gist 与对话 gist 分 namespace，避免互相污染、独立伸缩。**读时由模型在上下文中决定粒度**：gist 不足时才回取原文，实现自适应保真度而无需固定检索规则。
- **存储后端**：文件、pgvector、Milvus（三个可换后端）。

## 3. 实验设计

- **Benchmark**：**AppWorld**（公开多步智能体基准，任务需要规划、工具使用、状态跟踪与错误恢复）。
- **流程**：在 AppWorld 的 **train 与 dev** 分区上从智能体轨迹抽取准则；两个条件均在**留出的 test-normal 分区**评估。基线**无记忆**；实验组通过记忆接口检索并注入学到的准则。
- **控制变量**：两个条件使用**同一 GPT-4.1 智能体与同一推理循环**，唯一差异是记忆层，因此增益可归因于“作为可分离层提供的记忆”而非智能体本身改变。
- **指标**：AppWorld 的两个完成度指标——**Task Goal**（单任务成功）与更严格的 **Scenario Goal**（场景内所有任务都成功），并按 Easy / Medium / Hard 分层报告。
- **对比方法**：仅与“无记忆基线”对比；**未与** Reflexion、ExpeL、Voyager、Mem0、A-MEM、MemGPT 等其他记忆/自改进方法做横向比较。
- **可移植性验证**：同一记忆层未加修改地跑在四个独立开发的编码智能体宿主（Claude Code、Codex、Claw Code、IBM Bob）上，绑定各自原生拦截原语；以及三个可换存储后端。
- **结果（Table 3）**：
  - Aggregate Task Goal：69.6 → **73.2**
  - Aggregate Scenario Goal：50.0 → **64.3**（+14.3 点）
  - Hard 层 Scenario Goal：19.1 → **47.6**（翻倍以上）
  - Easy Task 89.5→91.2，Easy Scenario 79.0→89.5；Medium Task 66.7→70.8，Medium Scenario 56.2→56.2（**无变化**）；Hard Task 54.0→58.7。
- **作者自我定位**：明确称这些结果是“可行性与信号的证据，而非完整评估”，更完整的研究正在进行中。

  - **无污染/投毒/泄露的安全实验**：论文把 provenance 与准入检查论证为安全机制，但没有任何对抗性评估；
  - **无人类评估**：治理面（inspect/edit/delete）是核心主张之一，却没有用户研究或可用性评估。

- **总体判断**：作为**可行性演示（feasibility demonstration）**是合格的：它证明了跨宿主、跨后端的同一记忆层可以跑通并带来可测增益；但作为**科学评估**远不充分，作者本人也承认这一点。+14.3 点 Scenario Goal 与 Hard 层翻倍是最有说服力的信号，但缺乏消融使其归因只能是“整个记忆层”，而非其中任一设计决策。

## 6. 批判性评估：优点与不足

### 6.1 主要优点

- **问题定位准确且有产业现实感**。把“记忆”从“检索技术”重新表述为“中间件 + 治理问题”，并指出 cost 与 controls 才是记忆成为系统级问题的原因，这一框架比多数记忆论文的视角更贴近真实部署。学习—治理鸿沟的提法（本地记忆学得多但管不住，平台记忆管得住但学不深）是对现状的精准概括。
- **类型化记忆的论证有说服力**。用 retrieval interference 解释“偏好被情节淹没”不是遗忘而是被数量压过，并由此推出类型化是结构性要求而非工程偏好，这个推理链清晰且可检验。
- **控制面/数据面分离的设计判断成熟**。“智能体可以使用记忆，但策展记忆是受治理、人类可见的行为”——把 consolidation 与 inspection 移出智能体工具面，是对“让智能体自我改写长期记忆”这一风险的清醒回应。
- **purpose-directed gisting 是一个具体、可复用、有解释力的技术点**。压缩时编码 gist 的用途、按来源分 namespace、读时由模型决定回取原文的粒度，这套组合比“摘要后嵌入”更精细，且其动机（避免长段落稀释关键信号）可以被独立验证。
- **跨宿主绑定（Table 1）展示了真正的可移植性**。同一逻辑契约在四个独立开发的 harness 上以不同原语落地，这是“中间件”主张最有力的实证支撑，也是多数记忆工作不具备的工程纵深。
- **诚实的自我定位**。明确标注 preliminary、明确说结果是 signal 而非完整评估，避免了过度声称。

### 6.2 主要不足

- **实证强度与主张规模严重不匹配**。论文提出的是“记忆应成为一等中间件底座”这样的架构级主张，但支撑证据是单 benchmark、单模型、单对照、无消融、无成本数据的一次实验。主张的普适性与证据的狭窄性之间存在明显张力。
- **缺少最强基线的对比**。“把学到的准则直接写进系统提示 / AGENTS.md”是最自然、最廉价、工业界最常用的做法，也是中间件必须战胜的对手。论文回避了这一对比，使得“中间件优于定制化记忆”这一核心论点在 accuracy 维度上未被证明——它至多在治理维度上成立。
- **Cost 目标被反复强调却完全未测量**。这是论文自身框架的内部不一致：既然论证 cost 是记忆成为系统问题的原因，就应给出 token/延迟/存储的量化，否则该论证停留在概念层。
- **写路径一致性（consolidation）缺乏机制细节与评估**。add/update/merge/supersede/quarantine/reject 被列为写路径的协调动作，但论文没有说明冲突检测如何实现（语义相似度阈值？LLM 判定？）、误合并如何回滚、quarantine 的判定标准是什么。这恰恰是最容易出错、也最能体现“中间件”价值的部分。
- **安全论证停留在设计意图**。共享扩大投毒面、provenance 作为安全机制，这些论断合理但无任何对抗实验支撑；对于一篇把治理作为卖点的论文，这是显著缺口。
- **Medium 层零增益未被讨论**。这一反常结果可能暗示增益主要来自“困难任务上的探索节省”，而非普遍的行为改进，但论文未做任何分析。
- **对“记忆腐烂”的长期动态缺乏观察**。论文的诊断（append-only 会腐烂）很有力，但实验是一次性的离线抽取 + 评估，没有展示记忆库在多轮、长期运行下的演化、膨胀与退化曲线，也就无法验证 consolidation 是否真的抑制了腐烂。

## 7. 启示与可延展方向

- **可检验的研究议程**：论文实际上给出了一个清晰的可证伪清单——(a) 类型化 namespace 是否比单一嵌入空间带来更高召回精度；(b) purpose-directed gist 是否优于通用摘要；(c) dosage-aware 检索是否优于纯 top-k；(d) consolidation 是否降低重复率与矛盾率。任何一项的消融都能成为独立论文。
- **“中间件 vs 提示注入”的对照实验**是判断该路线价值的关键分水岭，也是最应优先补做的实验。
- **治理面的可用性研究**是空白地带：用户如何审查、编辑、授权智能体记忆，什么样的可见性模型能让人真正信任，这些是 HCI 与系统研究的交叉议题。
- **多智能体共享记忆的联邦模型**（默认私有 + 主动发布 + 来源可追溯）在工程上类比包管理/依赖管理，其版本冲突、回滚、可信发布者等问题都可借用既有生态的经验。
- **与权重内学习的边界划分**：论文提出外部记忆承载“无法按用户/租户训练进权重的部署级、项目级、组织级操作知识”，这是一个有用的分工假设，但缺乏实证——什么知识适合进权重、什么必须留在外部，仍是开放问题。
- **标准化机会**：若“记忆契约”真如 SQL 之于关系数据库，那么接口标准化（类似 MCP 已做的工具标准化）可能是该领域最有杠杆的一步，本文的六操作契约可作为草案起点。

---

## 8. 一句话总结

本文把智能体记忆从“检索技巧”重新定位为“位于智能体与存储之间、必须同时负责学习语义与治理语义的一等中间件”，给出了类型化记忆、经验飞轮与 purpose-directed gisting 的具体设计，并用跨四宿主、三后端的 AppWorld 可行性实验（Scenario Goal 50.0→64.3）证明了这条路走得通；但其证据强度仅够支撑“值得继续研究”，尚不足以支撑“应当如此架构”——尤其是缺失的消融、成本测量与最强基线对比，是该主张兑现前必须补齐的三块短板。

（完）
