## ABSTRACT 

In agentic search, a document can match an agent-generated sub-query without helping answer the user’s original question. Conventional rerankers score documents against the sub-query alone, overlooking the broader task and the agent’s reasoning. We introduce the Agent-Context-Aware Reranker (ACARe), a compact 4B LLM trained to rerank documents using this context when available. Across multiple benchmarks and agent families, ACARe improves retrieval quality over its base reranker while reducing search effort. These benefits extend to answer generation: ACARe improves accuracy and reduces searches over no reranking, while matching or exceeding the base reranker’s mean accuracy with more precise evidence. It also helps smaller agents narrow the retrieval-quality gap to larger agents, showing how better retrieval tools can make smaller agents more effective. The model, training data, and code will be released soon. 

## 1 INTRODUCTION 

Search agents answer complex questions by searching for evidence over multiple steps (Yao et al., 2023; Jin et al., 2025; Tongyi DeepResearch Team et al., 2025; Li et al., 2026). Given a user’s ques-tion, an agent issues a search query, reads the returned documents, and decides what to search for next. We call each agent-generated search query a sub-query . A reranker scores the retrieved docu-ments to prioritize the evidence the agent sees. Conventional rerankers score each document against only the sub-query, which is often keyword-like (Meng et al., 2026) and omits the broader task. A document can therefore match a sub-query without helping answer the user’s original question. The original question states the agent’s goal, while its available reasoning trace explains what evi-dence is needed next. Neither requires additional generation. Some first-stage retrievers (Z. Chen et al., 2026a; H. Chen et al., 2026) use this context, but deploying them requires local access to the document corpus. A second-stage reranker, however, refines candidates from any source, support-ing lexical and dense retrieval as well as search APIs exposing document text without corpus access, where context-aware first-stage retrieval is infeasible. We introduce the Agent-Context-Aware Reranker (ACARe), a 4B decoder-only LLM fine-tuned from Qwen3-Reranker-4B (Zhang et al., 2025), a compact, strong open-weight reranker. We use the sub-query and agent context to score candidates independently, which avoids the sequential sliding-window passes that listwise rerankers require for long candidate lists (Sun et al., 2023; Pradeep et al., 2023). To train ACARe, we combine new agent trajectories with original and re-mined DR-Synth (Z. Chen et al., 2026a) labels. Re-mining changes candidates but preserves sub-queries and traces. We incorporate independent context dropout to support missing fields and proprietary agents that do not expose reasoning traces. We also show that ACARe’s benefits combine with context-aware first-stage retrieval (Section 5.2), complementing existing retrievers. In summary, our contri-butions are:

## 2 BACKGROUND AND RELATED WORK 

Retrieval for search agents. Search agents interleave reasoning and external actions; deep-research systems extend this pattern to sustained search and evidence synthesis (Yao et al., 2023; Jin et al., 2025; Tongyi DeepResearch Team et al., 2025; Li et al., 2026). Fixed-corpus benchmarks such as BrowseComp-Plus enable reproducible evaluation of these interactions (Z. Chen et al., 2026b). Unlike a user question, an agent’s sub-query is generated within a trajectory and may omit infor-mation already present in the conversation. Meng et al. (2026) find that these queries often consist of keywords, phrases, and exact-match expressions, differing from the natural-language questions commonly used to train neural rankers. This motivates retrieval methods that use the agent’s context. 

Context-aware first-stage retrieval. AgentIR embeds the reasoning trace with the sub-query (Z. Chen et al., 2026a), while ITER also incorporates the original question and preceding sub-queries (H. Chen et al., 2026). Both require local access to the document corpus, whereas ACARe reranks returned documents. 

Session and conversational search. Context-aware ranking predates search agents: session-search models rank documents using a user’s earlier in-session search activity (Ahmad et al., 2019), and conversational search resolves context-dependent questions by rewriting them or by condition-ing retrieval and reranking on dialogue history (Dalton et al., 2020; Anantha et al., 2021; Qu et al., 2020). ACARe instead conditions a model-generated, often keyword-like sub-query on the agent’s original question and its own reasoning trace, with one checkpoint handling either field’s absence. 

Reasoning-intensive retrieval. ReasonIR, RaDeR, and ReasonEmbed train dense retrievers (Shao et al., 2025; Das et al., 2025; J. Chen et al., 2026). Their focus is improving one-shot neural retrieval rather than interpreting sub-queries within an evolving agent trajectory. 

Retrieval learning from agent feedback. LRAT learns from the agent’s browsing actions, un-browsed candidates, and post-browse reasoning (Zhou et al., 2026). Agentic-R combines local query–passage relevance with global answer correctness to measure passage utility and alternates agent and retriever optimization (Liu et al., 2026b). Critic-R uses post-retrieval reasoning to re-fine queries and converts feedback from successful and failed refinements into retriever supervi-sion (Alam et al., 2026). CoSearch jointly trains an agent and a generative ranker using rewards that combine ranking quality with trajectory outcomes (Zeng et al., 2026). These systems use down-stream agent behavior to train the retrieval tool, sometimes jointly with the agent. ACARe focuses on a different requirement: using the original question and available reasoning trace to interpret each sub-query at ranking time, with one checkpoint supporting all four context modes. 

Reranking in agentic search. Pointwise and generative listwise rerankers refine first-stage candi-dates (Zhang et al., 2025; Sun et al., 2023; Pradeep et al., 2023). Instruction-aware retrieval includes a reranker conditioned on human-written task descriptions (Asai et al., 2023). Sharifymoghaddam & 2Preprint. Work in progress. Lin (2026) use the search agent’s own LLM at low reasoning effort as a listwise reranker; medium-effort search with reranking can outperform high-effort search without reranking in retrieval quality and answer accuracy at lower effective token cost. Meng et al. (2026) report retrieval and answer-quality gains from reranking, generally with fewer searches, and test query-only and reasoning-conditioned sub-query rewriting. SetR selects passage sets that satisfy a query’s information re-quirements (Lee et al., 2025), while Rank4Gen learns selection and ordering from downstream gen-eration preferences (Fan et al., 2026). Generative ranking and selection add autoregressive decoding overhead; long candidate lists can also require sequential sliding-window passes (Sun et al., 2023; Pradeep et al., 2023). Concurrent to our work, RubricRanker (Liu et al., 2026a) trains a generative listwise selector with search rubrics, supporting reasoning-conditioned search and question-only RAG. ACARe instead scores documents independently and trains one checkpoint for four context modes, including question-only context when traces are hidden. 

## 3 ACAR E METHODOLOGY 

3.1 PROBLEM FORMULATION 

We consider an agent that gathers evidence for an original question Q through a ReAct-style loop (Yao et al., 2023). Its output is either a ranked document list for an upstream orchestrator or an evidence-grounded answer for a deep-search task. Both settings share the trajectory

Our reranker supports both outputs; the main experiments evaluate retrieval-only output, and a transfer experiment evaluates answer generation (Section 6.4). Conventional rerankers score candidates against qt alone, although sub-queries may omit the search intent or constraints in Q. We include available agent context to recover this information. 3.2 AGENT CONTEXT 

We use two context fields: the original question Q and the reasoning trace τt preceding the current search. The former is fixed throughout the session; the latter is the text the agent has already pro-duced, when exposed by its interface. We do not make an additional model call to elicit a trace. Con-text therefore requires no additional agent generation, although including it increases the reranker’s input length. We define four input modes: M0 contains qt alone; M1 contains (qt, τ t); M2 contains 

(qt, Q ); and M3 contains (qt, τ t, Q ). The instruction and query block depend on the mode, while the system message and document field are shared (Figure 4). In M0 , the prompt is identical to the base Qwen3-Reranker prompt. Following Z. Chen et al. (2026a), we use the current trace rather than concatenating traces from earlier turns. The decoder-only LLM jointly processes the sub-query, retained context, and one candidate docu-ment. Relevance can therefore depend on the available agent context, without requiring each docu-ment to answer the whole question. Context availability determines the inference mode. Agents that expose their reasoning can use M3 when Q is also available. Agents that do not expose reasoning can use M2 ; deployments without either field use M0 . The inference-context ablation in Section 6.2 compares these modes for one agent and benchmark. 3Preprint. Work in progress. 3.3 MULTI -TASK TRAINING OVER CONTEXT MODES 

ACARe is initialized from Qwen3-Reranker-4B and fine-tuned as a single checkpoint supporting all four modes. During training, the reasoning trace and original question are independently dropped with probability 0.5. A dropped or unavailable field is omitted, and the prompt uses the instruction corresponding to the remaining fields. When both fields are available, each mode has probability 

0.25 . Missing source fields can change the effective mode distribution. Dropout decisions are deter-ministic functions of the seed, epoch, field, and query, ensuring consistent masks across workers. Each training instance is a sub-query with its available context, one positive document, and retrieved negatives. The same sampled context is used for all documents in its group. The model scores each query–document pair using the difference between the next-token logits for yes and no . Following Gao et al. (2021), we use localized contrastive estimation (LCE) rather than pointwise binary cross-entropy to train the reranker to distinguish a positive document from retrieved negatives. LCE applies cross-entropy over the group’s scores with temperature 0.5. At inference, a sigmoid converts the logit difference to a relevance score without changing document order. Training inputs are capped at 5,120 tokens so that eight query–document pairs (one training group), model state, and activations fit within each GPU’s 80 GB memory; inference uses an 8,192-token cap. Section A gives the exact objective and optimization settings. A single checkpoint thus supports both agentic and one-shot retrieval. In the one-shot evaluation (Table 1), it uses M0 , so comparisons with the base reranker measure the effect of fine-tuning without additional inference context. 3.4 TRAINING DATA 

Training requires relevance labels for an agent’s sub-queries rather than only for the original ques-tion. We extend the DR-Synth construction of Z. Chen et al. (2026a) to retain Q alongside each sub-query and its reasoning trace. Starting from questions with gold answers and supporting doc-uments, an agent generates search trajectories. For each sub-query, an oracle reranker receives the retrieved candidates, gold supporting documents, original question, and gold answer. Its ranking supplies positive and negative documents for that sub-query. A separate judge filters trajectories by comparing the agent’s final answer with the gold answer. We combine three label sets from two rollouts. We retain the original DR-Synth labels and retrieve and label new candidates for its recorded sub-queries using Nemotron-3-Embed-8B 1 as a second retriever. Re-mining changes the supervision documents but preserves the sub-queries and reasoning traces. We also generate a new rollout using that second retriever, with the oracle’s top-ranked documents returned to the agent during search. The pool contains 16,601 instances, versus 5,238 in DR-Synth. We select the data mixture and hyperparameters on a validation split grouped by original question, then train the final checkpoint on the full pool. Section A specifies the models, candidate construction, filtering, and size of each label set.

5.1 ONE -SHOT RETRIEVAL 

Table 1 compares rerankers across four first-stage retrievers and three datasets in one-shot retrieval: each original question is searched once, without agent-generated follow-up queries. Results com-bine BCP’s two qrel sets and BRIGHT’s and TRQA’s subsets, with equal weight across datasets. Section C provides detailed results and standard deviations. For each dataset, we choose the retriever with which ACARe provides the smallest one-shot nDCG@10 improvement over no reranking. The agentic evaluation therefore uses the least favorable first-stage settings for ACARe under this one-shot criterion. We omit Jina-Reranker-v3, which consistently trails both other rerankers, and compare ACARe with no reranking and Qwen3-Reranker-4B throughout the remaining experiments.

## 7 CONCLUSION 

Search-agent sub-queries can omit the goal and reasoning needed to judge document relevance. We introduce ACARe, to our knowledge the first pointwise LLM reranker trained to use this context for search-agent sub-queries. Fine-tuned from Qwen3-Reranker-4B, ACARe improves mean retrieval quality across three benchmarks and five LLM families while reducing search effort. On TRQA, it improves context-aware AgentIR’s results for all five agents, whereas Qwen3-Reranker-4B low-ers mean nDCG@10 for four. On BCP, smaller agents gain at least as much as larger ones over no reranking, closing 51–74% of the nDCG@10 gap to larger agents without reranking, versus 26–46% with the base. The benefits extend to answer generation through a BM25 API over 553 million docu-ments. A BCP context control shows that ACARe’s context formulation also benefits the unchanged base reranker, while the trained checkpoint achieves the best means on every metric. These results 9Preprint. Work in progress. highlight ACARe as a promising lightweight reranker whose independent, parallelizable scoring makes deeper reranking practical to explore. 

## 8 LIMITATIONS AND FUTURE WORK 

We expand the training data through an agent rollout with a second retriever, while retaining the original DR-Synth seed questions, agent LLM, and oracle reranker. Varying these components, the corpus, and the retrievers and rerankers used for negative mining could broaden supervision and further improve reranking effectiveness. We evaluate on two existing deep-search datasets with fixed corpora, BCP and TRQA. The base-reranker context control uses one agent on BCP. Evaluation on additional such datasets as they become available and with live-web search APIs remains future work. Our cost analysis covers agent API usage, assuming agent LLMs are substantially larger and costlier than retrievers and rerankers. In our size study, smaller agents benefit more from a higher-quality retrieval tool, but further reducing their size toward the 4B reranker could make reranking costs non-negligible. Measuring total serving costs would clarify this effectiveness–cost tradeoff. 

## ETHICS STATEMENT 

ACARe is fine-tuned from Qwen3-Reranker-4B and may inherit biases and other limitations of the base model. Training examples are mined using an oracle reranker, whose judgments may introduce biases into the training dataset. Fine-tuning for relevance does not ensure that highly ranked documents are accurate, fair, or safe. Downstream applications should account for these risks when using the retrieved evidence.

You are a retrieval agent that finds all documents related to a given query. <Goal> You are given a search query and a list of documents retrieved for that query. Your task is to write new queries and use the given search tool to find *ALL* the related and somewhat related documents to the given query (i.e., maximize recall). If the user’s query is a question, you should not answer the question yourself. Instead, you should find the related documents for the given query. </Goal> <RELEVANCE_DEFINITION> - You should be careful, in the context of this task, what it means to be a "query", "document", and "relevant" can sometimes be very complex and might not follow the traditional definition of these terms in standard information retrieval. - In standard retrieval, a query is usually a user question (like a web search query), the document is some sort of content that provides information (e.g., a web page), and these two are considered relevant if the document provides information that answers the user’s query. - However, in our setting, this could be different. Here are some examples: * the query is a programming problem and documents are programming language syntax references. A document is relevant if it contains the reference for the programming syntax used for solving the problem. * both query and documents are descriptions programming problems and a query and document are relevant if the same approach is used to solve them. * the query is a math problem and documents are theorems. Relevant documents (theorems) are the ones that are useful for solving the math problem. * the query and document are both math problems. A query and a document are relevant if the same theorem is used for solving them. * the query is a task description (e.g., for an API programmer) and documents are descriptions of available APIs. Relevant documents (e.g., APIs) are the ones needed for completing the task. - This is not an exhaustive list. These are just some examples to show you the complexity of queries, documents, and the concept of relevance in this task. - Note that even here, the relevant documents are still the ones that are useful for a user who is searching for the given query. But the relation is more nuanced. - You should analyze the query and some of the available documents. And then reason about what could be a meaningful definition of relevance in this case, and what the user could be looking for. - Moreover, sometimes, the query could be even a prompt that is given to a Large Language Model (LLM) and the user wants to find the useful documents for the LLM that help answering/solving this prompt. </RELEVANCE_DEFINITION>

## E COST ANALYSIS 

We report the agent LLM’s API cost per query. Retrieval and reranker serving costs are excluded from all experiments, including those in the Analysis section (Section 6). Reported savings concern agent API charges, not total system cost; excluded costs may matter more for cheaper agents. Costs are computed from recorded token usage using the rates in Table 8, with reasoning tokens counted as output. Public list prices are as of September 2026. Lightning uses the experiment-recorded rates for its OpenRouter route: $0.08 for input, $0.04 for cache reads, and $0.20 for output per million tokens. Local inference is valued at the same rates, as a token-priced estimate. GPT-5.5 judging uses recorded OpenAI rates of $5 for input and $30 for output per million tokens; its pub-lished cache-read rate 11 is $0.50. No cache usage was recorded for the judge. MiniMax M3 has no recorded cache writes, so its cost calculation requires no cache-write rate. Because the conversation is resubmitted at each turn, a document can incur input charges repeatedly after it is first retrieved. Fewer searches and shorter trajectories can therefore reduce cost, but the number of calls alone does not determine the savings. The token-priced totals in Table 8 sum each recorded run’s per-query cost multiplied by its number of questions, plus retained answer-judge usage for both Piika studies. Runs reused across studies are counted once using their source-result paths. These totals exclude omitted experiments, unrecorded attempts, training costs, and judging outside those studies. Piika contributes 36 ClimbMix runs and 30 BCP context-control runs (Sections J.1 and J.2), totaling 8,052 question executions. Its recorded usage is valued at $50.30 for GPT-5.6 Luna, $123.92 for Nemotron-3.5 Lightning, and $64.21 for 7,802 GPT-5.5 judgments through OpenAI. The remaining 250 executions incur no judge cost. The Lightning total includes local inference valued at API token rates, so the combined total is a token-priced accounting estimate. Piika cost comparisons are omitted because serving conditions affected billed cost: Lightning runs switched between API providers and local serving under heavy throttling, and each Luna reranking configuration ran on its own vLLM server under a different load, so queuing delays changed agent-side prompt-cache reuse. Search counts are reported throughout the agentic evaluations as a measure of retrieval effort. Two additional factors affect the cost of a trajectory. First, document length and retrieval timing determine how much text appears in later prompts: a long document retrieved early contributes more repeated input than one retrieved near the end. Second, caching determines how much of that input receives a discounted rate. With implicit caching, cache availability can vary with endpoint workload and cache eviction, changing the billed cost even for similar token volumes. The reranker influences which documents are returned, but does not control the provider’s cache. Our measurements do not isolate the contributions of caching and document timing to cost variance. Averaged over benchmarks, ACARe uses significantly fewer search calls than Qwen3-Reranker-4B for every agent, but has significantly lower API cost only for Nemotron-3 Ultra, by approximately 12%. Sonnet has a 3% mean saving that does not remain significant after correction. The other three agents’ cost differences are also nonsignificant, including MiniMax M3’s 0.069-cent saving (p = 1 .000 ; Table 18). These five runs do not establish equal costs. Benchmark-specific outcomes are more mixed. Relative to Qwen3-Reranker-4B, ACARe has higher mean API cost in seven cases: Nemotron-3 Ultra, MiniMax M3, Gemini 3.6 Flash, and GPT-5.6 Terra on BRIGHT, and Gemini 3.6 Flash, GPT-5.6 Terra, and Claude Sonnet 5 on TRQA. Only Terra’s two increases remain significant after correction (Table 18). MiniMax M3’s cost differences are nonsignificant on all three benchmarks ( p = 0 .969 on BRIGHT; p = 1 .000 on BCP and TRQA). Thus the aggregate quality and search-effort gains should not be interpreted as uniform cost im-provements. Search calls provide a direct measure of retrieval effort, while API cost measures the combined effect of trajectory length, document content, and provider pricing.

## I AGGREGATION AND STATISTICAL TESTS 

In the retrieval evaluations, BCP quality metrics average the gold and evidence label sets; BRIGHT and TRQA quality metrics are macro-averages over twelve and three subsets, respectively. Search calls, LLM turns, and API costs are pooled over the questions within each benchmark. Overall results average the three benchmark-level values with equal weight. Tables report means and sample standard deviations over five runs (six for Piika); figures use the same means and standard deviations. We compare configurations with two-sided Welch t-tests on their run-level values and apply Benjamini–Yekutieli (BY) correction (Benjamini & Yekutieli, 2001) within each comparison fam-ily. BY controls the false discovery rate, the expected fraction of false rejections among rejected hypotheses, under arbitrary dependence between tests, provided the individual p-values are valid. All reported p-values are adjusted, with significance defined as p < 0.05 . Welch tests allow unequal variances but assume independent runs and approximately normal run-level means. With only five or six runs, these assumptions are difficult to assess. The tests assess whether differences are con-sistent across repeated executions of the same questions. They do not assess generalization to other questions. A nonsignificant result means that the repeated runs provide insufficient evidence of a difference, not that the systems perform equally. 

Main comparisons. The aggregate family contains 75 tests: all three pairwise comparisons among no reranking, Qwen3-Reranker-4B, and ACARe, for five agents and five metrics (nDCG@10, Re-call@10, searches, LLM turns, and API cost). The benchmark family contains the corresponding 225 tests over three benchmarks. Thus claims based on either quality metric account for testing both metrics. False discovery rate control applies within each specified family, not across the entire paper.
