# Routed Continual Learning 

> Michael Philip 1,∗

, Mahesh Balakrishnan 1, David Geraghty 1, David Mao 1, Vidhya Venkat 1, Ilya Mironov 11FAIR at Meta 

> ∗

Main Contributor 

Agents deployed at scale repeatedly encounter related problems, and it is natural to let them learn from each other’s experience rather than starting over each time. Unfortunately, there is no single way to retain that experience that works well across settings, and no way to know in advance which future problems a given experience will help with. A global history preserves every detail but becomes expensive and mixes together experience that may not belong together; compressing that history into one fixed representation limits the cost but can throw away valuable details. We introduce Routed Continual Learning (Routed CL), an architecture that decides how to partition and retain experience. Past trajectories are grouped into clusters, each of which maintains state using one memory system from a fixed library. Before each run, an LLM-based router either reuses an existing cluster or creates a new one, basing its decision on the problem statement, memory system descriptions, and cluster summaries. We also introduce Context Memory Adapter, which mediates between the memory system and the agentic loop by augmenting the agent’s initial context with the memory system’s outputs and updating the selected cluster with information from the trajectory. We evaluate the architecture on a heterogeneous stream that interleaves 301 instances from the six CL-Bench tasks with 97 banking instances from τ 3-Bench, for 398 instances total. Across four language models and five matched rollouts, Routed Continual Learning raises normalized reward over a single global in-context learning (ICL) history by 15–30% of the maximum attainable normalized reward, achieves higher mean normalized reward than ICL-only clustering, and reduces estimated API cost by 65–72% relative to Global ICL. These results support approaching continual learning as a routing problem that chooses both a learning mechanism and a state cluster rather than committing to one representation globally.

## 1 Introduction 

State-of-the-art agentic systems are designed to operate at scale, with distributed heterogeneous agents acting concurrently and independently. Many of these agents encounter related problems and could benefit from shared knowledge, which can reduce token cost, improve task performance, and keep agents from repeating one another’s mistakes. One striking example occurred during a recent OpenAI cyber-capability evaluation. Independently instantiated agents created an unintended shared message board and used it to propagate exploit findings across runs. The resulting exchange of information enabled agents in the broader evaluation to obtain breakthrough capabilities beyond the reach of individual agents (OpenAI, 2026; Greenblatt et al., 2026). Our goal is to make such sharing deliberate: to build a system that supplies agents with relevant prior experience by design, rather than expecting them to develop one. To this end, we must decide what information to extract from trajectories, how to represent it, which agents should receive it, and when it should be provided. Different applications may require different answers to these questions; no single memory system is optimal across all of them. The distributed environment of an enterprise setting compounds these challenges: agents are built by different teams, wrap different models, and have no reason to know that other agents exist. Our architecture places minimal requirements on the agents it supports. It intercepts an agent’s prompt and, when useful, injects relevant content directly into the agent’s context, requiring no explicit cooperation. The result of this work is an architecture with two central features: • Transparent deployment: The architecture requires neither coordination among individual agents nor changes to how they operate. • Routing: Because no single memory system serves every application equally well, a routing component selects a memory system and relevant prior state for each run. Continual Learning Bench (CL-Bench; Asawa et al., 2026) provides a useful starting point for evaluating an implementation of this architecture. Following CL-Bench’s convention, we call each individual problem an 

instance ; a sequence of instances from the same domain is a task . Examples of these tasks include text-to-SQL transformations and playing poker against deterministic opponents. An instance of a task for the first example is a single natural-language question that may require multiple SQL queries to resolve; an instance of the poker task is a single hand. CL-Bench evaluated six such tasks in isolation and found that naïve in-context learning (ICL) outperformed dedicated memory systems on the aggregate metric. Retaining prior trajectories provides a strong baseline when each task is evaluated separately, which is the target scenario for the benchmark. This approach becomes less effective when different tasks are interleaved: a single history combines experience that may be useful for one task but irrelevant for another. A learning system must therefore decide what observations to share among which instances, and when to use a different memory system. To expand the range of tasks beyond CL-Bench, we incorporate the Banking Knowledge domain from τ 3-Bench (Shi et al., 2026). Each instance is a multi-turn customer-service conversation in which an agent must follow a domain policy, retrieve unstructured knowledge, and use tools while interacting with a simulated user. This contributes 97 thematically related instances with an interaction structure and reward function substantially different from those of the six CL-Bench tasks. We introduce Routed Continual Learning , which assigns each instance to a cluster that couples a memory system with a set of prior trajectories (that can be empty). Before each instance, a router , implemented as a large language model (LLM), decides whether to reuse an existing cluster or create a new one, in which case the router selects a memory system from a fixed library. The memory system defines the learning mechanism; the cluster maintains the memory system’s state and publishes a summary to guide assignment of future instances. The router uses only the current instance, memory system descriptions, and cluster summaries; task labels during the benchmark evaluation are not supplied. Our five memory systems (Table 2) retain prior trajectories, distill reusable reasoning strategies, or model structured numerical state. Some memory systems require mapping a task-specific schema into generic state. We therefore introduce Context Memory Adapter , a shared runtime that derives this mapping, or adapter, from prior experience and supplies learned state through the agent’s context. 2We evaluate four language models on a heterogeneous 398-instance stream combining all six CL-Bench tasks with 97 τ 3-Bench banking instances. Four staged conditions progressively add capabilities: Stateless ICL (no cross-instance state), Global ICL (one shared history), Routed ICL (router-partitioned ICL histories), and Routed CL (the full memory system library). We compare these conditions on normalized reward and API cost. Our contributions are: • We formulate continual learning over heterogeneous, interleaved instance sequences as a joint decision: how to represent experience and which instances should share state. • We introduce Routed Continual Learning, which for each instance selects a memory system from a fixed library and a cluster to hold its resulting state. • We show that across four language models and five matched rollouts, Routed CL improves normalized reward over both Global ICL and Routed ICL while reducing estimated API cost by 65–72% relative to Global ICL. 

## 2 Related Work  

> Analysis of algorithms and learning theory.

Before turning to agentic systems, we recall earlier lines of work that share the same central insight: An algorithm or system tuned for a single-shot task differs from one optimized holistically for a sequence of related tasks, which is arguably the more practically relevant regime. By retaining state across tasks, the system can learn from experience, amortize computational effort, transfer knowledge, and adapt to the empirical task distribution. The amortized complexity analysis of algorithms and data structures (Tarjan, 1985) considers the average cost of a sequence of operations rather than their peak complexity, establishing, for instance, competitive guarantees for the LRU caching policy and amortized guarantees for splay trees (Sleator and Tarjan, 1985a,b). Self-improving algorithms adapt to the data distribution (Ailon et al., 2006), converging to the optimal expected complexity. In online learning, samples are revealed incrementally; the main challenge is to perform competitively relative to a baseline chosen in hindsight after observing the entire sequence (Shalev-Shwartz, 2012). Continual learning concerns models that learn from a sequence of tasks or changing data distributions, aiming to adapt to new information while retaining previously acquired knowledge (Parisi et al., 2019).  

> Prompt rewriting and context augmentation.

Model performance can be improved at inference time by adapting both how a task is specified and what information is supplied to the model. Automatic Prompt Engineering (APE) shows that automatically generating task instructions can outperform manually designed prompts (Zhou et al., 2023); more recently, GEPA demonstrates that prompts can be iteratively improved through LLM-based reflection on execution trajectories (Agrawal et al., 2026). Eevee jointly optimizes a router and a set of prompts, coupling routing to prompt updates so that each prompt specializes to the inputs it receives (Xu et al., 2026). APE and GEPA optimize prompts offline, over a batch of accumulated tasks; Eevee assumes ground-truth labels for training its router. Routed Continual Learning makes online choices, selecting a memory system and a cluster for each instance as it arrives, from a fixed library whose members we do not optimize. Context augmentation enriches the model’s input with retrieved knowledge or sampled outputs (Ram et al., 2023; Luo et al., 2024). Dynamic Cheatsheet maintains a single evolving memory of strategies and solutions carried across problems (Suzgun et al., 2026). Agentic Context Engineering (ACE) grows this memory through incremental edits rather than full rewrites, which reduces the risk of context collapse that repeated rewriting can cause (Zhang et al., 2026b). Both systems accumulate one context across all problems; Routed Continual Learning instead partitions accumulated state into separate clusters and selects among them, so that unrelated problems need not share a history.  

> Memory systems.

Systems that give agents access to past experience differ mainly in what they keep: raw context, distilled facts, advice, structured procedures, or latent vectors. Routed Continual Learning is 3compatible with all of them: it picks a memory system per instance from a fixed library, and keeps each pick’s state in its own cluster. MemGPT treats the context window like physical memory, paging information in and out of external storage as the agent requests it through function calls (Packer et al., 2023), while CoEvo-Mem learns the retrieval policy itself, adjusting how memories are fetched as it refines what they contain (Ye et al., 2026). Mem0 pulls relevant facts from each trajectory and reconciles them against what it already holds, adding, revising, or deleting entries as it goes (Chhikara et al., 2025). Reflexion writes a short self-critique after a failed attempt and reads it back on the next try (Shinn et al., 2023); ExpeL abstracts insights that hold across tasks (Zhao et al., 2024); Dynamic Cheatsheet keeps a running note of strategies that have worked (Suzgun et al., 2026); ACE grows a playbook of scored bullets, editing it in small increments so earlier entries survive (Zhang et al., 2026b); and ReasoningBank mines both successes and failures for reusable reasoning strategies (Ouyang et al., 2026). Fang et al. (2026) propose trajectory-informed memory generation that groups experience by outcomes: clean successes, runs that failed and recovered, and runs that succeeded wastefully. Other systems retain something other than free-form text from past executions. Agent Workflow Memory extracts reusable workflows (Wang et al., 2025); Voyager accumulates a library of executable skills (Wang et al., 2024); MemGen maintains a latent space representation (Zhang et al., 2026a).  

> Standard harness hooks and rewriters.

Most agent frameworks already expose a point at which a message can be intercepted and modified before an agent’s own logic runs, without changing the agent itself. AutoGen’s ConversableAgent, for instance, lets a caller register hooks that fire before a reply is generated, including one that updates the agent’s state (Wu et al., 2024). Production deployments extend the same idea into guardrail and middleware layers, where an input hook inspects or rewrites a message on its way to the model and an output hook does the same to the response, again without modifying the agent’s own code. In our implementation, Context Memory Adapter attaches at exactly this point: rather than validating or filtering a message, it augments the prompt to include retrieved memory content, using the same hook mechanism these frameworks already provide for other purposes. 

## 3 Problem Formulation 

Routed continual learning addresses settings in which neither the appropriate representation of past experience nor the prior state relevant to a new instance is known in advance. We consider a causally ordered, heterogeneous stream containing interleaved instances from several source tasks, without explicit task labels. Using only the visible instance specification, memory system descriptions, and cluster summaries, the system must determine how to represent experience and which instances should share state.  

> Heterogeneous continual streams.

Continual Learning Bench (CL-Bench) defines a task as an ordered sequence of problem instances (Asawa et al., 2026). We study a setting in which instances from multiple such source tasks are interleaved into one heterogeneous stream. Let source task d ∈ { 1, . . . , D } provide instances 

xd, 1, . . . , x d,N d . The evaluated stream x1, . . . , x N , where N = PDd=1 Nd, preserves the order of instances within each source task. At position t, the system receives the visible specification of xt: its natural-language prompt and required structured response format. It does not receive an explicit task label or information about its relationship to earlier instances. Completing an instance produces an agent-visible trajectory τt containing the instance prompt, model actions, tool outputs, and feedback revealed through normal interaction. The environment also assigns reward rt

for evaluation, but does not share it with the learning system. At every decision, the system may use only information exposed by that point in the interaction.  

> Continual-learning memory systems.

We call the component of our architecture that retains experience across agentic runs a continual-learning memory system. Let M be a finite library of such systems whose implementations and allowed configuration schemas are fixed before evaluation. A memory system renders text from its state for the actor’s context and updates that state by consuming trajectories. Once cluster c,4backed by system m, has been configured, these operations are 

zt = read m(Sc,t , x t; θc), Sc,t +1 = update m(Sc,t , τ t; θc),

where Sc,t is the cluster state, θc is its cluster-specific configuration, and zt is text added to the actor’s context. Only the selected cluster’s state is updated. Multiple agents may interact with the same cluster concurrently; 

read and update operations are atomic. Some memory systems require task-specific bindings between the task schema and generic state. For those systems, Context Memory Adapter derives the cluster-specific adapter configuration θc from prior runs; other systems use fixed interfaces. Memory systems interact with the agent through context; they neither act in the environment nor modify its parameters.  

> Stateful routing.

The system must choose both a learning mechanism and the cluster whose state the current trajectory will read and update. A cluster c is an isolated instance of one memory system, with its own state and an immutable description δc of which instances should share that state; multiple clusters may use the same system. Let Ct be the clusters available before instance t. Given xt, memory system descriptions, and summaries Σ( Ct), the router π chooses either reuse (c) for c ∈ Ct or create (m, δ ) for m ∈ M . The choice remains fixed during the instance. New clusters begin from initial state. Reusing too broadly can mix unrelated state, while unnecessary creation can prevent useful transfer. Thus, routing jointly selects a memory system and a cluster: Global ICL uses one ICL state, Routed ICL selects among ICL clusters, and Routed CL selects both. 

## 4 System Components 

Routed CL comprises an LLM router, isolated stateful clusters, a fixed memory-system library, and Context Memory Adapter. The memory system determines how experience is retained, while the cluster determines which instances share state. Upon receiving an instance, the router chooses an existing cluster or creates a new one; the cluster assignment stays static throughout the instance execution. Figure 1 summarizes this lifecycle. 

4.1 Router and Stateful Clusters 

The router implements π with one structured-output LLM call before each instance. It receives the visible prompt and response schema, each memory system’s declared learning behavior, and, for every cluster, only its identifier, memory-system type, immutable description, and completed-trajectory count. It cannot inspect raw trajectories, internal memory-system state, or hidden conversation state from earlier routing calls. The router is prompted rather than trained. Its prompt and memory-system library remain fixed during evaluation, and it receives no source-task labels or rewards. 

4.2 Frozen Memory-System Library 

Mechanism selection is meaningful only when memory systems encode different assumptions about reusable information. We use five systems spanning three representation families (Table 2). The router chooses among the five concrete systems; the families only organize the presentation and do not create another routing layer. These systems are examples rather than a canonical taxonomy. The library was selected during exploratory development on CL-Bench and frozen before confirmatory evaluation; our experiments test selection and configuration within it, not the synthesis of new memory-system families. 5Figure 1 Overview of Routed Continual Learning. > In-context Learning (ICL).

Each ICL cluster retains visible prompts, actor responses, and feedback as an ordered history, discarding the oldest messages only at the model context limit. Its only abstraction is the router-defined cluster boundary.  

> ReasoningBank.

We adapt ReasoningBank (Ouyang et al., 2026) to the Context Memory Adapter interface. After each completed visible trajectory, the same backbone model judges whether the attempt succeeded or failed and extracts up to three structured memory items capturing reusable strategies or failure-avoidance lessons. Before a later instance, the system retrieves the memories associated with the most similar prior request and injects them at the instance boundary. Our adaptation uses no hidden rewards, uses frozen local embeddings, and does not use ReasoningBank’s test-time-scaling extension.  

> Numerical memory systems.

The numerical systems’ statistical libraries consume generic typed records and contain no CL-Bench task names, task-specific fields, prompts, or scoring logic. Hierarchical Regression and 6Hierarchical Discrete-Event State use PyMC (Abril-Pla et al., 2023), and Persistent-Entity State uses River’s Bayesian linear regression (Montiel et al., 2021); task semantics enter through adapter bindings and extracted evidence. Appendix B.2 provides implementation details. 

4.3 Context Memory Adapter 

Context Memory Adapter configures cluster-specific adapters when a memory system requires task-specific bindings, and exposes the selected cluster’s state through the actor’s context; Appendix B.1 describes the adapter lifecycle and validation procedure. An adapter supplies only schema-bounded semantic bindings and permitted configuration choices, never parser code or task answers, so online adaptation is limited to routing, bounded configuration, and state updates within a frozen library. To isolate continual learning from task execution, Context Memory Adapter never acts in the environment or submits an answer. Before the first actor turn, it may inject a budget-bounded advisory alongside the unchanged prompt; the advisory remains in the within-instance history. The selected cluster is updated only with information from its assigned trajectory. The same actor retains its original tools and response schema, and only its response is scored. Context Memory Adapter cannot access hidden tests or evaluation rewards, so memory affects behavior solely through context. 

## 5 Experiments  

> Benchmark and heterogeneous stream.

Routed Continual Learning is intended for streams where prior experience can help, but the system is not told which memory system to use or which instances should share state. Evaluating the source tasks separately would test individual learning mechanisms but not the routing problem. We therefore construct a heterogeneous stream by interleaving all 301 instances from the six CL-Bench tasks (Asawa et al., 2026) with 97 Banking Knowledge instances from τ 3-Bench (Shi et al., 2026), for 398 instances total. CL-Bench contributes six tasks spanning distinct interfaces, reward functions, and forms of reusable cross-instance information. τ 3-Bench adds multi-turn customer-service interactions requiring policy-grounded reasoning, knowledge retrieval, and tool use. The source tasks are summarized in Table 3. For each rollout, we form one heterogeneous stream by randomly interleaving the seven source-task sequences while preserving each source task’s canonical order. All systems are evaluated on the same set of five rollouts. Source-task labels used for analysis are not supplied to the router or agents. Native prompts, tools, response schemas, feedback, and reward functions remain visible, so routing may use observable task structure.  

> Compared systems.

We compare four staged conditions with matched actors, task interfaces, budgets, model limits, and stream order. Stateless ICL resets after each instance; Global ICL shares one history across the stream; Routed ICL partitions that history among dynamically defined clusters; and Routed CL also selects among the five memory systems in Table 2. Configurable clusters derive their adapters from observable warm-up experience on first reuse. All ICL histories use a 100K-token context budget, applied stream-wide for Global ICL and independently per cluster for the routed conditions. Separately, we evaluate our ReasoningBank adaptation under two fixed-system configurations. Global RB maintains one memory store across the stream, whereas Routed RB maintains one store per router-selected cluster. This comparison uses three matched rollouts and is reported in Appendix C.2. We also evaluate Ground-truth assignment, a privileged diagnostic that uses source-task identity and a fixed memory-system and cluster mapping chosen during exploratory development and frozen before confirmatory evaluation.  

> Models and repetitions.

To assess whether our findings hold across model families, we evaluate four language models: Claude Opus 4.7, Claude Opus 5, GPT-5.6 Sol, and Gemini 3.7 Flash. Within each condition, every model-mediated role uses the evaluated model: the actor and any router, adapter configurator, typed extractor, ReasoningBank judge, or memory writer required by that condition. The fixed τ 3-Bench user simulator and evaluator are benchmark components shared across conditions. To estimate variability from stream ordering and stochastic model outputs, we evaluate each model–condition pair over five complete rollouts. Because persistent state couples later instances to earlier behavior, the 7complete rollout is the unit of replication. For each language model, we summarize the five paired differences between methods.  

> Evaluation protocol.

We froze all method components before confirmatory evaluation. Matched conditions receive the same task interface, feedback, budgets, and model limits; Appendix A.5 gives the complete specification. All task-derived evidence comes from the native task interface. The four staged conditions receive no source-task identities, privileged assignments, hidden tests, or held-out rewards; Ground-truth assignment receives only source-task identity. To prevent cross-instance leakage, we reset Sales Prediction’s writable workspace and expose Codebase Adaptation actors only to base-commit snapshots, with regression tests reserved for evaluation. These changes apply to every method but make the affected results not directly comparable to historical CL-Bench runs (Appendices A.4.1 and A.4.2). Resource totals include every model call. Appendix D reproduces the fixed prompts and memory-system descriptions.  

> Metrics.

We report normalized reward as the primary metric. For the six CL-Bench tasks, the external stateless reference published with CL-Bench maps to 0 and the task maximum to 1; scores below the reference are negative. τ 3-Bench instead uses its native [0 , 1] reward, and all seven source tasks are weighted equally. Our secondary metric, stateless-reference gain, compares each method with Stateless ICL using the same language model and matched interleaving: 0 denotes matched Stateless ICL performance and 1 the task maximum. Appendix A.6 provides the complete definitions. We estimate API cost for every model call using a frozen, dated public list-price schedule that accounts for token caching. Appendix A.7 gives the complete accounting policy. 

## 6 Results and Analysis 

We demonstrate that Routed Continual Learning sharply improves aggregate reward over Stateless ICL and globally shared memory baselines, while costing substantially less than Global ICL. Detailed task- and model-level breakdowns are deferred to the appendix.  

> Global ICL loses its advantage under heterogeneous interleaving.

CL-Bench found naïve ICL strongest when its tasks were evaluated as separate homogeneous streams (Asawa et al., 2026). In our interleaving, mean stateless-reference gain rises from 0.015 for Global ICL to 0.222 for Routed ICL and 0.280 for Routed CL. Figure 4 shows how this pattern develops over the stream. For Opus 4.7, Global ICL helps early but its gain declines later; for Opus 5, it remains worse than Stateless ICL throughout. The routed methods show larger gains later in the stream.  

> Clustering helps ICL but does not consistently help ReasoningBank.

Routed ICL exceeds Global ICL by 0.117– 0.241 normalized-reward points across models. By contrast, routing ReasoningBank produces no consistent reward gain and raises mean cost by 8–29% (Figure 3). This may be because ICL exposes an entire cluster history, whereas ReasoningBank already retrieves memories selectively by request similarity.  

> Memory-system selection adds task-specific gains.

Routed CL adds another 0.002–0.076 normalized-reward points. Gemini’s mean improvement is only 0.002 but is positive in four of five paired rollouts; the other models show larger gains. Table 5 reports the paired results. At the task level, Routed CL improves over Routed ICL on Cohort and τ 3-Bench for every model and on Spectrum for three of four models, while reducing cost on Sales and Spectrum for every model and on Cohort for three of four models (Figures 5 and 6). On Sales, for example, Opus 5 maintains essentially unchanged reward at 0.34 × the cost.  

> Routed CL improves the reward–cost trade-off.

Among the four staged conditions, Routed CL lies on the empirical reward–cost Pareto frontier for every model (Figure 2). It achieves higher reward than Global ICL at 65–72% lower cost and costs 25–33% less than Routed ICL on three models; on Opus 4.7, it costs 5% more for a 0.034 reward gain. ## 7 Conclusion and Future Work 

Agents learning across heterogeneous tasks must decide how to represent and group relevant experiences. We introduce Routed Continual Learning, which makes these decisions jointly by selecting a memory system and a stateful cluster for each agent run. On our heterogeneous stream spanning CL-Bench and τ 3-Bench, Routed CL achieves higher reward than both Global ICL and Routed ICL for all four language models at substantial cost reductions (e.g., saving 65–72% compared to Global ICL). Notably, Global ICL, found to be the strongest performing system by the original CL-Bench when evaluated on isolated tasks, gains almost nothing (mean +0.015 in aggregated normalized reward) relative to the stateless condition when the tasks are interleaved. These results support treating continual learning as a routing problem that jointly determines how experience is represented and which instances share state. Our experiments process instances sequentially, and each rollout uses one language model as the actor and for all model-mediated memory-system roles. Although the architecture isolates cluster state and defines atomic reads and writes, we do not evaluate simultaneous updates, stale reads, or cross-model reuse of cluster state. These remain important tests for distributed deployment. Future work could study richer interactions between components: reading from multiple clusters for a single 9instance, and updating several clusters or memory-system representations from the resulting trajectory, while controlling cost and interference.

## Ethics Statement 

Our experiments use previously released benchmarks and simulated interactions. The motivating example in the Introduction highlights a capability risk: pooling experience can enable a group of agents to achieve outcomes beyond the capabilities of any individual agent, including in security-sensitive settings. Persistent state can also propagate sensitive, erroneous, or adversarial information. Deployments should therefore enforce task- and user-level authorization, provenance, retention and deletion policies, and isolation across security boundaries, while assessing the capabilities of the combined system rather than only its component models.

A.2 Heterogeneous Stream Construction 

Feedback produced by a source task that advances automatically is buffered and delivered when that source task is next activated. This preserves its causal position without attaching it to another task’s trajectory. 

A.3 Implementation and Rollout Configuration 

The headline table aggregates five matched stream seeds (42–46) per model. Ground-truth assignment also reports five matched rollouts for every model. 

A.4 Benchmark Protocol Modifications 

A.4.1 Sales Prediction Workspace Isolation 

The released Sales Prediction runtime preserves its writable execution environment across instances and explicitly encourages the actor to save code, models, and notes under /app . This provides a general-purpose cross-instance storage channel outside the continual-learning system being evaluated. For every method in our evaluation, we instead discard the Sales container at each instance boundary and start a fresh one. The harness then reconstructs the current instance’s data room. Benchmark-provided observations, including the currently visible historical data and previous-round feedback, remain available through the native task interface; actor-created files do not persist. The task instructions are changed accordingly so that they accurately describe the execution environment. This isolation strengthens attribution to the evaluated continual-learning system but makes our Sales results not strictly protocol-equivalent to historical CL-Bench results. 

A.4.2 Codebase Adaptation Isolation 

CL-Bench describes Codebase Adaptation as beginning from an issue’s base commit and evaluating the submitted patch against hidden regression tests. The CL-Bench 1.0 release commit ( a7ddacb ) did not fully 13 enforce this separation. Actor workspaces retained the shared image’s Git database, from which later fix commits could be inspected, and the official regression-test patch was applied before the actor began interacting with the repository. Our hardened actor initialization first restores the base commit and removes untracked and ignored build artifacts. It then removes the inherited Git database and creates a fresh repository containing only a single snapshot commit. The official regression-test patch is never applied in the actor container. Evaluation remains unchanged: after submission, a separate evaluator reconstructs the base tree, applies the hidden regression-test patch and the actor’s submitted patch, and runs the designated tests. The runtime records whether actor sanitization was enabled and whether the test patch was visible for every run. This change matches the benchmark’s stated hidden-test protocol but differs from the released runtime used by historical runs. Aggregate results alone do not show whether a historical agent used either leakage channel. We therefore report our Code results as sanitized evaluations and avoid treating comparisons with historical Code scores as strictly equivalent. 

A.5 Frozen Evaluation Contract 

Before confirmatory runs, we freeze the router prompt and memory-system descriptions; all memory-system implementations; the prompts and schemas used for adapter configuration, typed extraction, ReasoningBank self-judgment, and memory extraction; statistical defaults; the Ground-truth assignment mapping; and the task harness and scoring code. We do not revise these components in response to confirmatory outcomes. Within each matched comparison, systems receive the same native instance prompts, tools, response schemas, visible feedback, action budgets, and actor context-window and response limits. When deciding how much retained ICL history fits, the runtime reserves 500 tokens within each configured 100,000-token budget. If the remaining history exceeds that allowance, it removes the oldest retained messages first. Global ICL applies this policy to one stream-wide history; Routed ICL and ICL clusters selected by Routed CL apply it independently per cluster. Within each model–condition pair, the same evaluated model serves as the actor and, where applicable, powers selection, adapter configuration, typed extraction, ReasoningBank self-judgment, and memory extraction. Resource measurements include all of these calls.

## B Additional Method Details 

B.1 Adapter Validation and Evidence Repair 

ICL uses a fixed interface, whereas ReasoningBank and the numerical memory systems use cluster-specific adapters. ReasoningBank’s adapter identifies the boundary between a repeated prompt wrapper and its changing request; its memory induction and retrieval behavior remain fixed. Numerical adapters instead bind visible task fields to roles such as targets, identities, groups, and time, and choose among the configuration options permitted by each memory system’s fixed typed schema. A configurable cluster’s first instance receives the original prompt unchanged. Its completed trajectory becomes the warm-up example, and adapter configuration occurs only if the cluster is subsequently reused. On the first reuse of a configurable numerical cluster, Context Memory Adapter configures its adapter from the completed warm-up trajectory together with the current visible prompt and response schema. A fresh memory-system runtime replays the warm-up trajectory, prepares the current instance, and checks the resulting state and bindings. If validation fails, Context Memory Adapter returns the deterministic error to the configuring LLM, which may return one complete repair. A second failure terminates adapter configuration rather than accepting an unvalidated configuration. Successful validation initializes the memory-system state from the warm-up trajectory, and the resulting adapter configuration is frozen for the lifetime of the cluster. After configuration, numerical memory systems invoke a typed extractor whenever new evidence becomes available. The extractor receives one complete visible event, such as the current query or a completed trajectory, and emits the records required by the configured adapter. Memory-system-specific validators check their schema, internal consistency, and exact provenance against the source event. An invalid batch receives at most one validation-informed repair; persistent failure is reported rather than accepted or silently truncated. The extractor does not fit the statistical model, associate latent entities, or generate predictions. Those operations remain inside the fixed memory-system runtime. 

B.2 Numerical Memory-System Implementations 

Hierarchical Regression. This memory system models repeated numerical outcomes indexed by stable keys, categorical factors, and optionally time. Its adapter chooses the target family and temporal structure, while the extractor establishes consistent dimension names and emits requested prediction points and visible realized outcomes. The runtime pools accumulated evidence through hierarchical regression implemented in PyMC, with global, key-specific, factor, and temporal terms, refitting as new outcomes arrive. Once an estimate has repeated support, it renders a compact forecast with its fitted observation-noise estimate and recent observations; the actor may still revise that estimate using the current environment. 

Hierarchical Discrete-Event State. This memory system models monotone event-free probabilities over ordered intervals through conditional hazards. Its adapter chooses the number of intervals and stable categorical context roles; the extractor maps visible aggregate measurements to target identities, reusable features, context levels, probability curves, and support weights. A hierarchical discrete-hazard model implemented in PyMC pools an interval-specific baseline with feature-, entity-, and context-level effects, then converts predicted hazards back into valid monotone curves. The runtime ingests visible aggregates from completed trajectories and renders the resulting curves for requested targets as advisory context on subsequent instances. 15 Persistent-Entity State. This memory system handles variable-size, unordered measurement sets whose underlying entities may persist without stable identifiers. Its adapter identifies the numerical coordinates that define entity identity, visible measurements that determine their uncertainty scales, values to predict, target family, and any optional query window. The extractor copies each visible measurement set into typed records without performing association. The runtime links observations through uncertainty-aware matching, updates persistent identity estimates and online Bayesian regressions, and renders current or previously confirmed entities relevant to the query as advisory context.

Line wrapping and runtime-value placeholders are normalized, but the fixed wording is otherwise verbatim. Text in angle brackets denotes visible data inserted at runtime. Stateless ICL and Global ICL add no system instruction to the native benchmark prompt. Configure the selected generic memory operator from visible task syntax. Configure only choices admitted by the response schema. D.2.5 Persistent-entity contract 

Operator: persistent_entity_state_v1 Input contract: Raw numeric identity coordinates, natural scale references, numeric values, optional visible bounds, step index, and provenance.
