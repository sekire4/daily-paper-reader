## Abstract 

Long-running agents rely on memory of their past interactions for task state, such as what has been completed and which conditions still hold. Such state is usually a derived state. No record states it, and it must be computed by rules from multiple records of an evolving history. Existing memory benchmarks score only the final answer, with no reference for the intermediate states behind it. A wrong answer therefore cannot be traced to the state that was missed, and a state that silently became outdated goes undetected. We present MemDerive , a diagnostic benchmark for agent memory over evolving data. It specifies each scenario symbolically, derives exact gold answers with Datalog, records the gold derivation DAG and the supporting events of every query, and renders the history in natural language with fictional entities and distractors. Its 10 scenarios contain 4,692 events and 1,503 queries whose difficulty varies along access, evolution, and composition. On this ground truth, MemDerive evaluates answer reliability, diagnoses failures by probing the nodes of the gold derivation DAG, and tracks whether answers stay correct as events arrive. Our evaluation of four memory systems reveals failures that final-answer benchmarks hide. On derived state, every memory system falls behind simple BM25 retrieval, although the same answer model reaches 96.01 % when given the supporting events. Most failures are ungathered, as a system holds the missing intermediate state but does not retrieve it for the question that needs it. Memory systems also rarely propagate implicit changes, which no new record states. These results suggest three principles for memory design. Gather inputs along the derivation, store rules with their versions, and maintain derived states through recorded dependencies.

We call a fact that no record states but that follows from several records by rules a derived state , and a question whose answer is a derived state a state question .The status of a task is a typical derived state. Like the result of a view over database tables, a derived state is computed from the history arXiv:2610.25373v1 [cs.DB] 18 Oct 2026 rather than stored in it. Here, however, the base data is natural language, and the view is defined only when a question arrives. Derived state is hard for memory systems. The records that support it rarely share words with the question and have low em-bedding similarity to it. They matter only in combination, and together they can outnumber any retrieval budget. A derived state is usually composed from intermediate states layer by layer, so one wrong intermediate state corrupts every state above it. It can also become stale without any record saying so. A later record that Nate entered a Chess tournament would remove Chess from the answer, although it never mentions the games he could play to relax. These properties affect every way of building memory, whether a system retrieves raw records for each question, extracts and stores facts as events arrive, or searches and reasons over the history when a question arrives. The bottleneck is therefore obtaining the intermediate states, not combining them, and an evaluation that scores only final answers cannot see it. Existing benchmarks were not designed to expose this failure. LoCoMo and LongMemEval test recall, temporal and multi-session reasoning, and knowledge updates over long conversations [30, 48]. StateMemBench separates current from superseded answers [13], and MemTrace audits how evidence is reached and used [29]. These benchmarks judge the final answer. Their histories are written text without executable semantics, so they cannot supply the correct value of an intermediate state, and a wrong answer cannot be traced to the step that failed (Table 6). Their updates are explicit, since a new record revises a fact and states its new value. A derived state also changes implicitly, when a fact it depends on changes and no record mentions the state. Rankings on these benchmarks therefore do not carry over to derived state. On LongMemEval, Mem0 reaches 84.00 % and exceeds BM25 at 78.60 %, yet on derived state every memory system falls behind BM25 .

Derivations as evidence. For each query, MemDerive records a gold derivation DAG that links the an-swer through its intermediate states to the events, and the witnesses, the minimal sets of events that support the answer. Second, most failures are ungathered . The system answers a missing intermediate state correctly when asked about it directly, but does not retrieve it for the question that needs it. ## 2.3 Gold Derivations and Witnesses 

An answer alone cannot show which inputs a system used or where it went wrong. MemDerive therefore records, for every query, how its gold answer follows from the history. 

Definition 5 (Gold derivation DAG) . The gold derivation DAG 

G𝑞 of query 𝑞 is a finite directed acyclic graph whose root is the target of 𝑞 . Its inner nodes are the derived states on which the root depends, called intermediate states , together with the resolved facts and rules used to derive the root. Its leaves are the events that assert these facts and declare these rules. Each edge points from a node to an input it needs, called a child . When the answer is unknown , a leaf marks the missing fact instead of an event. A shared input can serve several parents, so the structure is a DAG rather than a tree. The height of G𝑞 is the length of its longest path from the root, and its width is the largest number of nodes at the same depth. Height measures how deep a derivation is, and width measures how many inputs it combines at one level. Because every intermediate state is a node with a known gold state, an answer can be checked step by step rather than only at the root.

is the set of events that contribute to some derivation of 𝑧 (𝑞 ). A 

witness of 𝑞 is a minimal subset 𝑊 ⊆ 𝑆 (𝑞 ) from which 𝑧 (𝑞 ) can be derived, and W ( 𝑞 ) denotes the set of all witnesses of 𝑞 .A query can have several witnesses, because several events can assert the same fact. The definition of a witness follows minimal why-provenance [6]. An event outside 𝑆 (𝑞 ) whose record resembles relevant information is a distractor for 𝑞 .

## 2.5 Implications for Memory Systems and Evaluation 

A memory system can supply derived state in three ways, and the four characteristics confront each way with a different main problem. 

Retrieval of records. The system retrieves the records most similar to the query, possibly through a graph or tree index, and leaves the derivation to a language model [11, 17, 38]. Because no record states the derived state (Property 1), the records that support it share few keywords with the query and are semantically distant from it. They are also relevant only together, and their number can exceed any fixed retrieval budget (Property 2). Ranking records by similarity to the query can therefore miss the support for structural reasons, not merely for lack of keywords. 

Materialization at ingestion. The system derives and stores states as events arrive [19, 50, 54]. Derived state far outnumbers recorded facts, because intermediate states combine across entities, periods, and categories (Property 3). The system can therefore neither store every derived state nor know in advance which ones will be queried. An event can also invalidate stored states that it never mentions (Property 4), so the system must find those states and re-derive them [16, 32], and stored state can lag behind the history. 

Derivation at query time. The system searches and reasons when a query arrives, as agentic search does [44]. For every query it must gather the full support and combine every layer of intermediate states (Properties 2 and 3), and it recomputes intermediate states that many queries share. Each search and derivation step involves calls to a language model, so answers come with high latency and high token consumption. 

Implications for evaluation. Practical systems mix these strate-gies, and they place the computation in different components with different representations. An evaluation can therefore observe a memory system under test (SUT) only from the outside, through the answers it gives to queries. MemDerive adopts this black-box view and asks three evaluation questions. 

Q1. Answer reliability (§4.1). Does the SUT answer correctly, with citations to its support? Missed support shows up here first. 

Q2. Failure diagnosis (§4.2). Where does a wrong answer first depart from the gold derivation, and why? The strategies run into problems at different steps. 

Q3. Derived-state maintenance (§4.3). Does a correct answer follow the history as it grows, and what does the SUT pay at ingestion and at query time? Stored state can lag, and the strategies place their cost at different stages. 

## 3 Benchmark Construction 

MemDerive builds each scenario in three steps, shown in Figure 4. A symbolic specification (Section 3.1) is evaluated into gold (Sec-tion 3.2) and then rendered into natural language (Section 3.3). Difficulty control shapes the specification (Section 3.4). 

## 3.1 Scenario Specification 

Gold for derived state cannot be annotated reliably by hand, because an answer can depend on many events and on information being absent. MemDerive therefore specifies each scenario symbolically, as events with actions and queries with targets and cutoffs. Nat-ural language enters only at rendering, so the specification alone determines every gold answer. 

Scenarios and domains. A scenario is one evolving history together with its rules and queries, and a domain is a family of scenarios that share a workflow. The suite contains 10 scenarios in 3 domains. 

TripOps covers travel booking and reimbursement, ShopOps cov-ers orders, returns, and spending rules, and EduOps covers degree audits over prerequisite chains. Each scenario adds its own rules, corrections, and cancellations to the workflow of its domain. 

Query targets. Query targets are built from operators grouped into five families, and one target can combine several families. Each family exercises a different construct of the derivation program, listed in Table 2. Appendix A lists all operators. Because each con-struct demands a different computation from an SUT, success on one family says little about another. Table 2 confirms that the fami-lies stress different workload dimensions. Each query counts once there, under the family of its main operation. Witness is the mean witness size in events, Obs. the share of queries whose gold deriva-tion excludes an obsolete version, and height and width are means over the gold derivation DAGs. 

## 3.2 Reference Evaluation 

The reference evaluator is an executable implementation of the derivation program of Section 2.2. One computation produces the gold answer, the gold derivation DAG, and the witnesses of a query. While computing the answer, the evaluator adds a node to G𝑞 for everything it derives, reads, or checks, together with an edge to each input it uses. Witnesses are extracted from the leaves of G𝑞 

and of alternative derivations, and each is checked to be minimal. Because all gold objects come from this one computation, every node of G𝑞 has a known correct state, which Q2 needs, and gold can be recomputed at any cutoff, which Q3 needs. 

## 3.3 Natural-Language Rendering 

Rendering produces the record 𝑟 𝑒 of each event from its actions 𝐴 𝑒 

and turns each query target into a natural-language question. The specification determines what is correct, and rendering determines how far an SUT must reach from the question to the records that justify the answer. 

Faithful records. A record carries every argument of its action, so its fact is recoverable from the text. No record states a derived state, so Property 1 holds by construction. 

Entity virtualization. A model that recognizes an entity can an-swer from pretrained knowledge and skip the records that map the entity to a category. Rendering therefore invents every recognizable entity, including people, organizations, places, products, courses, and currencies, so that every mapping must come from the history. 

Access in rendering. Questions use the vocabulary of derived predicates, and they often refer to an entity through an associated event, a date, or a place rather than its identifier. For some queries, the key terms of the question appear in distractor records, which leave the answer unchanged, but in none of the supporting records.

## 3.4 Difficulty Control 

When generating a scenario, the generator sets how demanding each query is in each workload dimension [12]. Queries therefore spread over a range of difficulty in every dimension, and the dimen-sion measures of Section 2.4 record where each query falls. 

Access. Support is harder to gather when its events are far apart and do not resemble the question. Through dispersion , the generator spreads the events of one witness over the history, and rendering adds the lexical gaps, indirect references, and distractors of Sec-tion 3.3. 

Evolution. Current versions are harder to identify when facts are revised often and obsolete records appear late. The generator builds 

update chains that revise a fact several times and places obsolete records late in the history. 

Composition. A query is harder to compose when it combines more kinds of reasoning. The generator varies this number, the 

composition degree , from a single operation to combinations of version resolution, rule application, and checking that a collection is complete. 

Quota bands. Target shares of operator families, witness sizes, and answer types keep the workload off the easiest cases.

## 4 Evaluation Methodology 

The protocol follows the black-box view of Section 2.5. For every query, an SUT returns a context , the text it supplies for answering, and one answer model shared by all SUTs turns it into an answer, an answerability label, and cited events. Every measurement below is obtained by posing questions to the SUT.

## 4.2 Q2: Failure Diagnosis 

Q2 asks where a wrong answer arises and why. Because SUTs are black boxes, diagnosis cannot inspect their internal state. It can only ask further questions, and G𝑞 tells it which questions to ask and what their correct answers are. 

4.2.1 Failure Classes. A wrong answer arises at some state of the derivation. The SUT may be able to produce that state but fail to gather it when the derivation needs it, or it may fail to produce the state even when asked for it directly. Each case calls for a different repair, so MemDerive distinguishes three failure classes .

• A state is ungathered when the SUT returns it when asked for it directly, but the request for the state that needs it does not gather it. 

• A resolved fact or rule is unretrievable when the SUT cannot return it even when asked for it directly. 

• A derived state is misderived when the SUT derives it wrongly even when asked for it directly, although its inputs are gathered. The classes follow the workload dimensions of Section 2.4. Ungath-ered states are failures of Access. Unretrievable facts arise at Access or Evolution, depending on whether the fact has a superseded ver-sion, and misderived states arise at Composition. 

4.2.2 State Probes. Any node of G𝑞 that holds a resolved fact, a rule, or a derived state can be asked about directly. 

Definition 7 (State probe) . A state probe of a node 𝑣 in G𝑞 is a natural-language question at the cutoff of 𝑞 whose gold answer is the state of 𝑣 .Probes are rendered from fixed templates, and their gold answers come from the reference evaluator, so no language model writes or grades them. The suite contains 2,818 probes for 1,029 queries. The probed nodes, connected by the dependencies of G𝑞 , form the 

diagnostic DAG D𝑞 . Every SUT answers the same probes for the same queries in the same order. 

Two contexts. Each probe is answered under two contexts. In the inherited context, the answer model receives the context that the SUT returned for the question of a parent node, which for the children of the root 𝑟 𝑞 is the original query. This reproduces what the derivation had available when it needed the state. For the root, the inherited answer is the original answer. In the targeted context, the probe itself is sent to the SUT as a new query, and the answer model receives the context returned for it. This tests whether the SUT can return the information when asked for it directly. Let 𝑡 𝑠 (𝑣 ) ∈ { 0, 1}

indicate whether SUT 𝑠 answers the probe of 𝑣 correctly in the targeted context. Because a node can have several parents, inherited correctness belongs to an edge. For a child 𝑢 of 𝑣 , 𝑖 𝑠 (𝑢 | 𝑣 ) ∈ { 0, 1}

indicates whether 𝑠 answers the probe of 𝑢 correctly in the context returned for the question of 𝑣 , and 𝑖 𝑠 (𝑟 𝑞 ) indicates whether the original answer is correct. 

4.2.3 Failure Localization. A wrong probe answer does not by itself locate a failure, because an error can propagate upward, and a node computed correctly from a wrong input is wrong as well. The failure arises at a node that is wrong although all of its inputs are right. Such nodes mark where an SUT first departs from the gold derivation, and together they form its failure frontier . Localization uses the inherited context, because it shows whether each request gathered the states it needed. 

Definition 8 (Failure frontier) . A probed node 𝑣 lies on the failure frontier of SUT 𝑠 when some path 𝑟 𝑞 = 𝑣 0, . . . , 𝑣 𝑘 = 𝑣 in D𝑞 has

Complementary measures. Four further measures complement the two rates. 

• Stale-answer rate. The share of changed transitions at which the SUT still returns the previous gold answer. It distinguishes a missed update from a wrong one.

## 5 Experiments 5.1 Experimental Setup 

SUTs and reference conditions. The SUTs are four memory sys-tems and two raw-retrieval baselines. The memory systems are 

Mem0 [8], Cognee [31], LightMem [14], and MemoryOS [22]. They cover extracted-fact stores, graph-oriented memory, and hierarchi-cal organizations. The baselines rank the history with BM25 or with dense embeddings ( Embed ) and return the top items. They retrieve session documents by default, and figures mark session-level and event-level variants as -S and -E where both appear. Three refer-ence conditions bound the results. Closed-Book receives no his-tory, Full-Context receives the whole visible history, and Oracle 

receives the support 𝑆 (𝑞 ), all events that contribute to the answer. 

Models and defaults. The answer model is GPT-5.6 Sol with rea-soning disabled and temperature zero. All SUTs share our answer and judge prompts, released with the artifact. The judge prompt is stricter than those used in the original benchmarks, so scores can differ from previously reported ones. Memory systems that extract memories at ingestion use GPT-5.6 Luna as the extraction model. Dense retrieval uses Qwen3-Embedding-0.6B [52]. Every SUT re-turns 𝑘 = 15 items per query. Mem0 and LightMem do not return event identifiers, so their citations are mapped to events through the recorded memory attribution. 

Query sets. The main comparison asks all 1,503 queries of the 10 scenarios at the end of each history, over 4,692 events. The context-budget comparison caps the context at 500 to 16K tokens on 400 queries. Diagnosis probes the complete diagnostic DAGs of a subset of queries from every scenario, the diagnostic queries. Maintenance tracks 132 queries at five checkpoints, at 20%, 40%, 60%, 80%, and 100% of each history. Transition analysis uses the tracked queries whose gold is never unknown , which contain 106 changed transitions. For comparison, the SUTs are also evaluated on LoCoMo and LongMemEval [30, 48] with their official question sets. The artifact also records model settings, per-query outputs, and the inputs of every figure.

Figure 12(a) compares the targeted and inherited contexts on every edge of D𝑞 ,by how many levels the child lies above the deepest level of D𝑞 .The shaded distance holds a single query. The two contexts agree on the deepest level, which holds facts read from events. One level above, they separate. The targeted context answers 86–94% of these states for BM25 , Cognee , and Mem0 , whereas the inherited context answers only 54–74%. Each input can be retrieved alone, but the request for the derived state does not bring all of them together, as Property 2 predicts. 

The recoveries confirm the classes. Self-evidence recovery raises accuracy by up to 30.0 points (Figure 12(b)). It repairs 33–52% of the wrong answers of Mem0 , Cognee , and MemoryOS , whose failures are mostly ungathered, but only 9% for LightMem . Gold-evidence recovery repairs 39–65% of memory-system failures and adds 39 points for LightMem , so its wrong evidence is load-bearing. The failures that remain lie in how states are combined. 

An early correct state does not ensure recovery. Figure 12(c) relates how close to the root the first correct state of a failed query lies to the accuracy after self-evidence recovery. BM25 finds its first correct state 1.38 levels below the root on average and recovers to 80.00%, whereas LightMem finds it 2.52 levels below and recovers 

10 to 47.50%. An SUT whose correct states lie closer to the root leaves fewer levels to rebuild. Recovery still needs correct states on every branch, so one correct state is not enough. 

Finding 2. Most failures of memory systems are ungathered. The SUT can return the missing state when asked for it directly, but the request for the state that needs it does not gather it, and self-evidence recovery raises their accuracy by up to 30.0 points. LightMem instead loses evi-dence at ingestion, so only gold evidence repairs a substantial share of its failures. 

## 5.4 Q3: Derived-State Maintenance 

Refresh lags preservation. Figure 13(a) reports both rates of Equation 3. Memory systems preserve 91.03–92.86% of unaffected answers but refresh only 35.71–63.64% of changed ones. LightMem 

refreshes least and Mem0 most. 

Implicit changes are refreshed least. Of the 106 changed transi-tions, 18 are explicit and 88 are implicit. Memory systems refresh 82.4% of explicit changes but only 41.1% of implicit ones (Table 5). Raw retrieval refreshes 83.3% and 63.1%. Memory systems thus update what a new record states but rarely propagate a change through dependencies, which is the lag that Section 2.5 attributes to materialization. Raw retrieval derives at query time and loses less. Stale answers point the same way. Memory systems repeat the previous answer mostly after implicit changes, whereas raw re-trieval goes stale mostly after explicit ones, because the superseded record still matches the query. 

Missed updates persist. Figure 13(b) adds the regression and stale-answer rates. Memory systems repeat the previous gold answer in 9.43–18.87% of changed transitions. Recovery delay shows that, by the last checkpoint, 66–79 of the 106 changes remain unrecovered for memory systems, against 1 for Oracle .

Few answers stay correct throughout. Figure 14 reports contin-uous correctness. Memory systems fall from 28.03–65.15% at the first checkpoint to 16.67–41.67% at the last, raw retrieval ends near 43.18%, and Oracle keeps 93.18%. 

Finding 3. Memory systems preserve unchanged answers well but refresh only 41.1% of implicit changes, half their rate on explicit ones, so few tracked queries stay correct at every checkpoint.

## 6 Discussion 6.1 Lessons for Memory Systems 

Read together, the results of Q1 to Q3 and the cost measurements yield five lessons for the design of memory systems. 

L1: The bottleneck is gathering, not storage. Asked directly, 

BM25 , Cognee , and Mem0 return 86–94 % of the states one level above the evidence, but only 54–74 % within the context of the request that needs them, and most failures are ungathered. A memory should therefore split a request for a derived state along its derivation into requests for its inputs. Self-evidence recovery, which does exactly this, raises accuracy by up to 30.0 points. 

L2: Rules must be stored as first-class objects. Asked directly, 

Mem0 returns 17 % of rules and LightMem 8 %. Fact-centric extrac-tion summarizes policies and exceptions away, although every de-rived state applies them. Rules should be stored with their versions, like facts. 

L3: Once gathering works, composition becomes the bottle-neck. BM25 gathers evidence most completely, yet 38 % of its wrong

## 6.2 Scope 

Executable scenarios make every answer and its derivation check-able. They cover version resolution, rules, dependencies, sets, aggre-gation, and completeness, but not subjective preferences or open-ended planning. The shared answer model isolates what each SUT supplies, and the recoveries use the decomposition that the bench-mark provides. 

## 7 Related Work 

Agent memory systems. Memory systems differ in how they organize a history [49]. MemGPT [33] manages a hierarchy of mem-ory resources, Mem0 [8] extracts and updates salient facts, Memo-ryLLM [46] keeps memory in model parameters, MemoryOS [22] and LightMem [14] stage memory across levels, and Cognee [31], 

Zep [35], and AriGraph [3] link stored information in graphs. State-MemBench [13] and STALE [7] make supersession, dependencies, and invalidation explicit. MemDerive prescribes none of these rep-resentations. It evaluates their observable effect, whether the re-quested state is correct, whether its inputs can be recovered, and whether later changes reach it. 

Memory benchmarks. LoCoMo [30], LoCoMo-Plus [27], and LongMemEval [48] test recall, temporal and multi-session reason-ing, knowledge updates, and abstention over long conversations, and MemoryAgentBench [20] adds incremental evaluation of re-trieval, learning, and forgetting. MemBench [43], MEMTRACK [10], LongMemEval-V2 [47], MemoryArena [18], AMemGym [21], and AMA-Bench [53] move these tests into agentic tasks. Recent bench-marks target specific failures. Provenance and view maintenance. Database provenance ex-plains how query results, including aggregates, depend on input records [2, 15], and why and why-not provenance explain returned and missing results [6, 24]. Incremental view maintenance updates derived results when base data changes [16, 32], including higher-order delta processing and stream computation [5, 23]. MemDerive 

builds its witnesses on minimal why-provenance and recomputes gold as the history grows. It applies these ideas to memory over natural-language records, where the SUT must first recover the facts that a database would be given. 

## 8 Conclusion 

Agent memory must supply derived state, which no record states and which changes as the history evolves. MemDerive makes this requirement measurable. Symbolic scenarios give every query an ex-act answer, a gold derivation DAG, and its supporting events, so the benchmark can check final answers, locate the intermediate state where a derivation fails, and follow answers across updates. Our evaluation shows that current memory systems trail raw retrieval on derived state, that most of their failures are intermediate states they can return but do not retrieve for the question that needs them, and that they rarely propagate implicit changes. Reliable agent memory therefore needs dependency-aware gathering, ver-sioned rules, and incremental maintenance of derived state, much as a database maintains views over changing tables.
