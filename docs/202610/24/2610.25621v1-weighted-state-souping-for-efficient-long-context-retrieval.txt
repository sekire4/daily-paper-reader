# Weighted State Souping for Efficient Long-Context Retrieval 

William L. Tong 2,∗, Aryo Lotfi 1, Emmanuel Abbe 1, Josh Susskind 1, Cengiz Pehlevan 2, Eran Malach 11Apple, 2Harvard University 

> ∗Work done while at Apple

State space models (SSMs) combine fast inference and fixed state size with competitive language-modeling performance. Recently, state souping has been proposed as a procedure whereby an SSM independently encodes chunks of tokens like documents, tool definitions, or memory records. The resulting state encodings may be cached and recombined to cheaply construct a context for downstream queries. However, both state souping and vanilla SSMs deteriorate on long, crowded contexts, limiting their utility for long-horizon domains. To address this issue, we propose weighted state soup-ing , a simple method that learns query-dependent weights for composing cached states. The resulting models improve long-context performance substantially across both single- and multi-hop document question answering, needle-in-a-haystack retrieval, variable tracking, and tool use. Our method can be further adapted into an efficient sparse variant, yielding near-constant encoding cost with respect to context length while preserving (and sometimes improving ) perfor-mance. We also present simple theoretical arguments that illustrate why souping works and when it may fail, and discuss informally the advantages of weighted souping. Weighted state souping thus combines reusable context representations with selective retrieval, offering an efficient approach to language modeling over large collections of documents, tools, and other forms of structured context that increasingly dominate modern agentic workloads.

# 1 Introduction 

Many applications of large language models (LLMs) require long-lived context organized into discrete chunks of tokens: tool definitions for an agent (Schick et al., 2023; Patil et al., 2025), documents for question answering or retrieval-augmented generation (Rajpurkar et al., 2016; Yang et al., 2018; Trivedi et al., 2022; Lewis et al., 2020; Guu et al., 2020), and memory records or chat histories that persist across interactions (Packer et al., 2023; Wu et al., 2024; Salemi et al., 2024). A useful memory architecture must retrieve relevant chunks from an increasingly crowded store without repeatedly processing the entire history. In these settings, common practice concatenates the chunks of tokens and processes them as a single flat sequence. With the rising popularity of state space models (SSMs) and related fixed-state architectures (Gu & Dao, 2024; Dao & Gu, 2024; Katharopoulos et al., 2020; Schlag et al., 2021; Sun et al., 2024), an alternative approach becomes possible. Rather than perform a single autoregressive pass on a concatenated sequence, each chunk can be independently encoded into a state. The resulting collection of states are then point-wise summed to initialize the model before it processes a query (Figure 1). By analogy to model souping (Wortsman et al., 2022), this procedure is called state souping (Pióro et al., 2024; Jafari et al., 2025; Liu et al., 2025): the quantities combined are input-dependent recurrent states, rather than model parameters. State souping has an obvious efficiency advantage. State encodings can be computed in parallel and, for slowly changing chunks like memory records or tool definitions, cached and reused. This ability to cache representations makes souping naturally suited for handling the structured context that increasingly domi-nates modern agentic workloads: inference can depend on selected state encodings without repopulating the context with large memory artifacts, tool definitions, and documents. However, finite-state SSMs struggle 1arXiv:2610.25621v1 [cs.LG] 19 Oct 2026 to copy or retrieve from long contexts (Jelassi et al., 2024; Waleffe et al., 2024; Arora et al., 2024), and state souping performance similarly decays as more documents are added (Jafari et al., 2025). This loss of selectivity limits souping precisely where persistent memory is most useful. In this work, we introduce weighted state souping , which learns attention-like weights over state encodings. Across document QA, needle-in-a-haystack retrieval, variable tracking, and tool use, weighting substantially improves robustness as contexts grow beyond training lengths. Our method can be further adapted into a sparse variant that permits near-constant encoding cost while preserving — and sometimes improving —performance. Our main contributions are: • a novel weighted state souping procedure that permits robust selectivity, strong generalization on long contexts, and substantial efficiency gains over both Transformers and traditional SSMs, • a comprehensive evaluation over diverse benchmarks including multi-document question answering, needle-in-a-haystack retrieval, variable tracking, and agentic tool use, • a simple theoretical account of how souping successfully retrieves and composes across chunks, and its potential weaknesses compared against sequential models. We also discuss informally the advantages of weighted state souping. 

# 2 Related work 

State souping is a relatively recent method. Pióro et al. (2024) introduced the term, and explored linear combinations of recurrent states for in-context skill transfer. Jafari et al. (2025) study independently en-coded document states, showing that finetuning enables simple pooling operators to support downstream QA and retrieval. PICASO (Liu et al., 2025) derives state-composition rules similar to souping for permutation-invariant inputs. We build on these works by showing how query-dependent weighting permits both signifi-cantly stronger length generalization and substantial efficiency wins. State souping can be seen as an approximate form of state caching, a procedure whereby states generated from common prefixes can be cached and reused exactly for downstream requests. In Transformers, the procedure is more often called KV caching (Shazeer, 2019; Kwon et al., 2023). In SSMs, state caching has been explored particularly in the context of hybrid models, where common KV caching methods for attention blocks may not transfer directly to SSM layers. In particular, Pan et al. (2025) explore SSM-specific cache eviction policies to maintain an efficient prefix cache for SSMs. Shirokikh & Nikolenko (2026) explore a complementary idea in which cache checkpoints are saved along a sequence; future generation resumes from the deepest checkpoint that matches the current prefix. Gopal et al. (2026) investigate state caching in pure SSMs for retrieval augmented generation, and highlights its efficiency for edge-computing applications. Souping is also related to state tuning, the process of learning an initial state for a recurrent model. This process has been studied in the context of parameter-efficient fine tuning (PEFT) for state space models (Galim et al., 2024; Kang et al., 2025; Yoshimura et al., 2025). Kang et al. (2025) in particular find that state offset tuning , in which a learned offset is added to every recurrent state, outperforms initial state tuning and other PEFT methods like LoRA. State tuning has also been studied in the RWKV community (Xiao et al., 2025), and historically in early RNNs (Forcada & Carrasco, 1995). Our weighted approach to state souping is similar to methods that attempt to introduce attention-like features to state space models, interpolating between Transformers and SSMs. In particular, Akhauri et al. (2024) introduce a method in which SSMs produce compressed key-value representations before applying attention. Similarly, Infini-attention (Munkhdalai et al., 2024) combines local attention with a compressive recurrent memory. Memory Caching (Behrouz et al., 2026) explores storing and combining recurrent memory checkpoints through attention-like weights. Our approach focuses on structured contexts that permit state souping, and our weighting does not retain token-by-token attention to cached states during generation, ultimately yielding both substantial efficiency benefits and performance gains. Methods analogous to state souping have also been investigated in Transformers. Notably, Eyuboglu et al. (2026) introduce a method for directly training KV caches to encode documents. # 3 Weighted State Souping 

State souping operates in the following way. Let an input contain k token chunks c1, . . . , ck and query q.The SSM independently encodes each chunk into its final state si, where the state encompasses the collection of recurrent states across all layers. We then perform a point-wise average over the k encodings to make the “soup” s0 = 1

> k

Pki=1 si. s0 becomes the initialization for the SSM as it processes the user query (Figure 1). We use the same SSM for encoding and generation, but these models can be different. Souping is not an inference-time only intervention, and requires either learning from scratch or additional finetuning on a pretrained SSM to teach the model to used this composed initialization (Jafari et al., 2025). Crucially, the only channel through which the input chunks influence the query is the souped initialization. Since SSMs perform simple linear state updates, a soup constructed through an average of states can be viewed as a naive approximation of the state construct from a concatenated, sequential input. Such a mean soup is the approach used in prior work (Pióro et al., 2024; Jafari et al., 2025), and performs comparably with a sequential SSM. However, both mean souping and sequential SSMs struggle when operating over long contexts containing many input chunks (Jafari et al., 2025; Chen et al., 2024; Arora et al., 2024). As the number of chunks increases, a mean soup or finite SSM state becomes increasingly noisy, degrading performance. Query-dependent weighting may instead concentrate the souped state on relevant chunks, the inspiration for 

weighted state souping . Our method is related to other schemes that weight input tokens in sequential SSMs (Akhauri et al., 2024; Behrouz et al., 2026), though our focus is on a souping architecture for chunked inputs. To compute these weightings, we add a learnable linear readout that maps the final activation to a key and query vector. Each chunk produces key ki. Starting from a zero-initialized state, a pass over the user query produces u. We then compute the souped initialization as s0 = Pki=1 σ(ki ·u) si, with weighting function σ(·).The linear readout and base model are jointly finetuned. See Figure 1c for an illustration of this 1. Unlike a Transformer’s token-level attention, this procedure assigns one scalar weight per chunk, shared across all layers and heads and computed once from the original user query. The weights remain fixed during query processing and generation.

# 4 Experiments 

We use a 1.5B Mamba-2 SSM (Dao & Gu, 2024) and compare softmax-weighted, sparse, and mean souping against sequential Mamba-2 and a matched Transformer with rotary positional encodings (Su et al., 2021). We evaluate our models across a diverse range of tasks. For document QA, we use SQuAD (Rajpurkar et al., 2016) for single-hop; HotpotQA (Yang et al., 2018) and MuSiQue (Trivedi et al., 2022) for multi-hop. For NIAH and variable tracking, we use RULER (Hsieh et al., 2024). For tool use, we use the Berkeley Function Calling Leaderboard (BFCL) (Patil et al., 2025). To probe long-context performance on document QA and BFCL, we augment the input with additional distractors and plot performance for varying pool size k. If k is smaller than the number of gold documents or gold tool definitions (relevant only for the k = 1 datapoints), then the input consists only of gold samples. This suite tests selective retrieval and reasoning as the available context grows, crowding the relevant chunks with increasingly more distractors. Our models are finetuned to each task, using either the task-provided official training split (for document QA), a specialized post-training corpus (for tool use), or a disjoint subset of examples (for RULER). See Appendix C for additional details on training, evaluation, and our benchmarks. 

4.1 Benchmark results 

Figure 2 summarizes the main results; Appendix A reports on additional metrics and task subsets. In general, weighted state souping performs strongly even at large pool size k. While mean souping and sequential Mamba tend to deteriorate as the number of chunks increases, weighted souping matches their performance at small k, and persists in near-constant performance as k increases to several times beyond the max training size. This phenomenon persists across a diversity of tasks and benchmarks, including in multi-hop settings like HotpotQA, MuSiQue, and RULER variable tracking where the model must link information across multiple chunks. Similar to other works (Malach et al., 2026; Zhou et al., 2024), we observe that Transformers do not extrapolate well to sequences longer than the training data, though their in-distribution performance tends to be strong. Interestingly, sparse souping matches or improves on full softmax souping, particularly on multi-hop QA (HotpotQA, MuSiQue). Softmax mass may diffuse across many documents as k increases. Sparse souping instead may beneficially concentrate attention in the most relevant indices. An analogous benefit has been observed in sparse attention for Transformers (Veličković et al., 2024; Vasylenko et al., 2025; Zhang et al., 2024). One weakness of sparse souping is the need to specify the number of chunks Ntop to keep. If Ntop is insufficiently large, critical chunks may be dropped and the model’s performance suffers (Figure 5f). Designing a weighting function with adaptive sparsity represents an interesting avenue for further exploration. While the performance of weighted souping is generally strong, it underperforms at small k in the parallel multiple subset of BFCL, despite strong performance on python simple and parallel (Figure 6). Whether this reflects an optimization issue or a fundamental limitation remains open.

There are a number of further considerations for souping. 1) Weighted souping must also factor in the time to perform an initial pass over the user query to generate a query vector, and the time it takes to compute the weightings. For a fixed key dimension, scoring and normalizing the weights costs O(k) per query. Once the soup is constructed, the cost per generated token is constant with respect to k, since generation does not access the cached chunks again. In general, user queries average under 100 tokens (Zheng et al., 2024) and computing softmax weights is extremely fast, so the total added cost of computing the weights is typically negligible and amortized over the number of input chunks. 2) The retrieval time is heavily influenced by the specific memory holding the cached state encodings. GPU HBM is significantly faster than system RAM, which in turn is faster than system disk. Depending on where the encodings live, retrieval may in the worst case be slower than encoding from scratch. 3) Sparse souping improves efficiency further, since chunks assigned zero weight do not need to be retrieved. Hence, if the number of nonzero weights is constant with respect to the context length (which is true in our setting), then the encoding performance of sparse souping is effectively constant as context length grows 2.

# 5 Theory: retrieval and composition 

The experiments in Section 4 provide the main evidence for the effectiveness of weighted state souping. To complement these empirics, we present a simple theoretical analysis that begins to answer the questions of why souping works, and what potential strengths and weaknesses it may have compared with sequential models. Our arguments are primarily expressivity-based: we provide constructions showing that both souping and sequential models can implement an induction-head retrieval task representative of our empirical benchmarks. We also discuss possible weaknesses that independent chunk encoding introduces, namely a sensitivity to chunk boundaries and the inability to encode cross-chunk representations. We conclude with a discussion of the benefits weighted souping has for retrieval over long, crowded contexts. Our analysis is by no means a complete theoretical account of state souping. Instead, we introduce simple intuitions that build towards a principled understanding of the method.

5.3 One-hop induction 

We begin by considering the one-hop induction-head task, reflecting the setting in Olsson et al. (2022). We observe that both a sequential and souping model can solve the task, but chunk boundaries that separate the task’s key-value pairs can make souping fail. 

Proposition 2. Suppose that every key-value pair is contained in one chunk, each key occurs at most once, and the queried pair’s chunk receives positive soup weight. A single layer model with sufficient width (Section 5.2) solves one-hop induction for both sequential encoding and weighted state souping. 

See Section B.1 for the construction proving this statement. Proposition 2 demonstrates that even a single-layer SSM is sufficiently expressive to perform one-hop induction. Together with our earlier discussion in Remark 1, we observe that both souping and sequential models can readily perform in-context retrieval. However, souping is sensitive to chunk boundaries, as we establish in the next proposition. 

Proposition 3. Suppose that chunk boundaries split every key-value pair (i.e. every token is encoded as a separate chunk). Then no souping model solves all one-hop induction instances. Proof. Choose distinct indices a, b, u, v . Consider the two token sequences 

C = ( ka, v u, k b, v v ), y1(C, a ) = vu,C′ = ( ka, v v , k b, v u), y1(C′, a ) = vv .

After splitting into singleton chunks, both inputs have the same multiset {ka, k b, v u, v v }. For the same query, souping therefore produces the same state for C and C′. Hence, the model must return the same output on both inputs, though their labels differ, failing the task on at least one input. The setting in Proposition 3 is extreme, but underlines the sensitivity of souping to correctly formed chunks. However, this does not mean that souping cannot link information between chunks — our multi-hop document QA and variable tracking experiments demonstrate that souping models can robustly link information across multiple chunks. In the next section, we observe that souping can readily link disparate chunks when performing the multi-hop generalization of our task. 

5.4 Multi-hop induction 

We consider the multi-hop generalization of our induction-head task. We discuss how souping can continue linking information between chunks to solve the task, though under certain circumstances, it may be less efficient that a sequential input model. 

Proposition 4. Suppose that every key-value pair is contained in one chunk, each key occurs at most once, and every chunk containing an edge of the queried n-hop path receives positive soup weight. Souping and sequential models can solve the n-hop induction task by composing the construction in Proposition 2 across 

n layers. 

See Section B.2 for the construction proving this statement. In this way, we establish the basic competency of souping models to solve these classic in-context retrieval tasks. However, one advantage sequential models retain over souping is their ability to learn cross-chunk representations in deeper layers. Because souping encodes chunks independently, it remains impossible to directly encode information between chunks in deeper layers. Indeed, to learn Cn associations, a souping model would require B = Cn log 2 N bits, whereas a sequential model needs a factor of n fewer with just B = C log 2 N bits. More generally, sequential encoding may permit useful composed representations in deeper layers. The doubling construction is similar in spirit to the pointer-doubling strategy of Sanford et al. (2024), and gives a logarithmic-depth sequential solution in this ordered setting. We conjecture that this may yield a depth separation from souping under suitable width and precision constraints. 

5.5 Weighted state souping permits selective retrieval 

While souping may be sensitive to chunk boundaries and exhibit less efficiency for favorably ordered inputs, weighted souping nonetheless retains a decisive advantage over sequential models for long-context retrieval. Poor long-context performance can be understood as a consequence of gating and noisy contexts. In a sequential model with Mamba-like history decay, a contribution at distance ∆ is exponentially decayed by a factor α∆. Tong et al. (2026) have formalized the resulting tradeoff: reducing decay preserves distant signals but permits distractor variance to accumulate, whereas stronger decay controls that variance at the cost of attenuating earlier tokens. Hence, no setting permits a sequential model to retrieve from every token in a long context with even reliability. Weighted souping bypasses this tradeoff by permitting direct attention on the relevant chunks. In this scheme, distractor variance is determined only by the selected set of chunks rather than the full context size. Earlier chunks are not attenuated compared with later chunks, so weighting is computed evenly across the whole context. Provided that the weights remain concentrated as the number of distractors increases, weighted souping may maintain strong long-context performance when sequential and mean-souped variants fail. In some sense, weighted souping interpolates between recurrent accumulation and attention-like selection. It is not equivalent to full attention (souping weights are scalar, chunk-level, and computed once from the original query). Nonetheless, our experiments support the strong retrieval performance of weighted souping models. Together with their efficiency benefits, weighted state souping presents an attractive paradigm for future models. 96 Discussion 

Weighted state souping augments reusable context encoding with query-dependent selection. A lightweight routing head combines cached chunk states into a fixed-size recurrent initialization, improving long-context performance across document QA, retrieval, variable tracking, and tool use benchmarks. The results show that a fixed state need not imply uniformly compressing the entire available collection: each query determines which information enters the working state. Inference-time sparsification often improves both accuracy and state-transfer cost, particularly beyond the training pool size. The theory complements these results by demonstrating retrieval and cross-chunk composition, while identifying information lost at chunk boundaries and discussing the potential advantages of sequential processing. There remain many avenues for further exploration. Our focus in these experiments has been on single-turn interactions, but generalizing souping to multi-turn interactions featuring several rounds of back-and-forth between user and assistant remains an unexplored direction. There are also many opportunities for improving weighted state souping, for instance by replacing fixed-N sparse souping with adaptive sparsity that adjusts to the problem, exploring alternative weighting schemes, or using thinking tokens in conjunction with souping. Our theoretical discussion offers initial intuitions for why state souping works and when it may fail, but there remain many opportunities for investigating potential memory and depth separations between souping and sequential models.

C.1 Tasks 

Across the document-QA and tool-use benchmarks we probe long-context robustness with a shared pooling 

construction. Each example carries one or more gold items — the documents or tool definitions required to answer the query — which we always retain; we then add sampled distractors until the pool holds k items in total and shuffle so the gold position is randomized. Thus k counts the total number of in-context chunks (not the number of distractors), and k = 1 denotes a gold-only pool. Distractors are drawn without replacement from a split-local pool that excludes the example’s own gold items, so training and evaluation distractors never cross split boundaries. During finetuning the pool size is sampled per example as k ∼ Uniform[1 , k max ]; at evaluation we sweep k well beyond kmax to test generalization. All tasks share the Nemotron-Nano tokenizer (NVIDIA, 2025) (vocabulary size 131 ,072 ) and are evaluated on the public validation split (the official test splits are hidden). RULER is handled differently, as described below.  

> Berkeley Function Calling Leaderboard (BFCL).

A standard tool-use benchmark (Patil et al., 2025): the model is prompted with a list of tool definitions and must emit a tool call that solves the user query. Before evaluation we finetune each model for tool calling on a filtered subset of NVIDIA’s Nemotron agentic SFT data (NVIDIA, 2025), keeping the ≈228 ,700 examples whose first assistant turn is a tool call. We evaluate on BFCL, reporting the simple python (one function, one call; 400 examples), parallel (one function, multiple calls; 200 examples), and parallel multiple (multiple functions, multiple calls; 200 examples) splits. Tool pools are built with a global BM25 retriever (Robertson & Zaragoza, 2009) over the ≈14 ,700 -tool non-live vocabulary: candidate tools are scored by BM25, truncated to the top k, and the gold tool(s) are then force-included and randomly positioned. Training samples k ∼ Uniform[1 , 24] ; the headline evaluation sweeps k ∈ { 1, 12 , 24 , 36 , 48 , 64 , 96 , 128 }. Correctness is scored by BFCL’s abstract-syntax-tree checker, which validates the function name and every argument value against the reference-answer set. We additionally report an order-independent function-name-only match.  

> Stanford Question Answering Dataset (SQuAD).

A single-document extractive QA dataset (Rajpurkar et al., 2016): given a Wikipedia paragraph, the model quotes a text span answering the query. We use SQuAD v1.1 and draw distractor paragraphs from the same split. Training uses k ∼ Uniform[1 , 24] ; evaluation sweeps 

k ∈ { 1, 12 , 24 , 36 , 48 , 64 , 96 , 128 } over a fixed subset of 500 validation questions (shared across all arms via a common seed). We report exact match (EM) accuracy under SQuAD normalization (lowercasing, and removal of punctuation, articles, and extra whitespace). Dotted lines in the figures report closed-book accuracy ( k = 0 ,no documents in context) as a memorization floor.  

> HotpotQA.

A multi-hop QA dataset (Yang et al., 2018). Each context paragraph becomes one document, and the annotated supporting paragraphs are marked gold (a multi-gold example). Pooling, evaluation k-sweep, example count, and metrics match SQuAD.  

> MuSiQue.

A multi-hop QA dataset engineered to require genuine reasoning over many hops and to resist single-document shortcuts (Trivedi et al., 2022); it is a harder version of HotpotQA. We use the answerable variant ( musique_ans ), treating the annotated supporting paragraphs as gold and scoring against the gold answer and its aliases. Pooling, evaluation k-sweep, example count, and metrics match SQuAD. 

> SQuAD-

n. To further stress multi-document attention, we construct SQuAD-n: we merge n SQuAD exam-ples with distinct gold paragraphs into a single example whose prompt contains all n gold paragraphs (mixed among max( k − n, 0) distractors) followed by the n questions, labeled (1) . . . (n); the model must return the 

n answer spans in order. We use n ∈ { 3, 5}. We report micro-averaged EM over all (example, sub-question) pairs, and a strict joint EM that credits an example only when every sub-answer is an exact match.  

> RULER.

A synthetic long-context benchmark (Hsieh et al., 2024). We use an in-repository reimplementation of its tasks and focus on three subtasks: single needle-in-a-haystack (a magic-number “needle” line hidden among Paul Graham essays), multi-key NIAH (the needle is hidden among confusable distractor needles), and 20 variable tracking (chains of variable assignments embedded in filler text, where the model resolves the value of a queried variable by following a four-hop chain). Unlike the QA and tool-use tasks, RULER has no natural chunks and no distractor pool; following Jafari et al. (2025) we chunk each input into consecutive 256 -token blocks, so the “pool size” is ⌈context length /256 ⌉ and grows with the context. A block is treated as gold if its token span overlaps a needle sentence (NIAH) or an assignment in the queried chain (variable tracking). We cap the training context at 2048 tokens ( 8 chunks) and evaluate at context lengths {1, 2, 4, 8, 16 , 32 , 64 , 128 }Ktokens over 200 examples per (subtask, length). 

C.2 Models  

> Architectures.

Our SSM is a 1.5B-parameter Mamba-2 model (Dao & Gu, 2024): 32 Mamba-2 mixer layers (with no interleaved attention or MLP blocks), hidden size 2048 , RMSNorm, and no positional embedding. Each mixer uses a state-expansion factor of 2 (inner dimension 4096 ) partitioned into 64 heads of head dimension 64 , state dimension 128 , 8 groups, and a convolution kernel of width 4. The recurrent state is therefore 4096 × 128 = 524 ,288 elements per layer, or ≈16 .8M elements ( 33 .6 MB in bf16) across all 32 layers — this is the size of a single cached state encoding. Our Transformer is a 1.5B-parameter LLaMA-style model: 20 layers, hidden size 2048 , SwiGLU feed-forward width 5504 , 16 attention heads with full multi-head attention, rotary position embeddings, and RMSNorm. The two models are matched in parameter count (≈1.5B). Both are pretrained on the Nemotron-CC corpus (Su et al., 2025) (on the order of 300 B tokens) with the same optimizer schedule (AdamW, peak learning rate 3 × 10 −4, cosine decay), share the Nemotron-Nano tokenizer, and run in bf16. We deliberately give the Transformer rotary embeddings so that it can process contexts longer than those seen in training, so that the sequential-Transformer baseline is given a fair chance at length generalization.  

> Weighted-souping read-out.

We augment the SSM with a lightweight read-out head that produces the key and query vectors of Section 4. Concretely, we read the last-token residual activation at the final decoder block and pass it through two learned linear projections Wk, W q ∈ Rd×d′

with d = 2048 and d′ = 128 

(equivalently, a single projection to R2d′

split into a key half and a query half). The two projections are separate parameters, initialized to identical values ( Wk = Wq ) so the head begins as the parameter-free cosine ranker over the base model’s activations; they are untied thereafter and trained independently. The head is the only component initialized from scratch; it is trained jointly with the base model but placed in its own optimizer group at learning rate base LR × lr_scale , with lr_scale = 10 . 

> Cosine normalization.

The weight assigned to chunk i is σ(score i), where the score is a dot-product between the chunk key ki and the query vector u. Rather than the usual 1/√d dot-product scaling, we ℓ2-normalize the key and query and scale their cosine similarity by a learnable inverse temperature γ: score i = γ ki·u 

> ∥ki∥ ∥ u∥

.We initialize γ = 14 and cap it at 100 . Because the pre-nonlinearity logits are bounded to [−γ, γ ] regardless of pool size, the weighting stays well-conditioned as k grows, which we found important for generalizing to pool sizes far beyond the training distribution. Our headline weighting function σ is the softmax.  

> Sparse souping.

Sparse souping keeps only the top-N weights and zeroes the rest; with softmax we apply the mask before the nonlinearity so the surviving weights still sum to one. It is applied at inference time and reuses the softmax checkpoints unchanged. We use Ntop = 4 for the document-QA and BFCL figures and Ntop = 20 for RULER; the larger Ntop is needed for variable tracking, where gold information is spread across many chunks (we sweep Ntop in Figure 5).  

> Auxiliary routing loss.

We optionally supervise the weights toward the known gold chunks with an auxiliary loss, L = LSFT + λ Laux , where Laux is a cross-entropy over the k chunks under softmax weighting, computed from the same scores used to combine the states. We set λ = 1 for RULER and tool use, where the gold chunks are reliably identifiable, and λ = 0 for document QA, where the head learns the weighting purely from the downstream SFT signal.  

> Souping finetuning.

Finetuning is necessary to learn the souping format (Jafari et al., 2025). All souping models are finetuned from the pretrained base with the softmax weighting, residual read-out, and cosine 21 normalization above. For document QA we train for 3 epochs (SQuAD, HotpotQA) or 5 epochs (MuSiQue) at base learning rate 5 × 10 −6 with no auxiliary loss, from the train splits included with the benchmarks. For RULER we train for 6000 steps at base learning rate 10 −5 with λ = 1 , chunked at 256 tokens. For tool use we warm-start from a tool-calling-SFT checkpoint already finetuned on the Nemotron Agentic SFT split (NVIDIA, 2025), and train for an additional one epoch at base learning rate 10 −5 with λ = 1 to learn the souping format. In every case the read-out head uses the 10 × learning-rate multiplier described above. The sequential baselines are finetuned on the concatenated input for matched steps at learning rate 10 −5

(QA/RULER) or 5 × 10 −5 (tool use), so that all models see matched data and compute.  

> Decoding and evaluation.

All models decode greedily. For tool use, decoding is constrained by a tokenizer-level logit mask that enforces the tool-call envelope ( <TOOLCALL>[ ... ]</TOOLCALL> ); the constraint is applied identically to the souping arms and the sequential baselines. The QA and RULER tasks decode without constraints. Evaluation pool sizes, context lengths, and example counts are as given in Appendix C.1. 

C.3 Computational benchmark 

The timings in Figure 3 are measured on a single AWS p5.48xlarge node ( 8× H100). We compare four inference paths: a sequential Transformer, a sequential Mamba, full weighted souping, and sparse souping. For the souping paths, we time the encoding of a 128 -token query and the computation of the softmax weights, while the chunk state encodings themselves are retrieved rather than recomputed, from one of three memory tiers: GPU high-bandwidth memory (HBM), system RAM, or system disk. Each cached Mamba-2 encoding is the 33 .6 MB bf16 state described above, so retrieval cost is dominated by the bandwidth of the tier in which the encodings live; retrieval from HBM is far faster than from RAM, which in turn is faster than from disk, and in the worst case (short chunks retrieved from disk) retrieval can be slower than re-encoding. 22
