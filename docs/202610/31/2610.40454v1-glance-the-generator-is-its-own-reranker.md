## 摘要
检索增强生成通常为重排序和回答分别部署独立模型，导致模型驻留和段落处理重复。我们提出 Glance，它为生成器配备轻量级决策适配器和指针头，从共享预填充中对候选段落打分。简短的相关性探针从缓存上下文中分支出来，为每个段落产生一个分数，而无需分别对每个查询-段落对进行预填充。单个常驻的 9B 骨干模型支持生成、通用决策和重排序，每项决策技能仅增加约 0.1 GiB 内存。经过 39 分钟的 MS MARCO 微调后，Glance 在 SciFact 上达到 0.741 的 nDCG@10，在 NFCorpus 上达到 0.345，而 bge-reranker-v2-m3 分别为 0.721 和 0.326。在 300 个 HotpotQA 问题上，在相同基础生成器下，其选择的上下文相比交叉编码器选择的上下文将答案 F1 提高了 0.045（配对 bootstrap 95% 置信区间 [0.014, 0.076]）。在一项规模扩展研究中，重排序质量在从一次共享预填充中对多达 200 个候选（43k tokens）打分时持续提升，在此设置下其 nDCG@10 超过交叉编码器 0.058；并且仅由探针激活的适配器可使生成从原始段落缓存继续。这些初步结果展示了使用单个常驻骨干模型、基于生成器的重排序；当前评估涵盖两个检索数据集、一个问答数据集和一个骨干模型系列。

## Abstract
Retrieval-augmented generation commonly serves separate models for reranking and answering, duplicating model residency and passage processing. We introduce Glance, which equips the generator with a lightweight decision adapter and pointer head to score candidate passages from a shared prefill. Short relevance probes branch from the cached context, producing one score per passage without separately prefilling each query-passage pair. A single resident 9B backbone supports generation, general decisions and reranking, with approximately 0.1 GiB of additional memory per decision skill. After 39 minutes of MS MARCO fine-tuning, Glance achieves nDCG@10 of 0.741 on SciFact and 0.345 on NFCorpus, compared with 0.721 and 0.326 for bge-reranker-v2-m3. On 300 HotpotQA questions, its selected context improves answer F1 by 0.045 over cross-encoder-selected context under the same base generator (paired bootstrap 95% CI [0.014, 0.076]). In a scaling study, reranking quality keeps rising up to 200 candidates (43k tokens) scored from one shared prefill, where it exceeds the cross-encoder by 0.058 nDCG@10, and a probe-only activated adapter lets generation continue from the original passage cache. These initial results demonstrate generator-based reranking with one resident backbone; evaluation currently covers two retrieval datasets, one QA dataset and one backbone family.

## 1. 核心问题与研究动机

- **背景**：RAG 系统通常将「证据重排」与「答案生成」分配给两个独立模型。交叉编码器（如 monoT5、bge-reranker）需对每个 query–passage 对单独编码；LLM 重排器（pointwise/listwise）质量更高但成本更大。
- **核心痛点**：
  - 需要额外常驻一个重排器骨干，造成显存与部署重复；
  - 候选段落在重排阶段被处理一遍，生成阶段又被读一遍，计算重复；
  - 即便上下文窗口很大，长上下文模型仍存在「中间遗失」问题，重排依然必要。
- **核心设问**：生成器本来就要读这些段落，能否用**跨段落共享的计算**一次性判断所有候选？
- **整体含义**：提出 Glance，让生成器「兼任」自己的重排器——单一常驻 9B 骨干同时承担生成、通用决策与重排序，每项决策技能仅增加约 0.1 GiB。

## 2. 方法论

### 2.1 核心思想
- 在冻结的生成器骨干上挂载**轻量决策适配器**（rank-16 LoRA）+ **256 维指针头**；
- 对 k 个候选段落只做**一次共享 prefill**，然后从缓存上下文中分支出 k 个短相关性探针（每条约 30 token），每个探针产出一个相关性分数；
- 无需对每个 query–passage 对单独 prefill。

### 2.2 两种答案流水线
- **Glance（主流程）**：适配器在所有 token 上激活 → prefill 候选 → 探针打分 → 选 top-n → **关闭适配器重新 prefill** 选中段落 → 生成答案。
- **Glance-Activated**：适配器仅在探针 token 上激活（借鉴 Activated LoRA）→ 用基础权重 prefill 候选 → 探针打分 → **继续原缓存**用基础权重生成。缓存中仍保留全部 k 个候选，落选段落不会被移除。

### 2.3 决策模式与指针头
- 输入格式：`<state> s <q> instruction <opt> o1 </opt> … <decide>`；
- 指针头将 `<decide>` 处隐状态与每个 `</opt>` 处隐状态比较，对选项做 softmax；二元判断使用 `{false, true}`；
- **不生成任何文本**，一次决策 = 一次 prefill；骨干冻结，只训练 LoRA 与指针头。

### 2.4 三种多探针打包方式
- **packed_all**：state 为全部段落拼接，分支 i 提问「段落 i 是否包含回答/支持 query 的信息？」；
- **packed_q**：state 为 query，每个分支放入一个段落 + 相关问题；
- **listwise**：state 为 query，构造一个以 k 个段落为选项的选择题；
- 分支之间互不 attend，各自从 state 末尾继续位置编号；「single pass」= 一次共享段落 prefill + 一次批量探针续写。
- 注意：packed_all 中每个探针都能看到全部段落，因此分数并非统计独立，且可比较邻居。

### 2.5 混合骨干上的精确实现
- 骨干为 Gated DeltaNet 线性注意力层与全注意力层 3:1 交织；
- 全注意力层可用掩码隔离分支，但线性注意力层只携带**单一循环状态**，因此共享前缀只运行一次，每个分支从 state 末尾各层缓存的**副本**起步（注意力层 KV；DeltaNet 的卷积窗口 + 循环状态）；
- 该路径在训练与推理中一致，故每条记录只需计算一次 state；
- 由于 DeltaNet 状态按顺序汇总整个前缀、不能任意拼接 per-passage 缓存，主流程需重新 prefill 选中段落（约 1.5k token），且其缓存是用「适配器开启」状态算出的；Activated 变体则可直接续用完整候选缓存。

### 2.6 训练细节
- 从已有通用决策适配器热启动，在 4,000 条 MS MARCO 训练 query（Tevatron BM25 hard negatives）上微调；
- 每条记录打包 1 个正例 + 7–19 个 hard negatives，打乱，packed_all 格式，每个探针一个二元标签；
- 1 epoch = 500 步、55,598 个标注探针、7.7M forward token；LoRA rank 16，lr 5e-5（指针头 1e-4），batch 8，bf16；
- 训练数据不含任何 BEIR / HotpotQA 数据。

### 2.7 适配器配置
| 名称 | 训练 | 适配器激活范围 |
|---|---|---|
| zero-shot | 4.4k 通用决策记录，20 分钟，无检索数据 | 全部 token |
