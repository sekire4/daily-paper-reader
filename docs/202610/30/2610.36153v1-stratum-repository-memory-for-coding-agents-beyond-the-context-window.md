## 摘要
上下文窗口已增长千倍，但编码智能体仍然在每次会话开始时对过去的工作毫无记忆。它们会重新读取文件、重试失败的方法，并忘记数小时前已经确定的根因。这不是上下文长度问题，而是记忆架构问题。我们的假设是：编码智能体需要持久、具备经验感知能力的仓库记忆，使知识能够从一次会话保留到下一次。基于真实仓库的三项测量支撑了这一设计。第一，中型项目已经超过最大的生产上下文窗口，而将知识存储在模型的键值（KV）缓存中，相比以索引文本形式存储，所需字节数高 $10^4$ 到 $10^5$ 倍。第二，在 752 个真实缺陷修复提交中，中位数修复会编辑两个文件，而这些文件及其直接导入文件合计不足仓库的 10%；瓶颈在于选择，而非容量。第三，即使考虑传递导入可达性和测试链接，仍有 47% 的共同编辑文件对在结构上不连通；选择所需的知识必须从历史和经验中挖掘。我们提出 Stratum 的构想：一种与仓库共存的层次化记忆，并通过页面安全工具提供服务：每个响应都说明返回了什么、还剩下什么以及代价是什么。在包含一百万个节点的存储上进行检索，中位耗时为 1.7 ms。在一项针对八个真实缺陷的多会话实验中，一个新智能体继承了由不同模型撰写的先前会话记忆，在 24 次试验中有 21 次识别出根因文件，而仅检索基线为 24 次中的 6 次（Fisher $p<10^{-4}$），且中位 token 成本低 4.5 倍。将全部八项调查的笔记汇集到一个存储中，成功率仍为 8/8。

## Abstract
Context windows have grown a thousand-fold, yet coding agents still start every session with no memory of their past work. They re-read files, retry failed approaches, and forget root causes they established hours earlier. This is not a context-length problem but a memory-architecture problem. Our hypothesis: coding agents need persistent, experience-aware repository memory, so that knowledge survives from one session to the next. Three measurements on real repositories motivate the design. First, mid-size projects already exceed the largest production context windows, and storing knowledge inside the model's key-value (KV) cache costs $10^4$ to $10^5$ times more bytes than storing it as indexed text. Second, across 752 real bug-fix commits, the median fix edits two files, and these files plus their direct imports amount to less than 10% of the repository; the bottleneck is selection, not capacity. Third, even with transitive import reachability and test links, 47% of co-edited file pairs remain structurally disconnected; the knowledge needed for selection must be mined from history and experience. We sketch Stratum, a tiered memory that lives with the repository and serves it through page-safe tools: every response states what was returned, what remains, and what it cost. Retrieval over a store of one million nodes takes 1.7 ms at the median. In a multi-session experiment on eight real bugs, a fresh agent that inherited a prior session's memory, written by a different model, identified the root-cause file in 21 of 24 trials versus 6 of 24 for a retrieval-only baseline (Fisher $p<10^{-4}$), at 4.5x lower median token cost. With the notes of all eight investigations pooled in one store, success remained 8/8.

## 1. 核心问题与研究动机

- **问题定位**：尽管上下文窗口四年间从 2K 扩展到 1M tokens，编码智能体仍每次会话"从零开始"——重复读文件、重试失败方案、遗忘此前已确立的根因。作者主张这不是上下文长度问题，而是**记忆架构问题**。
- **核心假设**：编码智能体需要**持久、经验感知的仓库记忆**，使知识能跨会话、跨模型存活；应区分"模型能装下的"（已读 token 的注意力状态）与"智能体应记住的"（仓库、历史与自身经验）。
- **三项测量（F1–F3）支撑动机**：
  - **F1 模型驻留知识不可扩展**：Django 单仓库即 6.2M tokens，为最大生产上下文窗口的 6 倍；10 亿 tokens 以索引文本存约 4 GB，以 fp16 KV 状态存 70B 模型约 298 TB，差距 4–5 个数量级，且 KV 状态模型特定、换模型需重建。
  - **F2 直接连通工作集很小**：752 个真实 bug 修复提交中，中位修复仅改 2 个文件；加上一跳导入闭包仅占仓库代码 2.7%–9.9%，说明**瓶颈是选择而非容量**。
  - **F3 选择知识不在静态结构里**：852 个提交、3,695 个共改文件对中，仅 23.5% 有直接导入边，扩展至传递可达性与测试链接后仍有 **47.3% 结构不连通**；但共改对比随机对高 26 倍有导入边——另一半关系须从版本历史与经验中挖掘。

## 2. 方法论：STRATUM 设计

### 2.1 核心思想
- 类比数据库**缓冲池（buffer pool）**：大而廉价的冷存储 + 小而快的工作集 + 控制器在两者间调度；但记忆**驻留在开发者机器上、紧邻仓库**，而非模型或服务栈内部。
- 记忆分三类：
  - **结构化记忆**：文件、API、导入/测试边（解析重建）；
  - **历史记忆**：共改边、决策、设计理由（从 git 历史挖掘）；
  - **经验记忆**：失败尝试、根因、调试发现（由智能体写回）。

### 2.2 存储与控制器
- **冷层**：SQLite 知识图谱，节点为源文件、测试、研究笔记、决策、失败、根因发现；类型化边为 `imports`、`tests`、`similar`、`sources`、`co_changes`（持续从 git 历史挖掘）。
- 本地嵌入 + **HNSW 索引**做相似检索；文件监听器基于内容哈希差异重索引，并刷新共改统计。
- **驻留评分公式**：
  $$S(v) = w_1 G(v) + w_2 C(v) + w_3 H(v) + w_4 P(v)$$
  其中 $G$ 为与正在编辑文件的图邻近度，$C$ 为共改亲和度，$H$ 为时间衰减访问频率，$P$ 为显式 pin 优先级。作者明确将其定位为**研究假设而非已调优策略**。
- **驱逐策略**：按分数向下驱逐；pin 节点永不驱逐；编辑文件直接邻居保留接口级细节；其他温节点降级为一行摘要；其余回 SSD（<3 ms）。上下文余量低于 15% 时优先驱逐最大最冷节点并报告。

### 2.3 九个页安全（page-safe）工具
- 经 **MCP（Model Context Protocol）** 暴露：
  - 5 个读工具：`tree`（层级列出）、`search`（嵌入+关键词+时效）、`get`（按 summary/api/full 细节级分页返回）、`walk`（沿类型化边遍历）、`budget`（报告 token 用量）；
  - 1 个写工具：`remember`（持久化新知识节点）；
  - 3 个驻留控制：`pin`/`unpin`、`prefetch`、`evict`。
- **页安全契约**：每个响应是一个信封，携带内容、分页状态（`page`、`total_pages`、`has_more`）、剩余 token 预算与提示（如"Page 2/3; create() is on this page"），**绝不静默截断**，由智能体自行决定加载什么、何时停止。
- **写回闭环**：任务结束时持久化所学，下一会话（可能由不同模型运行）继承。

### 2.4 五条设计理由（R1–R5）
- R1 存文本与结构而非张量（小 10⁴–10⁵ 倍、可跨模型迁移；但嵌入需按编码器重算）；
- R2 让分页对智能体可见（长上下文存在"中间迷失"误用问题）；
- R3 学习边、保留失败（负知识被认为价值最高）；
- R4 面向 OS 式策略的语义信号（是否优于 LRU 是开放问题）；
- R5 与代码同生、与服务端前缀缓存组合。

## 6. 主要结论与发现

- **瓶颈是记忆架构而非上下文长度**：所需知识体量小（中位 2 文件）、约一半对静态分析不可见、且只有以文本形式存于代码旁才可负担。
- **表示成本**：文本 + 图比 KV 状态小 10⁴–10⁵ 倍，且天然跨模型可移植；KV 缓存工作与 STRATUM **互补而非竞争**（前者让当前轮更便宜，后者决定当前轮装什么）。
- **检索可行性**：10⁶ 节点存储中位检索 **1.70 ms**、P99 2.76 ms、两跳遍历 0.95 ms，远快于一次 LLM 轮次。
- **跨会话、跨模型迁移有效**：继承另一模型所写笔记后，reader 成功率 **21/24 vs. 6/24**（87.5% vs. 25%），中位输入 token 成本低 **4.5×**（43.3K vs. 196.6K）；池化 26 条笔记后仍 **8/8**，说明积累不损害检索。
- **全上下文对照**：C 成功率 14/16（与 B 的 87.5% 持平），但单次调用 164K tokens ≈ 整个记忆会话的 3.8 倍，成本每轮重复、无持久化，且对 Django 这类仓库（reader 窗口的 31 倍）不可行。
- **总体判断**：窗口扩大无法提供跨会话知识；持久经验化仓库记忆是可行且高性价比的替代路径。

## 7. 优点

- **问题重构有说服力**：用三项可复现测量把"上下文不够长"重新表述为"记忆架构缺失"，论证链条清晰（成本 → 容量 → 选择性）。
- **系统视角与软件工程视角结合**：将记忆层次（分页、驱逐、pin）与 MSR 经典技术（共改挖掘）融合，并把共改边做成任务中实时遍历的活边。
- **页安全契约设计新颖实用**：显式 `has_more`/`budget`/`hint` 把上下文变成智能体可推理的资源，直击检索管线静默截断与"中间迷失"问题。
- **负知识（失败/RCA）作为一等公民**：将"试过什么、为何失败"作为可链接的持久节点，是对现有 RAG 栈的差异化贡献。
- **实验设计的关键控制到位**：异模型 writer/reader、全上下文对照、池化积累测试、writer 全解验证，有效隔离了"迁移"这一被测变量。
- **坦诚的自我定位**：明确把 $S(v)$、语义驱逐、负知识价值标为待验证假设，并给出 RQ1–RQ5 研究路线与复现包。

## 8. 不足与局限

- **实验规模与外部效度**：E5 仅 8 任务、2 个小仓库，且为"重新诊断"而非"迁移到新任务"；结论难以直接外推到大型仓库或长周期开发。
- **基线偏弱**：检索基线为词法而非嵌入检索；未与"会话摘要继承"等更简单方案对比，可能高估经验记忆的增益。
- **统计与偏差风险**：E2/E3 仅分析 Python 文件；导入图构建于最新提交而分析的是旧提交，文件可能已移动；按 commit message 关键词筛选可能偏向描述良好的修复；一跳闭包只是所需上下文的代理，未对照开发者实际查阅的文件（留待 RQ2）。
- **E4 使用合成内容**：真实嵌入下的检索质量、控制器开销、索引新鲜度维护成本均未测量。
- **核心机制未验证**：语义驱逐策略 $S(v)$ 是否优于 LRU、负知识是否真能减少重复失败、跨框架迁移能力，均只有设想无实验。
- **应用限制与风险**：作者自承记忆卫生问题——**错误笔记会污染后续会话**，写回的网页内容构成**提示注入通道**；摘要保真度、团队共享存储的权限与一致性亦未解决。
- **资源披露不足**：未说明模型调用量、推理成本与硬件细节，复现成本难以评估。
