## 摘要
大语言模型（LLM）智能体工作于记忆需求差异很大的场景中。关于过往对话的问题需要其明确提及的精确事实，而多步任务需要已执行步骤的轨迹，以及下一步无法具体指明的细节。现有记忆各自针对一类场景进行设计与测试。诸如 A-Mem 的检索式记忆会遗漏当前查询未表达的步骤，摘要会丢失精确字符串，而将两者配对则预先固定了预算的划分。我们提出 FlexA-Mem，一种通用记忆，它将每个历史单元一次性写入不可变存储，并在每次调用时渲染出新的记忆。渲染出的记忆由紧凑的记录时间线以及细节组成，这些细节由固定规则填入剩余空间，无需调用 LLM。这些细节要么是作为原始文本或摘录的相关单元，要么是与查询最匹配的逐字片段。借助单一存储，FlexA-Mem 可服务两类场景。在 4k 预算下的 AppWorld 挑战任务上，它比第二优方法高出 11.5%；在 147 个未使用且预测提前固定的任务上，它比带摘要的 A-Mem 高出 12.2%。在 LongMemEval 和 LoCoMo 上，它与不写入任何记忆的专用关键词检索器相当，而基于 LLM 所写文本构建的记忆在预算紧张时远远落后。消融实验表明，时间线承载了 AppWorld 的完成能力，而恢复机制在该任务中主要节省步骤，并在精确事实问题上决定准确率。代码见 https://github.com/WujiangXu/Flex-Amem

## Abstract
Large language model (LLM) agents work in scenarios with very different memory needs. A question about past conversations needs the exact facts it names, while a multi-step task needs a trace of the steps already taken together with details that the next step cannot name. Existing memories are each designed and tested for one kind of scenario. Retrieval memories such as A-Mem miss steps that the current query does not express, summaries drop exact strings, and pairing the two fixes the split of the budget in advance. We propose FlexA-Mem, a general memory that writes each unit of history once into an immutable store and renders a fresh memory for every call. The rendered memory is a compact timeline of records plus detail that a fixed rule fits into the remaining room without an LLM call. The detail is either relevant units as raw text or excerpts or the verbatim pieces that best match the query. With one store, FlexA-Mem serves both kinds of scenario. On AppWorld challenge tasks at 4k, it outperforms the second-best method by 11.5%, and on 147 unused tasks with predictions fixed in advance it outperforms A-Mem with a summary by 12.2%. On LongMemEval and LoCoMo, it matches a dedicated keyword retriever that writes no memory, while memories built on text written by an LLM fall far behind at tight budgets. Ablations show that the timeline carries AppWorld completion, whereas recovery mainly saves steps there and decides accuracy on exact facts. Code is available at https://github.com/WujiangXu/Flex-Amem

# FlexA-Mem 论文结构化总结

## 1. 核心问题与研究动机

- **背景**：LLM 智能体需要在固定 token 预算下工作，历史很快超出单次调用容量，且模型对长上下文中部信息利用不可靠，因此“记忆决定预算里放什么”。
- **场景差异**：
  - 关于过往对话的事实问答：依赖查询明确指出的少量精确事实（日期、字符串等）。
  - 多步智能体任务：依赖“已做过什么”的轨迹概览，以及下一步无法用查询命名的细节（API 参数、早先输出）。
- **现有方法各自偏科**：
  - 检索式记忆（如 A-Mem）返回与查询最接近的笔记，适合事实召回，但会遗漏当前查询未表达的步骤（如“之前已登录”）。
  - 摘要/压缩保留轨迹概览，却丢失精确字符串。
  - Summary+A-Mem 等混合方案在写入时固定预算切分比例，无法随场景、任务步骤和预算变化。
  - MemGPT、Sculptor 等把细节交给工具，但智能体很少主动调用。
- **核心矛盾**：写入历史时无法预知未来查询与预算，因此“概览与细节如何平衡”不应在写时承诺，而应在每次调用时廉价决定。
- **论文主张**：提出 FlexA-Mem——**一次写入、每次调用重新渲染**的通用智能体记忆，用单一不可变存储同时服务“多步任务追踪”和“精确事实召回”两类场景。

## 2. 方法论

### 2.1 核心思想

- 每个历史单元只写入一次，原始文本永久保留、不可变、不被改写。
- 每次调用根据当前预算和查询，即时渲染出：
  - 一条紧凑的**记录时间线**（与查询无关，保留全局轨迹）；
  - 用固定规则把剩余预算分配给**恢复出的细节**（相关单元的原文/摘录，或全历史中最匹配查询的逐字片段）。
- 读取阶段除“合并记录”外**不调用 LLM**。

### 2.2 上下文与预算定义

- 第 t 次调用的上下文：\(C_t=[P_t;M_t;W_t]\)，且 \(|C_t|\le \bar B\)。
  - \(P_t\)：固定提示（指令、任务/问题）；
  - \(M_t\)：渲染出的记忆；
  - \(W_t\)：最近窗口，原样展示最新单元。
- 安全预算 \(\bar B=0.95B\)；记忆可用额度 \(A_t=\bar B-|P_t|-|W_t|\)。
- 时间线占用后剩余空间 \(R_0=A_t-\|T_t\|\)。

### 2.3 写入记忆

- 单元划分：智能体连续步骤打包为约 1,000 token 的单元；对话按用户轮次切为约 2,000 token 的 span。
- 单元离开最近窗口时写入笔记 \(m_i=(r_i,s_i,f_i,e_i,L_i,\Pi_i)\)：
  - \(r_i\)：原始文本，永不改变；
  - \(s_i\)：一次 LLM 调用生成的 ≤80 词记录；
  - \(f_i\)：关键词、标签、简短描述等检索字段；
  - \(e_i=\phi(s_i\|f_i)\)：句向量；
  - \(L_i\)：与 embedding 余弦最相似的三条更早笔记的双向链接；
  - \(\Pi_i\)：按行断开、每片 ≤κ token 的片段。
- 关键设计：**从不重写笔记**，因为后续调用可从原始文本恢复细节，重写邻居只增加成本而不增加信息。

### 2.4 记录时间线

- 每次调用展示按时间排序的记录 \(T_t\)，形成智能体“做过什么”的紧凑轨迹。
- 时间线过长时，从最旧开始，每次最多合并 4 条连续记录为一条 LLM 生成的合并记录；合并结果缓存复用。
- 合并条件：\(\|T_t\|>\max(\rho A_t,\ A_t-D_t)\)，其中 \(D_t\) 为把所有候选按原文展示的总成本。
- 智能体任务中，若最新单元单独占用超过 1/4 预算，则本次调用临时隐藏最旧记录。

### 2.5 单元恢复（面向智能体）

- 查询嵌入：智能体用“任务 + 最新单元”的归一化嵌入和；读者用问题嵌入。
- 候选生成：
  - 余弦相似度最高的 k 个种子；
  - 种子的链接邻居与时间相邻单元；
  - 得分 \(g_t(j)=\max\{\lambda^{[i\ne j]}c_t(i): i\in S_t,\ j\in\{i\}\cup L_i\cup N_i\}\)，\(\lambda<1\) 对经链接/时间到达的单元打折。
- 分辨率从高到低：**原文 raw ≻ 摘录 excerpt ≻ 记录 record**。
- 展示成本：
  - 若仅显示记录：成本为 0；
  - 否则成本为“该分辨率文本长度 − 记录仍独立存在时已占的长度”。
- **Fit-or-degrade 规则**：按候选得分顺序，给每个候选“仍能放下的最高分辨率”；记录永远放得下；原文放不下时退化为与查询最匹配的逐字摘录，而不是直接退回记录。
- 摘录 = 记录 \(s_i\) + 按 BM25 排序、总长 ≤ E 的原文片段，保持原顺序，逐字保留。
- 更相关的单元不会被降级来给较不相关的单元让位；预算越小，越多单元自动变为摘录。

### 2.6 片段恢复（面向事实问答）

- 对全历史所有片段按 BM25 排序，按顺序装入 \(R_0\)。
- 选中片段跟在时间线之后，按单元分组、按时间排序。
- 时间线只保留其份额 \(\rho A_t\)，未用完的份额借给片段；一个单元可贡献多个片段，适合证据分散在多次会话的情况。

### 2.7 恢复模式选择

- 智能体任务 → 单元恢复（保留每个细节周围上下文）；
- 历史事实问答 → 片段恢复（只把预算花在匹配文本上）。
- 模式按任务类型设定，**不在运行时按查询自适应选择**；作者明确将其列为未解决问题。

## 6. 主要结论与发现

- **智能体任务**：
  - AppWorld Test-Challenge 4k 下比次优方法 ReadAgent 高 **11.5%**（p<0.001），6k 高 7.7%；
  - 6k 下与完整历史基本持平（62.4% vs 62.1%）；
  - 147 个未用任务 4k 下比最强基线 Summary+A-Mem 高 **12.2%**（Holm 校正 p=0.006），与完整历史差异不显著。
- **事实召回**：
  - LongMemEval 上片段恢复与不写记忆的 BM25 关键词检索器差距 ≤0.7%；
  - 4k 下比 A-Mem

- 4k 下比 A-Mem 等写入式记忆系统明显更高，且在 4k–32k 预算范围内保持较稳定的准确率；预算增大时收益主要来自可恢复更多逐字证据，而非依赖更长的记录。
  - LoCoMo 上同样表现出“预算越紧、相对优势越明显”的趋势；在 2k/4k 等低预算设置下，片段恢复比摘要式或固定比例混合方案更能保留答案所需的关键字符串。
  - 事实问答场景中，FlexA-Mem 的核心优势不是“记住更多”，而是“在预算内把匹配查询的原文片段排到前面”，因此与纯 BM25 检索的差距很小，但显著优于会改写/压缩原始证据的记忆系统。
- **成本与效率**：
  - 读取阶段除时间线合并外不调用 LLM，因此每任务 token 成本显著低于 A-Mem、Summary+A-Mem 等需要频繁写入/重写或额外 LLM 调用的方案。
  - 写入成本为每单元一次记录生成调用，整体随历史长度线性增长；由于原始文本永久保留，后续调用可通过规则恢复细节，避免反复改写邻居带来的额外开销。
- **消融结论**：
  - 去掉记录时间线会损害多步智能体任务，说明“全局轨迹概览”对步骤追踪不可替代。
  - 去掉单元恢复或把恢复退化为仅记录，会显著降低智能体任务表现；说明原始文本/摘录的按需恢复是精确细节的主要来源。
  - 去掉链接、摘录、fit-or-degrade 均造成不同程度下降；其中 fit-or-degrade 在低预算下尤其关键，因为它避免“相关单元因放不下原文而直接消失”。
  - 随机候选、随机顺序、时间线后再选等变体均不如原方法，支持“先按相关性排序、再按预算逐级降级”的设计。
  - A-Mem + fit-or-degrade 仍不及 FlexA-Mem，说明收益不仅来自预算分配规则，也来自“不可变原始存储 + 时间线 + 双恢复模式”的整体结构。

- **恢复模式需预先指定**：智能体任务用单元恢复、事实问答用片段恢复，但运行时不会根据查询自适应选择；混合型任务（既需轨迹又需精确事实）可能不是最优。
- **依赖任务类型标注**：模式选择按任务类型设定，实际部署中若任务边界模糊，需要额外启发式或分类器。
- **时间线合并仍调用 LLM**：虽然读取阶段大部分是规则操作，但长时间线下合并记录会产生 LLM 调用，带来延迟与成本。
- **写入记录质量影响检索**：记录 \(s_i\) 和检索字段 \(f_i\) 由一次 LLM 调用生成，若记录遗漏关键实体，可能影响种子召回；不过原始文本和片段恢复可部分缓解。
- **评测盲测程度有限**：最终方法在看过部分主实验结果后设计，只有 147 个未用 AppWorld 任务做了预测固定确认；LongMemEval 聚合结果也被用于设计片段恢复规则，因此并非完全预注册盲测。
- **运行方差与基线调优**：部分配置只跑一次，AppWorld 两次运行差异可达 4.8%，一些领先幅度小于该波动；部分基线只在子集上运行或阈值经开发集校准，存在比较偏差风险。
- **未报告算力硬件**：论文只报告 token 成本，未给出 GPU 型号、数量、训练/推理总时长，难以从算力角度复现或横向比较。
- **长历史下的写入开销**：每单元一次 LLM 调用在超长历史中仍是线性成本；论文未深入讨论写入阶段的缓存、批处理或增量优化。
- **多模态/工具状态记忆未覆盖**：方法主要面向文本历史；对图像、结构化工具状态、外部数据库变更等场景的适用性未验证。

## 8. 启发与可迁移设计

- **“写时保守、读时灵活”**：不要在写入时固定概览/细节比例，而是永久保留原始证据，在每次调用时按预算重新渲染。这一原则可迁移到 RAG、对话记忆、代码智能体日志管理等场景。
- **不可变存储 + 多分辨率视图**：同一单元可被渲染为记录、摘录、原文三种分辨率，按相关性和剩余预算逐级降级；比“摘要后丢失原文”更适合需要精确字符串的任务。
- **时间线作为低成本全局索引**：一条紧凑记录时间线能以很小预算提供“做过什么”的轨迹，弥补纯相似度检索对未表达步骤的遗漏。
- **fit-or-degrade 的预算分配思想**：先保证高相关候选以最高可行分辨率进入上下文，再考虑低相关候选；比固定长度截断更符合“预算有限但证据价值不均”的现实。
- **双模式恢复的工程取舍**：智能体任务保留细节周围上下文，事实问答只装匹配片段；这种按任务类型分派恢复策略的做法，比单一通用检索器更容易调优。
- **评测建议**：对记忆系统应同时报告任务完成率、事实准确率、token 成本、运行方差和预注册确认结果；仅报告单一 benchmark 或单次运行容易高估收益。

## 9. 总体评价

FlexA-Mem 的核心贡献在于把“记忆写入”与“上下文渲染”解耦：写入阶段只做一次低成本记录并永久保留原文，读取阶段用规则化预算分配和时间线合并，在固定 token 预算下同时服务多步任务追踪与精确事实召回。方法设计简洁、免训练、工程可落地，且在 AppWorld、SWE-bench、LongMemEval、LoCoMo 上覆盖了较广的预算与模型组合。实验上，智能体任务的提升较有说服力，尤其是低预算和未用任务确认实验；事实问答场景则更多体现为“不劣于强检索基线、显著优于压缩式记忆”，而非全面碾压。主要保留在于最终方法并非完全预注册盲测、部分配置运行次数有限、基线调优程度不一，以及恢复模式仍需按任务类型预先指定。总体而言，这是一篇问题定义清晰、设计原则明确、实验较扎实的记忆系统论文；其“不可变原始存储 + 按调用重渲染 + 多分辨率降级”的思想比具体数字更具迁移价值。
