## ABSTRACT 

Deploying LLM agents in specialized domains often require fine-grained task-specific procedures and knowledge a general model lacks, yet parameter training is costly and non-interpretable, and hand-engineered agent systems shift the cost to expert labor. Episodic memory updates at context level, but single agent adaptation struggles to alleviate cross-task interference, especially with complex tasks such as multi-application navigation or data pool analysis. Although multi-agent evolution alleviates this problem, existing methods lack clear definitions on update rules and rely on the backbone model to decide where and how much the system changes. This ill-scoped evolution makes learning follow the backbone’s structural preferences rather than the observed failures: one backbone accumulates skills while another spawns agents. We present EMMA (structured Episodic Memory for Multi-Agent workflow synthesis), which treats the configuration of a multi-agent system (controller routing memory, specialists inheriting a generalist prompt, and per-step procedural skills) as episodic memory. EMMA makes the ownership and admissibility of updates explicit: a reflector assigns each diagnosed failure to the scope owning its correction and proposes one edit within it, and backbone-independent guards keep every accepted edit scoped, incremental and bounded. Across KramaBench, AppWorld and BBEH with five backbones and four baselines (ACE, GEPA, EvoMAS and ADAS), EMMA attains the best overall performance on every benchmark, up to 32.5% over the strongest baseline, maintains consistent improvements across backbones, and uses 17–38% fewer training executions than the most efficient baseline. 

## 1 Introduction 

Deploying LLM agents in specialized domains demands more than general capability. Real-world applications such as data-to-insight pipelines and multi-application tasks require tailored conventions and procedures that a general model does not possess [Lai et al., 2026, Trivedi et al., 2024]. Two mechanisms are conventionally used to supply such knowledge, and each incurs a distinct cost. Parameter training, whether supervised fine-tuning or reinforcement learning under objectives such as GRPO and DAPO [Shao et al., 2024, Yu et al., 2025], is computationally expensive and yields an artifact that can be neither inspected nor selectively corrected. Human engineering of agent systems avoids that cost but transfers it to expert labor: hand-specified roles and topologies perform well [Du et al., 2024, Hong et al., 2024, Li et al., 2025] but must be re-authored for every new domain. Episodic memory offers a more efficient mechanism, in which the experience of solving a task is persisted as text and reused on later tasks with the model weights held fixed. Reflexion, A-Mem and MemRL store retrievable reflections, notes and utility-ranked entries [Shinn et al., 2023, Xu et al., 2025, Zhang et al., 2026a], while ACE and GEPA adapt the context of a ReAct-style agent, as an accumulating playbook and as a reflectively optimized prompt [Zhang et al., 2026b, Agrawal et al., 2026]. Both use a single generic agent and adapt only its context. Complex applications such as data lake analysis, however, involve thousands of files from various sources [Lai et al., 2026]. EMMA achieves the best mean performance on every benchmark, improving over the strongest baseline by up to 32.5%, while ranking first in 17 of 20 settings and using the fewest training executions.

## 3 EMMA: Structured Episodic Memory for Multi-Agent Workflow Synthesis 

EMMA instantiates Definition 1 with a memory whose entries are the configuration of the multi-agent system of Section 2.2. Section 3.1 describes the architecture that reads this memory, Section 3.2 the training procedure that writes it, and Section 3.3 summarizes training and inference. 3.1 Architecture 

As shown in Figure 2, EMMA consists of a controller, a persistent episodic memory, and a task-local execution environment. The memory persists across tasks and is written only during training; the execution environment is created for each attempt and discarded afterwards.

Each entry carries a topic, a summary, domain tags and a generality label (general, domain-specific or task-specific). Rather than retrieving by similarity, the controller reads this index and chooses which entries to load for the current task; loading none is a valid choice, since irrelevant memory degrades planning. The skill pool S holds short procedures for classes of sub-problems (an algorithm, a rule system, a pitfall checklist, a format convention), indexed by a one-line “when to use” description. The controller sees only the index and assigns skills per step; the sub-agent receives their full text. The three levels answer different questions: C, how the task is divided and routed ; the agent prompts, how an agent works on any subtask ; and S, how a class of sub-problem is solved . This separation gives every lesson a single home, which the training procedure in §3.2 exploits. 

3.1.2 Step-Wise Synthesis with Overflow Decomposition 

Given a task, the controller loads its selected memory and emits an ordered plan in which each step names an agent, a subtask and the skills to assign. It dispatches one step at a time (Eq. 2), reads the output, and then continues, revises the remaining steps, or terminates. Each sub-agent receives the task, its subtask, its skills and a controller-curated summary of earlier outputs, which keeps context small while passing on what the step needs. A step may exhaust its sub-agent, by filling the context window or by running out of rounds. EMMA reads this as evidence that the subtask was specified too coarsely, not that the agent failed, and applies overflow decomposition : the controller uses the partial trace to split the unfinished step into smaller steps over existing agents, splices them into the plan, and resumes at the same position with completed work preserved. Every overflow is also recorded as evidence for the reflector; the full procedure is given in Algorithm 2 in Appendix A.

What the reflector sees. Unlike a scalar fitness, the reflector receives the whole trajectory of the failed attempt: the plan, the code each sub-agent issued, the evaluator’s explanation of the failure, the history of earlier revisions of this task, the full prompts of the agents that ran, the assigned skills, and any overflow events. It may also inspect the full execution log of selected steps. 

What it decides. As shown in step 3 of Figure 3, the reflector follows a fixed four-step procedure. It localizes the step where the outcome went wrong; classifies the failure into one of the five scopes listed in Table 1; generalizes the correction so that it applies to every task of the same kind, naming no entity or answer of this one, as the reflector’s generalization instructions require; and minimizes it to the smallest change within the lesson’s designated scope. It then outputs exactly one action. These ownership rules make the update scoped: each failure scope z ∈ Z has a set of available actions Act( z), which edit only the part of the memory that owns the correction. A one-off execution_slip 

is never written to durable memory; a failed working habit ( agent_behavior ) is written into a prompt, in p0 if it is general and in a specialization if it is role-specific; a wrong or missing method ( procedure ) into a skill; and a wrong decomposition or dispatch ( routing ) into controller memory. New agents are reserved for work that no agent can do or that repeatedly overflows one agent. 5EMMA: Structured Episodic Memory for Multi-Agent Workflow Synthesis 

3.2.2 Guarded Update 

As shown in step 4 of Figure 3, a proposed action is applied only if it passes a set of programmatic guards, which depend on the memory, the task and the revision history but never on the backbone: scope–action compatibility , the action is one of the available actions Act( z); prompt preservation , a prompt change keeps most of the existing prompt and may only touch an agent that ran in the failed attempt; bounded memory growth , the agent and skill pools and every entry stay within fixed sizes, and a new agent must be a genuine specialization rather than a duplicate or a label; 

no leakage , no artifact may contain the reference answer or copy a span of the task text; and change of strategy , no memory level is edited in more than two consecutive failed revisions, and if the same step overflows twice in a row, the action must change how the work is split. A refused proposal returns its reason to the reflector, which tries again; persistent refusals default to no change. A newly created or revised skill or agent is named in the re-run’s plan, so the edit is actually exercised. Together, the scoped update and the guards fix the envelope of learning: every accepted edit touches one entry within its designated scope, is incremental, and keeps the memory bounded, whichever backbone proposed it. The backbone decides which available edit to make, so a stronger model can still learn better memory, but no backbone can make a larger, misplaced or destructive one, so what is learned follows the training feedback rather than the backbone’s habits. Multi-agent search methods lack such an envelope, since the meta-model proposes a whole new configuration; as Figure 1a shows, when the update is ill-scoped even the kind of edit becomes a backbone habit. 

3.3 Training and Inference 

As stated in Algorithm 1 in Appendix A, training makes a single pass over the training set in a fixed order, running one attempt chain per task; accepted edits persist regardless of the re-run’s outcome. After each chain, one chain-aware controller update records a few routing lessons, and the memory is snapshotted. After the pass the memory is frozen, one artifact per benchmark and backbone, with no checkpoint selection. At inference on held-out tasks, the controller keeps memory selection, replanning and overflow decomposition, but no reflector is called and nothing is written. 

## 4 Related Work 

LLM-based multi-agent systems. Hand-designed systems such as ChatDev [Qian et al., 2024], MetaGPT [Hong et al., 2024], AutoGen [Wu et al., 2024], debate and mixture-of-agents topologies [Du et al., 2024, Xu et al., 2023, Li et al., 2025] and Magentic-One [Fourney et al., 2024] established role specialization and orchestration, but remain task-specific and carry a coordination cost [Cemri et al., 2025, Tran et al., 2025, Wang et al., 2025a, Zhang et al., 2025b, Li, 2026]. Automatic design treats the system as code to search, as in ADAS [Hu et al., 2025] and MAS-GPT [Ye et al., 2025]; optimizes its structure, as in GPTSwarm [Zhuge et al., 2024], AFlow [Zhang et al., 2025a], AgentSquare [Shang et al., 2025], AutoAgents [Chen et al., 2024] and generated topologies [Li et al., 2026a]; or evolves agents and whole configurations, as in EvoAgent [Yuan et al., 2025] and EvoMAS [Hu et al., 2026]. As discussed in Section 1, these methods let the backbone propose whole candidates, with safeguards for executability or novelty rather than for the scope of a change (Appendix D.1), which makes what they learn sensitive to backbone behavior; EMMA instead admits one guarded edit within a diagnosed scope. 

Episodic learning and procedural memory. Reflexion [Shinn et al., 2023], TextGrad [Yuksekgonul et al., 2024], MIPRO [Opsahl-Ong et al., 2024] and GEPA [Agrawal et al., 2026] improve agents from natural-language feedback on traces; Dynamic Cheatsheet [Suzgun et al., 2026], A-Mem [Xu et al., 2025], Agent Workflow Memory [Wang et al., 2025b], MemRL [Zhang et al., 2026a] and ACE [Zhang et al., 2026b] accumulate a store, ACE through incremental curation that avoids collapse under wholesale rewriting. Skill libraries study how procedures are authored [Zhou et al., 2026, Liu et al., 2026], selected [Li et al., 2026b] and routed [Zheng et al., 2026, Li, 2026]. These serve a fixed, usually single ReAct agent [Yao et al., 2023]; EMMA stores a multi-agent configuration and extends incremental updating with a level hierarchy and deterministic guards.

5.2.2 Update Efficiency 

As reported in Table 4, EMMA achieves the best mean performance with the fewest training executions on every benchmark , 17–38% fewer than the most efficient baseline. EMMA re-runs only failed tasks, and each re-run tests one localized, guarded edit. This result demonstrates that these updates are on-point: each training execution yields a targeted correction rather than a speculative restructuring, which maximizes learning efficiency over the baselines. 

5.3 Ablation Studies 

All ablations are conducted on KramaBench with Claude Opus 4.5 [Anthropic, 2025], under which full EMMA attains 0.647; Table 5 reports all compared configurations. 

Memory levels. This ablation asks whether treating the multi-agent configuration as memory contributes beyond what a fixed system can learn. Controller memory is learned in every arm, while the skill and agent pools are either kept at their initial state or learned. Learning procedural skills accounts for the larger of the two gains, which indicates that much of the transferable knowledge concerns how recurring classes of sub-problems are solved. Learning the agent pool as well brings a further gain (0.591 to 0.647), showing that specialized agents capture knowledge that skills alone do not, and supporting our premise that the structure of the system, not only its context, should be learned. Because controller memory is present in all arms, its individual contribution is not isolated. 

Episodic learning vs. test-time adaptation. This ablation asks whether the gains stem from memory learned on training tasks rather than from adaptation on the evaluated tasks themselves. We compare EMMA with within-task reflection (DACode, Reflexion and smolagents DeepResearch; Huang et al., 2024, Shinn et al., 2023, Roucher et al., 2025), which revises a solution within one trajectory, and with EvoMAS applied as cross-task self-evolution on the test split without ground truth. All test-time variants remain well below EMMA, indicating that corrections derived from verified training failures transfer to held-out tasks more effectively than additional adaptation at test time. As these arms 8EMMA: Structured Episodic Memory for Multi-Agent Workflow Synthesis also differ in feedback access and adaptation split, the comparison supports the transfer of learned memory rather than isolating persistence alone. 

Case study: what training produces. In the Sonnet 5 run on BBEH, a single failed zebra puzzle led to three artifacts, each written at the level that owns it: a constraint-satisfaction skill, a specialist agent created from overflow evidence, and a routing rule in controller memory. Subsequent zebra tasks were solved on the first attempt, and a held-out puzzle was solved and verified unique in a single dispatched step (Appendix F). This illustrates how scoped updates distribute one lesson across the memory hierarchy and how the resulting artifacts are reused. 

## 6 Conclusion and Limitations 

In this paper, we present EMMA, structured Episodic Memory for Multi-Agent workflow synthesis, which treats the configuration of a multi-agent system (controller routing memory, inheriting agents and procedural skills) as episodic memory and updates it only within the scope of each diagnosed failure, through a single edit that passes backbone-independent guards. The experimental results show that EMMA achieves the highest mean performance on every benchmark and split across five backbones from two model families, ranks first in 17 of 20 benchmark–backbone settings, and uses the fewest training executions, while the multi-agent search baselines degrade sharply on open-weight backbones. These results indicate that scoped, guarded updates let what is learned follow the training feedback rather than the backbone’s structural preferences. Despite these advantages, EMMA narrows but does not eliminate the performance gap between backbone families, and pairing a strong reflector with weaker executor agents is a natural way to exploit this. In addition, accepted edits persist even when an attempt chain ends unsolved; we observed no systematic degradation, but ineffective or harmful entries may remain, and cross-verification on mini-batches or multiple epochs could identify them. We consider both directions as future work. 9EMMA: Structured Episodic Memory for Multi-Agent Workflow Synthesis

## D Baseline Methods 

All four baselines in the main comparison learn persistent artifacts from training feedback and freeze them for evaluation. DACode, smolagents DeepResearch and Reflexion appear only in the ablation of Section 5.3. 

ACE [Zhang et al., 2026b] grows a playbook of identified bullets for a fixed ReAct agent with code execution. A generator solves the task with the playbook in context, a reflector tags bullets as helpful or harmful, and a curator applies incremental edits; the playbook with the best validation accuracy is frozen. Feedback is answer correctness on KramaBench and, on AppWorld, the no-ground-truth mode in which the reflector sees only unit-test pass/fail and the trace. 

GEPA [Agrawal et al., 2026] evolves the prompt texts of a compound system. Candidates are evaluated on training mini-batches; a reflection model reads the traces and rewrites one component; a Pareto front over validation tasks (drawn from the training split) selects survivors. Feedback is the benchmark metric plus the execution traces. 

EvoMAS [Hu et al., 2026] evolves complete multi-agent configurations (topology, prompts, models, tools) by meta-model selection, mutation and crossover for three steps, keeping successful configurations in an experience memory. In the main comparison the reward is the dataset evaluator (oracle mode) minus a token-and-latency cost term, and the best configuration and memory are frozen. The separate EvoMAS arm of Table 5 adapts on test tasks through self-reflection without ground truth. 

ADAS [Hu et al., 2025] has a meta-agent write complete agent programs in code, evaluates each on the training split, and keeps an archive that conditions the next proposal, with a budget matched to GEPA. The best archived program is frozen; where no discovered program beat the hand-written seed (DeepSeek v3.2 and Kimi-K2.5 on AppWorld), the seed is reported. 15 EMMA: Structured Episodic Memory for Multi-Agent Workflow Synthesis 

D.1 Update Constraints in Learned Baselines 

Table 10 compares how each method constrains a single update, as described in the respective papers [Zhang et al., 2026b, Agrawal et al., 2026, Hu et al., 2026, 2025]. “Not described” means that the paper specifies no such mechanism. The two multi-agent search methods leave both the locus and the magnitude of a change to the backbone: ADAS checks a proposal only for novelty (two self-reflection steps) and executability (up to five debugging rounds), and EvoMAS restricts a mutation to one component type (prompts, models, tools or topology) but not how much of that component changes. You specialize in building and solving LARGE constraint-satisfaction problems (CSP), such as logic-grid/zebra puzzles with many categories and many numbered clues, using OR-Tools CP-SAT or equivalent. Working method: 1. Never attempt to transcribe the source, encode every constraint, solve, AND debug infeasibility inside a single call. Split the work yourself into checkpointed phases and persist state to files between phases: (a) transcribe categories/values and clue text once, save verbatim; (b) build one small set of well-tested helper functions per relational pattern (identity, negation, adjacency, ordered-between, at-end, fixed-position) and unit-test each on a tiny toy example before using it; (c) encode constraints in fixed-size batches (e.g. 25-40 clues at a time), saving the partial model/constraint list to a file after each batch so later batches or later steps can resume without re-deriving; (d) only after all batches are encoded, solve once. 2. Track your round budget explicitly. ## Zebra/logic-grid CSP encoding and verification (CP-SAT or equivalent) 1. UNIQUE NAMES PER CATEGORY: give every value a name unique across ALL categories (e.g. prefix with category), never reuse a bare word like 'biking' in two different categories (hobby vs activity). Category-value collisions silently corrupt constraints and are a common source of false INFEASIBLE. 2. PIN DOWN PRIMITIVES ONCE, THEN REUSE: before encoding any clue, write exactly one helper function per relational pattern actually used by the clues (identity/'is the', negation/'is not', 'immediately left/right of' as pos(A)+1==pos(B), 'next to'/'adjacent' as |pos(A)-pos(B)|==1, 'X is somewhere in between A and B in that order' as pos(A)<pos(X)<pos(B), 'at one of the ends', fixed absolute position references like 'the person at position K'). Test each helper on a tiny 2-3 variable toy example that has a known expected SAT/UNSAT outcome before applying it to all clues. 3. ENCODE ALL CLUES IN ONE PASS, VERBATIM: extract literal clue text once, then encode every clue directly against its exact wording using only the verified helpers from step 2. Do not re-interpret or 'improve' phrasing case by case. 4. TREAT A FIRST INFEASIBLE AS A BUG SIGNAL, NOT A PUZZLE FACT: these puzzles are constructed to be satisfiable. If the full model reports INFEASIBLE, do NOT start dropping/relaxing individual clues as if some clue is 'wrong' -- that treats an assumed defect in the puzzle as ground truth. Instead: (a) recompute the unsat core, (b) for every clue in the core, re-derive its encoding from the literal text completely independently (fresh helper call, fresh mental parse) and diff against the original encoding, (c) specifically re-check direction (which side is 'immediately left' vs 'right'), identity vs adjacency conflation, and any off-by-one in absolute position indices. Fix any mismatch found and re-solve the FULL model (not a dropped-clue variant). Only conclude a clue is genuinely unsatisfiable with the rest after this re-audit still reproduces the same minimal core with all encodings independently re-verified as literal-correct. 5. VERIFY UNIQUENESS ONLY AFTER SAT: once SAT, re-solve with the found full assignment excluded (add a blocking clause) to confirm UNSAT (unique solution) before reporting any derived attribute as the final answer. If a second solution exists, the model is underconstrained -- check for an unencoded or misencoded clue. 6. BUDGET DISCIPLINE FOR LARGE PUZZLES: encoding 100+ clues and solving is one continuous task; do not spend rounds re-deriving the same helper twice. If you are more than half your round budget in without a completed, verified SAT solve, stop broad exploration (e.g. stop trying clue-drop variants) and instead do the targeted re-audit in step 4 on the actual unsat core -- this converges faster than guessing which clue to relax.
