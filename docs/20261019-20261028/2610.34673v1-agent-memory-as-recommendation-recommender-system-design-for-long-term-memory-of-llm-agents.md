## 摘要
在多个会话中服务用户的大语言模型（LLM）智能体，必须在每次请求时挑选少量存储记忆送入有限的上下文窗口。这一选择在很大程度上决定了智能体能否正确作答，并且在网络规模下每次请求都要执行。该选择面临三重挑战：记忆库规模庞大且持续增长、每次请求的成本预算，以及需要全部证据的多会话问题。许多记忆系统在每条历史记录上耗费数百至数千次 LLM 调用来构建笔记或图结构，且各自独立设计，因此难以确定究竟是哪个组件带来了准确率。这些挑战与推荐问题的特性相仿，因此我们将智能体记忆形式化为带预算的列表推荐：请求即用户，存储记忆即物品，上下文窗口即推荐列表。该形式化将各类记忆系统纳入统一的推荐级联设计空间，并将准确率分解为各阶段所控制的信息完备度。在此指导下，我们提出 AgentMemRec，它借鉴推荐系统中的候选生成、排序学习与列表构建方法，在无需任何 LLM 调用的情况下完成记忆选择。在 LongMemEval 的多会话问题上，AgentMemRec 的准确率比 A-Mem、HippoRAG 2、DynamicRAG 和 T-Mem 等记忆与上下文选择方法高出 10 至 31 个百分点。其效果与每次查询需 64 次调用的 LLM 重排序器相当，而服务成本降低 3.2 倍；在 LoCoMo 上，它在写入阶段无需任何 LLM 调用即优于 Mem0 和 Zep。该分解表明，性能提升源于推荐列表更常包含全部证据，因此推荐系统设计为 LLM 智能体的长期记忆提供了有效且高效的基础。

## Abstract
Large language model (LLM) agents that serve users across many sessions must choose, for every request, the few stored memories that enter a limited context window. This choice largely decides whether the agent answers correctly, and it runs on every request at Web scale. This selection faces three challenges: a large and growing store, a per-request cost budget, and multi-session questions that need all of their evidence. Many memory systems build notes or graphs with hundreds to thousands of LLM calls per history, and each is designed on its own, so it is unclear which component yields the accuracy. These challenges mirror the properties of recommendation, so we formalize agent memory as budgeted slate recommendation, with the request as the user, stored memories as items and the context window as a slate. The formalization places memory systems in one design space of recommender cascades and factorizes accuracy into the completeness that each stage controls. Guided by it, we propose AgentMemRec, which adapts candidate generation, learning to rank and slate construction from recommender systems and selects memories without any LLM call. On multi-session questions of LongMemEval, AgentMemRec outperforms memory and context-selection methods, including A-Mem, HippoRAG 2, DynamicRAG and T-Mem, by 10 to 31 points of accuracy. It matches an LLM reranker that makes 64 calls per query at 3.2 times lower serving cost, and on LoCoMo it outperforms Mem0 and Zep without any LLM call at write time. The factorization attributes the gains to slates that more often hold all of the evidence, so recommender-system design offers an effective and efficient foundation for the long-term memory of LLM agents.

## 1. 核心问题与整体含义

- **研究背景**：面向 Web 的聊天助手需要为每位用户维护跨会话的长期记忆。每次请求时，LLM 智能体必须从持续增长的记忆库中挑选少量记忆送入有限的上下文窗口（约 2,700 tokens），而这一选择在很大程度上决定回答是否正确。
- **三重挑战**：
  - **记忆库规模大且持续增长**：LongMemEval-M 单条历史约 500 个会话、150 万 tokens，而回答模型最多只读 2,700 tokens。
  - **每请求成本预算**：选择器在每次请求上运行，用 LLM 给整个记忆库打分，成本会随库规模与流量线性增长。
  - **多会话证据需齐全**：问题的证据可能分散在多个会话中，缺少任一证据 turn 会使 Qwen 准确率下降 37–64 个点；反馈只针对整个上下文，而非单条记忆。
- **现有方法的困境**：HippoRAG 2、A-Mem、T-Mem 等系统用数百至数千次 LLM 调用构建笔记、图或时间层级，但各自独立设计，难以判断哪个组件真正贡献准确率；且这些方法在仅 0.50–0.68 的多会话问题上能集齐全部证据。
- **核心洞察**：上述三属性与推荐系统高度同构——请求即用户、记忆即物品、上下文窗口即推荐列表（slate）。论文据此将智能体长期记忆形式化为**预算受限的列表推荐**，并在此统一框架下重新设计记忆选择。

## 2. 方法论

### 2.1 形式化框架

- **问题定义**：请求 \(x=(q,t_q)\)，目录 \(I(x)=H(q)\) 为带日期的会话 turn 集合，成本为渲染后 token 数 \(c=\text{tok}\circ\text{render}\)，奖励 \(u(S,q)\) 为评判器接受答案的概率。目标是最大化期望奖励，同时满足每请求 token 预算 \(B\)。
- **设计空间**：任何记忆系统可表示为四元组 \(d=(\varphi,g,f,h)\)：
  - \(\varphi\)：写时映射（构建记忆单元及附属信息）；
  - \(g\)：候选生成，返回候选池 \(P(q)\)；
  - \(f\)：排序器，对池内单元排序；
  - \(h\)：列表构建，在预算内选出 \(S_B(q)\subseteq P(q)\)。
  - LLM 成本按 \(\varphi\) 的每历史调用与 \(g,f,h\) 的每请求调用分别计量。

### 2.2 三个理论结果

- **命题 3.3（阶段分解）**：\(\text{Acc}(\pi)=a_i+(a_c-a_i)\,r_{\text{pool}}\,r_{\text{rank}}\)，其中 \(r_{\text{pool}}=\Pr[G\subseteq P]\) 为池完备性，\(r_{\text{rank}}=\Pr[G\subseteq S_B\mid G\subseteq P]\) 为排序完备性，\(a_c,a_i\) 分别为完备/不完备列表上的平均奖励。该式把准确率归因到各阶段，且 \(r_{\text{slate}}\le r_{\text{pool}}\) 给出池的上界约束。
- **命题 3.4（归约到逐项排序）**：在奖励不依赖列表组成、单元成本可加、各单元独立属于 gold 的概率为 \(p_v\) 的假设下，预算内最大化期望奖励等价于 0-1 背包，物品价值为 \(-\log(1-p_v)\)；等成本时最优列表即按 \(p_v\) 降序选取。这将概率排序原则从单文档推广到预算下的完备证据集。
- **命题 3.5（填充与截断）**：贪心填充沿排序走，加入所有仍能放下的单元；任何满足预算的前缀都包含于填充结果。若奖励在“前缀→填充”之间不下降，则填充不劣于任何逐问题截断。

### 2.3 设计问题与 AgentMemRec

- **设计目标**：\(\max_{\varphi,g,f}\ r_{\text{pool}}(\varphi,g)\cdot r_{\text{rank}}(f\mid\varphi,g)\ \text{s.t.}\ \text{LLMcost}(d)\le L\)。池宽同时影响两因子（更宽提升 \(r_{\text{pool}}\) 但引入更多干扰），每个坐标的 LLM 调用只在其能提升乘积时才值得。
- **AgentMemRec 在 \(L=0\) 下的实例化**：
  - **候选生成（提升 \(r_{\text{pool}}\)）**：BM25 词法通道 + bge-m3 稠密余弦通道，用 RRF（\(k=60\)）融合，取 top \(N=128\)；池大小由开发集上 \(r_{\text{pool}}r_{\text{rank}}\) 乘积选定（128 的 0.912 优于 64 的 0.879）。
  - **学习排序（提升 \(r_{\text{rank}}\)）**：LightGBM + LambdaRank 目标，每个（问题，池内 turn）对使用 10 个廉价特征——5 个相关性信号（bge-m3 余弦、全局稠密与 BM25 排名对数、融合池位置、bge-reranker-v2-m3 交叉编码器分数）与 5 个 turn 上下文（是否用户角色、会话内相对位置、年龄天数对数、长度对数、与问题共享的 spaCy 关键词）。训练标签为 152 个开发问题的 gold 标注，共 19,456 对。
  - **列表构建（填充）**：按排序贪心填充至 \(B=2{,}700\) tokens，放不下的 turn 跳过继续；渲染时按会话分组、按日期排序，采用官方 LongMemEval 格式。不做逐问题截断。
  - **可选写时记录**：Qwen3-32B 每会话读一次，写出带日期、实体、引用 turn 的类型化记录；记录通道向 128 池追加最多 32 个被引用 turn；相对时间标签把引用记录日期附着到含相对时间表达的 turn 上（仅保留不晚于问题日期的日期）。选择阶段仍无 LLM 调用。
