## 摘要
在专业领域部署 LLM 智能体通常需要细粒度、任务特定的流程与知识，而通用模型缺乏这些内容；然而参数训练成本高且不可解释，手工设计的智能体系统则将成本转嫁给专家劳动。情景记忆在上下文层面进行更新，但单智能体自适应难以缓解跨任务干扰，尤其是在多应用导航或数据池分析等复杂任务中。尽管多智能体演化可以缓解该问题，但现有方法对更新规则缺乏清晰定义，并依赖骨干模型决定系统在何处以及发生多大变化。这种范围界定不清的演化使学习遵循骨干模型的结构偏好，而非观测到的失败：一个骨干模型会累积技能，而另一个则会生成智能体。我们提出 EMMA（面向多智能体工作流合成的结构化情景记忆），它将多智能体系统的配置（控制器路由记忆、继承通用提示的专家智能体，以及每步过程性技能）视为情景记忆。EMMA 明确了更新的归属与可接受性：反射器将每个诊断出的失败分配给拥有其纠正范围的对象，并在该范围内提出一次编辑；与骨干模型无关的守卫确保每次被接受的编辑都限定在范围内、增量式且受约束。在 KramaBench、AppWorld 和 BBEH 上，使用五个骨干模型和四个基线（ACE、GEPA、EvoMAS 和 ADAS），EMMA 在每个基准上都取得最佳总体性能，相较最强基线最高提升 32.5%，在不同骨干模型上保持一致的改进，并且相比最高效的基线减少 17–38% 的训练执行次数。

## Abstract
Deploying LLM agents in specialized domains often require fine-grained task-specific procedures and knowledge a general model lacks, yet parameter training is costly and non-interpretable, and hand-engineered agent systems shift the cost to expert labor. Episodic memory updates at context level, but single agent adaptation struggles to alleviate cross-task interference, especially with complex tasks such as multi-application navigation or data pool analysis. Although multi-agent evolution alleviates this problem, existing methods lack clear definitions on update rules and rely on the backbone model to decide where and how much the system changes. This ill-scoped evolution makes learning follow the backbone's structural preferences rather than the observed failures: one backbone accumulates skills while another spawns agents. We present EMMA (structured Episodic Memory for Multi-Agent workflow synthesis), which treats the configuration of a multi-agent system (controller routing memory, specialists inheriting a generalist prompt, and per-step procedural skills) as episodic memory. EMMA makes the ownership and admissibility of updates explicit: a reflector assigns each diagnosed failure to the scope owning its correction and proposes one edit within it, and backbone-independent guards keep every accepted edit scoped, incremental and bounded. Across KramaBench, AppWorld and BBEH with five backbones and four baselines (ACE, GEPA, EvoMAS and ADAS), EMMA attains the best overall performance on every benchmark, up to 32.5% over the strongest baseline, maintains consistent improvements across backbones, and uses 17-38% fewer training executions than the most efficient baseline.

## 1. 核心问题与研究动机

- **背景需求**：在专业领域（如数据湖分析、多应用导航）部署 LLM 智能体，需要细粒度、任务特定的流程与领域知识，而通用模型并不具备这些知识。
- **现有两条路径各有代价**：
  - **参数训练**（SFT、GRPO、DAPO 等）：计算昂贵，且产物不可检视、不可选择性修正。
  - **人工设计智能体系统**（ChatDev、MetaGPT、AutoGen、Magentic-One 等）：效果好，但成本转嫁给专家劳动，每个新领域都要重新编写。
- **情景记忆路线**（Reflexion、A-Mem、MemRL、ACE、GEPA）：把经验存为文本、冻结模型权重，但都只适配**单个通用 ReAct 智能体**的上下文。面对数据湖分析等复杂任务时，单智能体无法按子任务特化行为，失败只在长轨迹末端才可观测，学习信号无法归因到具体步骤。
- **多智能体演化路线**（EvoMAS、EvoAgent、ADAS、AFlow）：搜索智能体配置或程序，但**更新规则界定不清**——由骨干模型自行决定“改哪里、改多少”。
- **关键问题（图 1）**：缺乏范围约束时，更新退化为骨干模型的“结构习惯”——Claude Opus 5 倾向累积技能（单基准创建 18 个技能），DeepSeek v3.2 倾向生成智能体（83 个训练任务创建 114 个智能体）。学习因此跟随骨干模型的结构偏好，而非观测到的失败。
- **核心主张**：应把多智能体系统配置本身视为情景记忆，并让**失败诊断决定更新的归属与幅度**，而非让骨干模型自由发挥。

## 2. 方法论

### 2.1 核心思想
将多智能体配置（控制器路由记忆、继承通用提示的专家智能体、每步过程性技能）作为可读写的**结构化情景记忆**；每次失败经诊断后被分配到唯一“作用域”，只允许在该域内做**一次受守卫的编辑**，并在新环境中重跑验证。

### 2.2 问题形式化（Definition 1）
- 固定骨干参数 θ，给定训练集 D_train 与初始记忆 M₀，仅用 D_train 求：
  - **M\* = argmax_M E_{q∼Q}[v(q, Exec_θ(M, q))]**
- 评估时记忆冻结，Update 不再作用于留出任务；因无梯度，“改哪里、改多少”是显式设计选择。

### 2.3 三级分层记忆 M = (C, A, S)
| 层级 | 内容 | 回答的问题 |
|---|---|---|
| **控制器记忆 C** | 主题 + 摘要 + 领域标签 + 通用性标签（general / domain-specific / task-specific） | 任务如何**分解与路由** |
| **智能体池 A** | 系统提示 p_j、输入/输出契约、Python 工具 | 智能体**如何工作** |
| **技能池 S** | 子问题类别的短流程，按“何时使用”一行描述索引 | 一类子问题**如何求解** |

- **提示继承**：新专家继承通用智能体当前提示，**p̃_j = p₀ ∥ p_j**，通用习惯写一次即可传播到所有专家。
- **按索引选择**：控制器读取索引自行挑选要加载的条目，允许“不加载”（无关记忆会损害规划）。

### 2.4 逐步合成与溢出分解
- 控制器输出有序计划，**一次只派发一步** (q_t, a_t, S_t, κ_t) = π_c(q, C_q, A, S, h_{t−1})，读取输出后再决定继续、修订剩余步骤或终止。
- 子智能体只收到“控制器整理的先前输出摘要”κ_t，控制上下文规模。
- **溢出分解**：步骤耗尽子智能体上下文或轮次时，视为“子任务粒度过粗”而非智能体失败——控制器用部分轨迹把该步拆成更小步骤、拼接回计划、在原位置续跑；溢出同时作为反思证据。

### 2.5 训练流程（尝试链 + 结构化反思 + 受守卫编辑）
1. **Rollout**：新环境执行，用任务自身信号（LLM 裁判 / 单元测试 / 精确匹配）门控。
2. **反思器输入**：完整轨迹（计划、代码、评估器解释、历史修订、参与智能体完整提示、注入技能、溢出事件），可下钻查看执行日志。
3. **反思四步**：定位失败步骤 → 分类到五类作用域 → 泛化（不提及本任务实体/答案）→ 最小化，输出**恰好一个动作**。
4. **作用域—动作所有权表（Table 1）**：
   - `execution_slip` → 仅本任务计划指令（REVISE_PLAN / NO_CHANGE）
   - `agent_behavior` → 智能体提示（REFINE_PROMPT）
   - `procedure` → 技能池（REVISE_SKILL / CREATE_SKILL）
   - `missing_capability` → 先技能、后智能体（CREATE_SKILL / CREATE_AGENT）
   - `routing` → 控制器记忆（MEMORY_NOTE / REVISE_PLAN；溢出时可 CREATE_AGENT）
5. **程序化守卫（与骨干无关）**：
   - 作用域—动作兼容性
   - 提示保留（≥60% 原行存活、仅能改参与过的智能体、<6000 字符）
   - 有界增长（智能体 ≤10、技能 ≤40、技能 <3000 字符）
   - 无泄漏（不得含答案或任务原文 ≥15 词跨度）
   - 策略变更（任一层级不得连续 >2 次失败修订仍被编辑；同一步连续两次溢出必须改变工作拆分方式）
   - 被拒提案把原因反馈给反思器（3 轮），仍失败则 NO_CHANGE。
6. **训练设置**：单遍、固定顺序；接受编辑无论重跑结果如何都保留；每任务后写 ≤2 条控制器记忆并快照；最终冻结。
7. **推理**：保留记忆选择、重规划、溢出分解；不调用反思器、不写入。
